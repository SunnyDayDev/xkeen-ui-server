# Прототип xkeen-ui-server: сценарии и смысл решений

## Назначение документа

Документ сохраняет продуктовую идею прототипа: что показано на экранах, зачем это нужно и какое поведение следует описать в будущих OpenSpec-спецификациях. Основан на обсуждённых решениях и проверке макета [xkeen-ui-server-design.pen](../design/xkeen-ui-server-design.pen), экраны 00–16 и обзорная схема. Дата сверки: 2026-09-05.

Это основа для спецификаций, а не спецификация всего продукта и не перечень реализованных возможностей. Центральный сервис, агент и веб-интерфейс пока не реализованы. Реальный эксперимент с Entware/XKeen/Xray описан отдельно в [стенде](../lab/README.md) и [его спецификации](../openspec/specs/router-lab/spec.md).

В тексте различаются:

- **Согласованное поведение** — решения, которые нужно сохранить при реализации.
- **Решение прототипа** — способ показать это поведение: расположение, подписи, формы и действия. Его можно уточнять, сохраняя смысл.
- **Открытый вопрос** — поведение, которое ещё нельзя переносить в спецификацию как утверждённое.

Поздние уточнения из обсуждения имеют приоритет над устаревшими подписями макета. Такие расхождения перечислены в конце документа. Адреса, имена, ревизии, количества элементов и версии на экранах — демонстрационные данные.

## 1. Продуктовая идея

У нескольких роутеров много общей конфигурации, но у каждого остаются собственные параметры и исключения. Пользователь описывает общее один раз и получает возможность менять его сразу для всей группы, сохраняя индивидуальную настройку устройств.

Центральный сервис хранит общие шаблоны **и все индивидуальные настройки**. Агент роутера получает уже собранную конфигурацию, применяет её и сообщает результат. «Локальное» в интерфейсе означает «для этого роутера»; такое изменение тоже хранится на центральном сервисе.

```text
Template elements + variables + default order
                        |
Router values + replacements + exclusions + local elements/order
                        |
                        v
                Effective configuration
                        |
              Validation + apply plan
                        |
                        v
                 Router agent
                        |
              Files + Xray API / XKeen
                        |
                        v
                Application result
```

Пользователь должен понимать три вещи: откуда взялось конкретное значение, какие устройства затронет изменение и что уже применено на каждом устройстве. Этим объясняются плашки происхождения, предпросмотр итоговых файлов и отдельные статусы связи и применения.

### Основные понятия

| Понятие | Смысл в прототипе |
| --- | --- |
| Шаблон / профиль | Общая конфигурация для группы роутеров. «Базовый профиль» — пример названия шаблона, а не особый встроенный тип |
| Секция | Группа элементов в редакторе: входы, выходы, маршрутизация, DNS и т. д. |
| Элемент / блок | Единица наследования со стабильным ID, содержимым и собственными переменными |
| ID блока | Связывает элемент шаблона с его переопределением; сохраняется при полной замене |
| Идентификатор для роутинга | Xray `tag`, на который ссылаются правила. Его точная связь с ID блока ещё требует решения |
| Значения переменных | Персональные параметры роутера при сохранении структуры шаблона |
| Полная замена | Собственное содержимое вместо содержимого общего блока; связь по ID сохраняется |
| Локальный элемент | Дополнительный элемент, существующий только для выбранного роутера |
| Желаемая ревизия | Конфигурация, которую центральный сервис ожидает увидеть на устройстве |
| Применённая ревизия | Конфигурация, для которой агент завершил применение и проверку |

Стабильные ID нужны, чтобы наследование не зависело от позиции в списке. Они не должны принуждать пользователя к фиксированному порядку правил.

## 3. Навигация и жизнь роутера

**Согласовано.** В боковой панели есть «Шаблоны», «Роутеры» и «Настройки». Устройства вложены в раздел «Роутеры» с небольшим **отступом слева**, а не дополнительным промежутком сверху. У каждого устройства свой индикатор статуса.

Раздел «Роутеры» открывает общий экран 00 с инструкцией и списком. Выбор конкретного устройства открывает его страницу. Внутри устройства используются вкладки «Общее», «Входы», «Выходы», «Маршрутизация», «Итоговый конфиг».

Однажды подключившийся роутер остаётся в списке и боковой панели, даже если агент недоступен. Это позволяет видеть ожидающие применения устройства. Название редактируется на экране 03 и не меняет техническую идентичность устройства.

«Общий шаблон» на странице роутера — **выпадающий список**, поскольку устройство может использовать другой профиль. Прототип показывает действие выбора; судьба существующих значений и переопределений при смене профиля ещё не определена.

Удаление находится на странице роутера. Оно убирает устройство из списка, но при следующем подключении агента устройство появляется снова. Удаление не означает отзыв ключа. Правила сохранения имени, персональных настроек и истории при этом действии остаются открытыми.

**Почему так.** Видимость устройства, его название, право подключения и конфигурация — разные вещи. Интерфейс не должен создавать впечатление, что исчезновение строки остановило агент или запретило ему подключаться.

## 4. Подключение: сначала параметры, затем агент

Сценарий проходит через экраны 00 → 09 → 12 → 03:

1. Пользователь создаёт подключение, задаёт название и выбирает шаблон.
2. Форма показывает переменные элементов выбранного шаблона. Значения без дефолта обязательны; значения с дефолтом можно унаследовать.
3. Пока обязательное значение отсутствует или не соответствует типу, продолжение недоступно. Ошибка находится рядом с полем, например `${clientId}`.
4. После заполнения доступны адрес сервера, индивидуальный ключ и настройки агента.
5. Пользователь устанавливает агент и передаёт настройки. Агент сам подключается к серверу, получает конфигурацию и сообщает результат.
6. После первого подключения устройство появляется в списке и боковой панели. Ожидание подключения и успешное применение — разные состояния.

Смена шаблона на первом шаге требует повторной проверки обязательных параметров. Ключ связывает агент с подготовленной конфигурацией устройства. IP показывается для диагностики, но не служит идентичностью роутера.

**Почему так.** Устройство должно начинать работу с конфигурацией, для которой уже известны необходимые значения. Пользователь видит проблему до установки и не вынужден выяснять причину ошибки по журналам роутера.

### Уточнение установки после создания макета

На старте проекту не нужны собственные `.ipk` и репозиторий opkg-пакетов. Согласованный путь — исполняемые файлы/скрипты на роутере и служба в Entware `init.d`, затем инструкция и установочный скрипт из GitHub. Желаемый формат — `curl -fsSL <URL установщика> | sh`; точные URL и параметры ещё не определены. Сервер также должен запускаться в Docker.

В обсуждении предложена раскладка агента: запуск из `/opt/sbin/xkeen-agent`, дополнительные файлы в `/opt/lib/xkeen-agent/`, настройки в `/opt/etc/xkeen-agent/`, состояние в `/opt/var/lib/xkeen-agent/`, init-скрипт `/opt/etc/init.d/S99xkeen-agent`. Это ориентир для спецификации установки; конкретные имена и номер старта не являются готовым контрактом.

Для скрипта предложены выбор роли «сервер/агент» и сохранение настроек и ключей при повторной установке. Детали обновления и удаления службы предстоит описать отдельно. Entware/opkg остаётся окружением устройства и способом получения его зависимостей.

## 5. Шаблон: произвольный JSON и переменные каждого блока

Экран 01 показывает шаблоны и область их использования. Отдельный профиль нужен группе устройств с другой базовой конфигурацией. Копирование профиля — показанный в прототипе способ начать такой вариант; правила копирования ID и связей ещё требуют спецификации.

Экран 02 устроен как список секций и редактор выбранного элемента. У элемента видны ID, сырой JSON и определения переменных: имя, тип, дефолт и признак скрываемого значения.

**Согласовано.** Неизменяемые поля предзаполняются в JSON шаблона. Изменяемые значения описываются переменными. Пользователь может задать любую структуру JSON, включая поля и протоколы, для которых у интерфейса нет специальных форм. «Добавить элемент» не должно замыкать модель на показанных примерах секций.

**Почему так.** Сервис управляет конфигурацией через шаблоны. Поддержка нового поля Xray не должна требовать разработки и выпуска новой формы интерфейса.

### Синтаксис переменных

Используется `${variableName}`. В JSON и у поля ввода показывается одна и та же ссылка: например, «Порт · `${serverPort}`». Имя принадлежит конкретному элементу и ищется целиком. В `${server.address}` точка — часть имени, а не доступ к вложенному объекту.

Подстановка целого JSON-значения сохраняет тип. Иллюстрация синтаксиса шаблона:

```json
{
  "address": "${server.address}",
  "port": "${serverPort}",
  "streamSettings": "${streamSettings}"
}
```

При подстановке `serverPort` типа number строка-ссылка становится числом; `streamSettings` типа object становится объектом. Это фрагмент, показывающий механизм, а не полный конфиг Xray. Для объектов и массивов прототип предусматривает JSON-редактор значений.

Отсутствие дефолта делает переменную обязательной. Дефолт и индивидуальное значение различимы: пользователь может вернуться к значению шаблона. Скрытые поля в макете означают маскирование значения в интерфейсе; способ его хранения ещё не выбран.

Проверка JSON-синтаксиса, типов переменных, ссылок между элементами и совместимости готовой конфигурации с Xray — отдельные проверки. Возможность ввести произвольный JSON не отменяет проверку итогового результата.

Интерполяция внутри длинной строки, литеральный `${...}`, имена с `}`, `null` и точные правила пустых значений остаются открытыми. Скобки выбраны для явной границы имени и поддержки точек и других символов; они не превращают содержимое в исполняемое выражение.

## 6. Два режима переопределения и происхождение элементов

Экраны 10 и 11 отдельно раскрывают два режима, также доступные из редакторов роутера.

| Режим | Что задаёт роутер | Что продолжает приходить из шаблона |
| --- | --- | --- |
| Только переменные | Значения объявленных переменных | Структура JSON, постоянные поля и определения переменных |
| Свой JSON | Готовое содержимое блока целиком | Связь с исходным блоком по неизменному ID; содержимое и переменные не подмешиваются |

**Согласовано.** ID заменяемого блока всегда совпадает с ID блока шаблона. Он показывается вне JSON-редактора и не редактируется. Полная замена позволяет даже изменить протокол внутри блока, сохранив его место в модели наследования. Политика изменения Xray `tag` отдельно не согласована.

Полная замена не является частичным наложением JSON. Если в шаблоне изменилось содержимое этого блока, собственное содержимое роутера сохраняется. Остальные наследуемые элементы устройства продолжают получать общие изменения.

«Убрать переопределение» возвращает наследование. «Отмена» закрывает редактирование без сохранения текущей правки; это другое действие. Для смены режимов с уже введёнными данными ещё нужно определить сохранение черновика.

Локальный элемент не заменяет общий блок: он добавлен только для выбранного роутера. Его ID должен позволять ссылаться на элемент и хранить его позицию; правила генерации и уникальности предстоит уточнить.

**Почему так.** Обычная персонализация должна сохранять будущие общие обновления. Полная замена нужна для случаев, когда роутеру требуется другая структура. Явный выбор режима показывает пользователю, какую часть наследования он меняет.

## 7. Маршрутизация: итоговый порядок и независимое наследование

Экран 06 показывает единый итоговый список общих и локальных правил. В нём одновременно видны унаследованное правило, отключённое общее правило, локальное правило и полная замена.

**Согласовано.** Есть одна кнопка «Добавить правило» и перетаскивание. Переставлять можно **как общие, так и локальные правила**. Пользователь может вставить локальное правило между общими, отключить общее или заменить его содержимое.

Порядок и содержимое наследуются независимо. Перестановка общего правила не должна создавать собственную копию JSON. В прототипе есть отдельное состояние «Порядок настроен для этого роутера» и действие «Вернуть порядок шаблона».

Список показывает реальный порядок проверки правил сверху вниз. Предупреждение после завершающего правила объясняет, почему более поздние правила могут не работать. Подпись `catch-all` сама по себе не доказывает, что правило безусловное: будущая проверка должна учитывать его содержимое.

**Почему так.** Связь по ID позволяет централизованно обновлять правило, даже если на устройстве оно перемещено. Пользователь должен видеть результат совместного порядка, а не вычислять его по раздельным спискам исключений.

Ещё не определено, куда помещать новое общее правило при уже изменённом порядке роутера, что делать при удалении исходного правила и как восстанавливать порядок шаблона при наличии локальных элементов. Эти случаи нельзя решать молчаливой вставкой в произвольную позицию.

## 8. Входы, выходы и ссылки из роутинга

На экранах 04, 05 и 13 список элементов находится рядом с настройками выбранного элемента. Видны происхождение, ID блока и идентификатор для роутинга.

**Согласовано.** У входов есть вкл/выкл; входы и выходы можно переопределять и удалять. На их идентификаторы можно ссылаться в роутинге. Отдельный переключатель вкл/выкл для выходов пока не является согласованным требованием.

Вход нельзя выключить или удалить, если на него ссылается итоговый роутинг. Экран 04 показывает заблокированные действия, объяснение и список зависимых правил с переходом к ним. Экран 13 показывает противоположное состояние: у свободного входа действия доступны.

Проверка должна учитывать шаблон, собственный JSON, локальные правила и все переопределения. Сервер повторяет её при сохранении: одна только блокировка кнопки не гарантирует корректность конфигурации. Сначала пользователь изменяет ссылки, затем выключает или удаляет вход.

Удаление общего элемента только для одного роутера должно сохраняться как персональное исключение, иначе элемент вернётся при следующей сборке. Представление такого исключения ещё не выбрано. Отдельно предстоит решить UX удаления используемого выхода и участие отключённых правил в анализе зависимостей; итоговый применяемый конфиг не должен содержать неразрешённых ссылок.

**Почему так.** Пользователю нужна свобода настройки, но ошибка в одном элементе не должна незаметно ломать зависимые правила. Причина запрета и путь её устранения показаны непосредственно рядом с действием.

## 9. Итоговый конфиг и проверка общего изменения

### Экран 07: результат сборки

Показан готовый файл после подстановки значений, переопределений, отключений и определения порядка. Файл выбирается в списке, доступен для чтения и скачивания. Панель происхождения объясняет, какие части пришли из шаблона, добавлены локально, заменены или исключены.

**Идея.** Пользователь может проверить конкретный результат и связать его с исходными настройками. Редактирование производится в шаблоне или настройках роутера; изменение текста предпросмотра не создаёт ещё один источник конфигурации.

JSON на экране сокращён для объяснения. Он не задаёт алгоритм сериализации, правила удаления неизвестных полей или полный формат ревизии. Готовые файлы должны сохранять все заданные поля, включая не показанные в примере.

### Экран 08: последствия до применения

Для изменения общего правила показаны три разных результата:

| Роутер | Причина | Результат |
| --- | --- | --- |
| A | Этот блок полностью заменён | Итоговое содержимое не меняется; применять нечего |
| B | Блок наследуется, агент на связи | Получит новую ревизию; в примере достаточно API и записи файла |
| C | Блок наследуется, агент недоступен | Желаемое состояние сохраняется; обновление будет получено при подключении |

Показаны «было/будет», количество затронутых устройств и план применения. «Сохранить и применить» завершает проверку. Границы сохранения черновика и публикации ревизии ещё требуют спецификации.

**Почему так.** Изменение общего шаблона не обязательно меняет каждый использующий его роутер. Проверка должна опираться на итоговую конфигурацию каждого устройства с учётом переопределений.

## 10. Доставка, применение и честный статус

Агент сам подключается к центральному сервису и идентифицируется ключом. Раз в 60 секунд сообщает доступность и IP; состояние ревизии позволяет сверять актуальность. При подключении или восстановлении связи получает актуальную конфигурацию. Подписка на уведомления ускоряет доставку изменения, а периодическая сверка помогает восстановиться после пропущенного уведомления.

Конкретный транспорт не выбран. Статус активности не означает, что серверу нужен входящий порт на роутере или что нужно отправлять команду напрямую на заявленный IP.

Сервис пересобирает затронутые конфигурации. Если итоговый результат не изменился, повторное применение не требуется. На обзорной схеме для этого показан hash; алгоритм сравнения и канонизация JSON ещё не определены.

| Изменение | Согласованное направление применения |
| --- | --- |
| Поддерживаемая замена правил маршрутизации | Подготовить весь файл и проверить полный конфиг; заменить весь набор правил через API Xray; записать файл; проверить результат |
| Входы и изменения вне возможностей API | Подготовить и проверить файлы; записать их; перезапустить XKeen; проверить результат |
| `exclude_ips` | Отдельный файл XKeen и применение его сетевых настроек; в прототипе показан рестарт XKeen |

API применения — API **Xray**. XKeen отвечает за управление процессом и интеграцию с сетевым окружением. Поддержка произвольного JSON не означает, что каждое его поле меняется без рестарта.

[Эксперимент](../lab/results/arm64.md) подтвердил замену набора правил через API без смены процесса и сохранение поведения после записи и рестарта. Это не обещание горячего применения всех полей `routing`: например, `domainStrategy` в проверенном релизе таким способом не обновляется. XKeen проверен в режиме `Other`; прозрачный перехват и `exclude_ips` ещё не проверены.

Вызов API и запись файлов не являются общей атомарной операцией. Последняя рабочая ревизия, журнал применения и восстановление показаны как направление будущего агента. Сбой между операциями и неудачный откат должны быть различимы; точный протокол восстановления ещё предстоит спроектировать.

Связь и результат применения отображаются отдельно:

| Ситуация | Что должен понимать пользователь |
| --- | --- |
| На связи, нужная ревизия применена | Устройство доступно и актуально |
| На связи, ревизия отстаёт | Подключение есть, но изменение ещё не завершено или возникла ошибка |
| Нет связи | Устройство остаётся в списке; актуальная ревизия ожидает подключения |
| Ошибка проверки или применения | Получение конфигурации не засчитывается как её успешное применение |
| Неуспешный откат | Восстановление также завершилось ошибкой и требует внимания |

«Применено» означает завершённую запись и проверку работающей конфигурации. Время последнего контакта, желаемая и применённая ревизии объясняют краткий статус в боковой панели.

## 11. XKeen `exclude_ips`

**Согласовано.** Общие шаблоны должны охватывать и исключения IP XKeen. Это отдельная часть конфигурации, а не поле `routing` или другая секция Xray.

На экране 16 показано решение прототипа:

- группа «XKeen» в списке секций и элемент `exclude_ips`;
- текстовый список, один IP-адрес или CIDR на строку;
- переменные `${bypass.network}` и `${upstream.address}`, их дефолты и обязательность;
- выходной файл `/opt/etc/xkeen/ip_exclude.lst`;
- пояснение о записи списка и рестарте XKeen для применения firewall;
- возможность изменить значения переменных или заменить список целиком, сохранив ID элемента.

**Почему так.** Единый источник истины должен охватывать настройки, влияющие на попадание трафика в Xray. Представление элемента выбирается по его реальному формату: здесь нужен список, а не искусственная JSON-секция.

Форма списка и два режима его персонализации показаны как продолжение общей модели. Отдельные экраны переопределения `exclude_ips` и его размещение на странице конкретного роутера пока не нарисованы. Правила IPv4/IPv6, комментариев, дублей, пустого списка и переменных, разворачивающихся в несколько строк, требуют спецификации.

На устройстве только с Xray элемент не применяется. Как именно показывать неподдерживаемый элемент и можно ли опубликовать такую ревизию для этого устройства — открытый вопрос. Пропуск элемента не должен ошибочно подтверждать его применение.

## 12. Настройки внешнего API

Экраны 14 и 15 показывают два поддерживаемых состояния внешнего API управления. Через него сторонний клиент должен управлять теми же объектами и действиями, что доступны в UI: шаблонами, устройствами, параметрами, переопределениями, применением и настройками.

**Согласовано.** Есть отдельные переключатели «Внешний API» и «Авторизация API». Авторизация опциональна: приватное развёртывание может использовать API без токена. Этот режим должен быть явно виден.

| Канал | Назначение | Отношение к переключателю внешнего API |
| --- | --- | --- |
| Веб-интерфейс | Действия пользователя | Продолжает работать |
| Внешний API сервиса | Управление из внешних приложений | Включается и выключается переключателем |
| Протокол агента | Ключ устройства, получение конфигурации и отчёты | Продолжает работать, идентификация устройства сохраняется |
| API Xray | Применение поддерживаемых изменений внутри устройства | Не является внешним API центрального сервиса |

Токен внешнего API и индивидуальный ключ агента выполняют разные задачи. Отключение авторизации внешнего API не означает отключение ключей роутеров и не определяет вход в веб-интерфейс.

**Решение прототипа.** Показаны скрытый токен, копирование, замена и `Authorization: Bearer <token>`. Конкретная схема токенов, количество клиентов, ротация, хранение, права и начальные положения переключателей ещё не утверждены. Экран с включённым API не задаёт установочный дефолт.

**Почему так.** Возможность автоматизации нужна независимо от конкретного внешнего клиента. Управление доступом не должно прерывать синхронизацию устройств или лишать пользователя интерфейса, из которого API включается обратно.

Названия уровней используют принятые термины: **Tokens → Atoms → Molecules → Organisms**. Повторяющиеся элементы оформлены компонентами и экземплярами, чтобы смысл и состояния сохранялись на всех экранах.

### Происхождение и статус — разные признаки

| Подпись происхождения | Значение |
| --- | --- |
| Из шаблона | Содержимое наследуется |
| Параметры / Только переменные | Значения настроены для устройства, структура продолжает наследоваться |
| Заменено / Полная замена | Используется собственное содержимое общего блока |

Индикатор устройства показывает состояние связи и применения: зелёный — на связи и актуален, янтарный — требуется внимание, серый — нет связи. Текст на странице объясняет причину; цвет не заменяет объяснение. Серый заблокированный переключатель входа также не должен восприниматься как доступное действие или обозначать отсутствие связи.

| Установка | URL, параметры, архитектуры, обновление и удаление службы | Превратить рисунок подключения в рабочую инструкцию |
| Полнота интерфейса | Пустые состояния, загрузка, недоступность сервера, узкие экраны, клавиатура | Прототип показывает основные сценарии, но не все состояния готового продукта |

Эти замечания позволяют использовать прототип как основу, не превращая устаревшие подписи и условные примеры в требования.

## 17. Как использовать документ при подготовке OpenSpec

Для очередного небольшого изменения выбрать сценарий и связанные экраны, перенести согласованное поведение в проверяемые требования и отдельно разрешить влияющие на него открытые вопросы. В `design.md` изменения сохранить причины выбора и ссылки на соответствующие разделы этого документа. В задачах связать реализацию с наблюдаемым результатом сценария.

Например, подключение затрагивает экраны 00/09/12/03, а переопределение — 02/05/10/11/07/08. Один экран может обслуживать несколько возможностей; один OpenSpec change не обязан реализовывать все нарисованные страницы.

При новом решении обновлять этот документ и связанные предметные документы. Завершённые и синхронизированные спецификации в `openspec/specs/` описывают уже принятый контракт своей области. Прототип сохраняет общий замысел и основания, но не должен молча менять этот контракт.
