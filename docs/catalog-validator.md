# Изолированная проверка каталога Xray

Внутренний клиент C06.2 проверяет один подготовленный каталог. Владелец явно выбирает локальный Unix socket или HTTPS-адрес доверенного исполнителя. Во втором случае оператор исполнителя получает все файлы в открытом для него виде, включая пароли, ключи и персональные значения. TLS защищает их в пути. Отказ или недоступность проверки блокируют публикацию. Сервер может продолжать работу с черновиками.

## Размещение

Запустите `xkeen-validator` на отдельном доверенном Linux-хосте с локальным Docker Engine либо на Docker-хосте сервера. Только этот worker получает доступ к Unix socket Docker. Учетную запись worker следует считать администратором Docker-хоста. Для каталога состояния используйте выделенную приватную директорию с режимом 0700, желательно на tmpfs без резервного копирования. При запуске и перед следующим запросом worker освобождает оставшиеся после сбоя задания. Процесс PID 1 в задании ограничивает выполнение Xray даже при завершении worker.

При локальной поставке приложению нужен доступ только к приватному Unix socket worker. Для сервера в контейнере смонтируйте каталог этого socket: права владельца/группы должны разрешать соединение, каталоги пути должны принадлежать root или UID приложения и быть защищены от записи посторонними. Каталог состояния и Docker socket приложению не требуются. На Entware aarch64 можно явно настроить удалённый worker. При отсутствии доступного изолированного исполнителя проверка возвращает `ErrValidatorUnavailable`. Проверенный путь Entware использует обычный непривилегированный клиент.

## Образ и запуск worker

Соберите `cmd/xkeen-validator` для хоста. Для одноразового образа используйте [Dockerfile](../lab/validator.Dockerfile), бинарник `cmd/xkeen-validator-run` под архитектуру образа и доверенный локальный образ-источник с закреплённым Xray 26.3.27 по пути `/opt/sbin/xray` и согласованными assets в `/opt/etc/xray/dat/`. Оператор проверяет источник, состав и контрольную сумму образа по доверенному манифесту поставки. До настройки worker сравните полученный ID с утверждённым ID. Для локальной демонстрации пример сборки со своим исходным образом arm64:

```sh
context=$(mktemp -d)
CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build -trimpath -o "$context/check" ./cmd/xkeen-validator-run
chmod 0755 "$context/check"
docker build --platform linux/arm64 --pull=false --network=none \
  --build-arg "XRAY_SOURCE=$TRUSTED_SOURCE" --iidfile "$context/image-id" \
  -f lab/validator.Dockerfile "$context"
go build -trimpath -o ./xkeen-validator ./cmd/xkeen-validator
```

Запуск в локальном режиме для заранее созданных приватных каталогов:

```sh
./xkeen-validator -image "$APPROVED_IMAGE_ID" -state "$WORKER_STATE" -socket "$WORKER_SOCKET"
```

Worker проверяет версию в том же неизменяемом образе. Запуск требует Docker Engine c memory/swap, PID, CPU quota и seccomp. Образ запускается по ID с `--pull=never`. Корень и каталог проверяемых файлов доступны только для чтения; внутри среды исполнитель сверяет digest полного набора. Xray запускается с `run -test`, отдельным UID, без capabilities и внешней сети. Журналы под `/opt/var/log/xray` помещаются в приватный tmpfs на 1 MiB. Другие файлы профиля должны быть явно предусмотрены утверждённым образом. Ссылки на файлы работающего устройства могут потребовать дополнительного профиля в будущем.

## Внешний исполнитель

Передайте серверу фиксированный HTTPS origin через `--validator-origin`, отдельную доверенную CA через `--validator-ca` и клиентскую пару mTLS через `--validator-client-cert` и `--validator-client-key`. Для локального режима укажите абсолютный `--validator-socket`. [Подготовка роутера](server-skeleton.md#подготовка-роутера-f09) использует одну из этих настроек. Со стороны worker задайте серверный сертификат и ключ, CA клиента и SHA-256 разрешённого конечного клиентского сертификата. Держите ключи у их владельцев, с приватными правами, вне образа и каталога заданий. Пример запуска:

```sh
./xkeen-validator -image "$APPROVED_IMAGE_ID" -state "$WORKER_STATE" \
  -listen "$WORKER_LISTEN" -cert "$WORKER_CERT" -key "$WORKER_KEY" \
  -client-ca "$CLIENT_CA" -client-sha256 "$ALLOWED_CLIENT_SHA256"
```

Worker и клиент используют TLS 1.3. Не включайте запись тел запросов, трассировку данных или TLS-терминацию сторонним сервисом. Клиент проверяет имя и цепочку сертификата исполнителя, игнорирует proxy из окружения и отклоняет перенаправления. Worker проверяет цепочку клиента и разрешённый отпечаток. При ротации обновите настройки обеих сторон и перезапустите worker. Переключение на другого получателя требует явной настройки. Публичной операции управления для вызова worker в C06.2 нет.

## Результаты и ограничения

Одна попытка привязана к случайной метке, профилю и SHA-256 по отсортированным именам и байтам с длинами полей. Пять обязательных файлов и необязательный `06_extra.json` ограничены 8 MiB суммарно. Worker принимает одну задачу одновременно. На контейнер выделены 128 MiB, 48 PID, половина CPU, ограничение открытых дескрипторов и 12 секунд выполнения. Весь запрос исполнителя ограничен 20 секундами, клиентский запрос — 30. Переполнение вывода, нарушение лимита, несовпадение версии/манифеста или неожиданный ответ дают недоступность. Доказанный отказ каталога возвращает `ErrCatalogRejected`. Неоднозначные ошибки Xray, в том числе ошибки чтения ресурсов, дают недоступность. Сырой вывод и содержимое файлов не включаются в ошибки и журналы.

`lab/check-validator.sh` собирает образ из лабораторного Xray и запускает синтетические положительную и отрицательную проверки, проверку временного файлового журнала, очистку и положительный запрос от клиента Entware aarch64 через локальную тестовую пару mTLS. Для воспроизведения нужен локальный образ `xkeen-router-lab:dev` под arm64 и доступный Docker Engine. Проверенная среда — LinuxKit aarch64 в Docker Desktop. Совместимость ядра физического роутера с изоляцией worker не проверялась. [Порядок работы стенда](../lab/README.md)
