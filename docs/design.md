# Дизайн

Основной файл: [xkeen-ui-server-design.pen](../design/xkeen-ui-server-design.pen). Это редактируемый концепт интерфейса, а не работающее приложение. Данные в нём вымышленные. Файл читается и изменяется через MCP Pencil.

[Описание прототипа и причин решений](prototype.md) раскрывает сценарии каждого экрана, согласованное поведение и открытые вопросы для будущих спецификаций. Здесь хранится краткая карта макетов. Устаревшие подписи установки на экранах 00 и 12 перечислены в описании прототипа: актуальный путь — установочный скрипт и Entware `init.d`, без собственных `.ipk` на старте.

## Порядок работы над UI

**Согласовано:** если задача на любом этапе разработки затрагивает UI, сначала отражаем изменения в `design/xkeen-ui-server-design.pen` через MCP Pencil, затем реализуем интерфейс.

1. Описываем поведение и критерии готовности в OpenSpec, определяем затронутые экраны и состояния.
2. Обновляем макет с использованием дизайн-системы. Показываем применимые к сценарию состояния, включая ошибки, загрузку, пустые данные и недоступные действия. Если актуальный макет уже полностью описывает задачу, проверяем его и указываем соответствующие экраны в артефактах изменения.
3. До реализации проверяем размещение, обрезку, подписи, состояния и влияние изменений общих компонентов на затронутые экраны. При изменении сценариев или карты экранов актуализируем этот документ и [описание прототипа](prototype.md).
4. По спецификации и актуальному макету пишем тесты поведения UI, подтверждаем Red, затем реализуем интерфейс и выполняем Green/Refactor согласно [порядку TDD/BDD](architecture.md#tddbdd-от-сценария-к-тесту-и-реализации). Готовый UI дополнительно проверяем визуально по макету.

Этот порядок явно отражаем в задачах OpenSpec. Если при реализации требуется изменить интерфейс, сначала возвращаемся к макету и связанным сценариям, затем обновляем тесты и код. Обновление макета само по себе не означает, что поведение реализовано.

## Дизайн-система

- `Tokens`: цвета, типографика, отступы, радиусы и семантические состояния.
- `Atoms`: Button, Badge, Input, Select, Toggle, TextArea.
- `Molecules`: FormField, SelectField, RoutingRule, EndpointRow, RouterRow, NavItem, OverrideMode, SettingsRow.
- `Organisms`: общая Sidebar.

Цвета происхождения: синий — из шаблона или заполнены его переменные; фиолетовый — локальный элемент; янтарный — полная замена. Цвет статуса устройства не заменяет текстовое объяснение состояния на его странице.

## Навигация

Основные разделы: «Шаблоны», «Роутеры», «Настройки». Под «Роутеры» расположен список однажды подключившихся устройств с небольшим отступом слева и индикаторами статуса.

На общей странице роутеров находятся описание подключения и список устройств. Настройки отдельного роутера содержат переименование, выбор общего шаблона через выпадающий список и удаление из списка с пояснением о повторном появлении при следующем подключении.

## Карта экранов

| Номер | Экран |
| --- | --- |
| 00 | Роутеры: подключение и список |
| 01 | Шаблоны: список |
| 02 | Шаблоны: редактор элементов, сырого JSON и переменных |
| 03 | Роутер: общее |
| 04 | Роутер: входы, блокировка действий при зависимостях |
| 05 | Роутер: выходы |
| 06 | Роутер: маршрутизация и перетаскивание |
| 07 | Роутер: итоговый конфиг |
| 08 | Проверка изменений шаблона и плана применения |
| 09 | Подключение: профиль и обязательные переменные |
| 10 | Переопределение: только переменные |
| 11 | Переопределение: свой JSON |
| 12 | Подключение: ключ и установка агента |
| 13 | Вход без зависимостей: доступные действия |
| 14 | Настройки: внешний API с авторизацией |
| 15 | Настройки: внешний API без авторизации |
| 16 | Шаблоны: XKeen `exclude_ips`, текстовый список и переменные |

В редакторе шаблонов `exclude_ips` расположен в отдельной группе XKeen. Макет показывает список IP/CIDR с `${variableName}`, определения переменных и результат `/opt/etc/xkeen/ip_exclude.lst`. Это отдельный текстовый файл, а не секция JSON Xray. Предлагаемый редактор позволяет менять значения переменных или заменять список целиком с сохранением ID элемента. Изменение требует применения настроек XKeen/firewall; стенд только с Xray его не проверяет.

Отдельный обзорный фрейм показывает архитектуру, сборку конфигурации, синхронизацию и применение.

## Состояния, которые важно сохранять

- Подключение не продолжается, пока не заполнены обязательные переменные без дефолта.
- Имена переменных в JSON и подписях формы используют единый синтаксис `${variableName}`.
- При переопределении ID блока виден отдельно и не редактируется.
- Вход, используемый роутингом, нельзя выключить или удалить; видны зависимые правила.
- Полная замена, локальный элемент и изменение порядка не смешиваются в одно состояние.
- Доступность устройства и применение конфигурации показываются отдельно.
- Авторизация внешнего API опциональна; оба режима имеют явное описание.

Размеры, тексты и форма отдельных контролов могут уточняться. Наличие элемента в макете само по себе не означает завершённого технического решения; открытые вопросы перечислены в остальных документах.
