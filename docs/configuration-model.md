# Модель конфигурации

## Шаблон и элементы

Шаблон содержит элементы конфигурации: входы, выходы, правила маршрутизации и другие секции Xray. Каждый элемент Xray имеет стабильный ID, сырое JSON-содержимое и собственные определения переменных. Для настроек XKeen прототип также содержит `exclude_ips`: отдельный текстовый список с переменными, результатом которого является `/opt/etc/xkeen/ip_exclude.lst`, а не секция JSON Xray. Сценарий и открытые вопросы этого элемента описаны в [прототипе](prototype.md#11-xkeen-exclude_ips).

Редактор не должен ограничивать JSON набором известных протоколов или полей. Поддержка новой конфигурации не должна требовать разработки специальной формы: пользователь описывает JSON и объявляет нужные переменные. Проверка синтаксиса, типов переменных и связей выполняется отдельно от проверки конфигурации установленным Xray.

ID блока определяет его связь с шаблоном. При индивидуальном переопределении этот ID остаётся неизменным и показывается вне редактируемого содержимого.

Для ссылок в Xray используются идентификаторы входов и выходов (`tag`, `inboundTag`, `outboundTag`). Макеты показывают ID блока и идентификатор для роутинга отдельно. Точную модель их сопоставления, уникальности и допустимого изменения `tag` необходимо закрепить до реализации.

## Переменные

**Статус:** контракт A05 согласован; реализован отдельный шаг A06 для уже подготовленных значений. Выбор дефолтов, обязательность, проверка определений и полный синтаксис B01/B02 ещё не реализованы. Полные требования и граничные сценарии — в [спецификации переменных](../openspec/specs/configuration-variables/spec.md); текущий объём реализации описан ниже.

### Реализованный шаг A06

Функция `configuration.SubstituteValues` в [ядре](../internal/configuration/substitute.go) принимает ID элемента, сырой JSON шаблона и `map[string]json.RawMessage` с готовыми значениями одного элемента. Она подставляет целые ссылки в корне, объектах и массивах с сохранением пяти JSON-типов, неизвестных полей, порядка массива и точности чисел. Имена сравниваются целиком, включая точки, с учётом регистра и без нормализации.

Шаблон и каждое переданное значение проверяются как один JSON, включая неиспользуемые значения. Ошибки `invalid_json`, `duplicate_json_key` и `unknown_variable` содержат ID, источник, известное имя и путь либо байтовую позицию от нуля. Входы не меняются; результат имеет отдельный буфер, при ошибке он отсутствует. Диагностика не содержит значений или сырого JSON.

Минимальный вызов из Go-кода внутри проекта:

```go
result, issues := configuration.SubstituteValues(
    "outbound-demo",
    json.RawMessage(`{"port":"${port}"}`),
    map[string]json.RawMessage{"port": json.RawMessage(`443`)},
)
// result: {"port":443}; issues: пустой набор
```

Для примера нужны импорты `encoding/json` и `github.com/SunnyDayDev/xkeen-ui-server/internal/configuration`. Целевая проверка: `go test ./internal/configuration -count=1` при доступном [Go toolchain](server-skeleton.md#toolchain).

Эта операция не принимает определения и дефолты, не выбирает значения и не проверяет их соответствие объявленному типу. Она предназначена для подготовленного набора и корректных целых ссылок. Успех A06 не означает прохождения полной валидации: null, экранирование, некорректные/частичные ссылки и заполненность требуют B01/B02. Функция пока не подключена к HTTP, публикации или устройствам. Правила ниже описывают полный согласованный контракт, включая ещё не реализованные части.

### Ссылки и типы

Ссылка записывается как `${variableName}`. Например, `${clientId}` и `${server.address}`. Имя между скобками ищется целиком в определениях переменных конкретного элемента, с учётом регистра и без нормализации; точка не означает вложенный путь или доступ к свойству. Имя непустое, не содержит пробельных/управляющих символов и `$`, `{`, `}`. Остальные символы, включая точки, дефисы и буквы вне ASCII, разрешены. Дубликаты имён внутри элемента и значения для необъявленных имён отклоняются.

Пример содержимого элемента шаблона:

```json
{
  "tag": "primary-proxy",
  "protocol": "vless",
  "settings": {
    "address": "${server.address}",
    "port": "${serverPort}",
    "id": "${clientId}"
  },
  "streamSettings": "${streamSettings}"
}
```

Это пример синтаксиса шаблона, а не готовая конфигурация подключения. Он требует определений переменных и значений.

| Имя | Тип | Значение по умолчанию |
| --- | --- | --- |
| `server.address` | string | Нет — нужно заполнить |
| `serverPort` | number | `443` |
| `clientId` | string, скрываемое значение | Нет — нужно заполнить |
| `streamSettings` | object | Задаётся JSON-объектом в шаблоне |

Если JSON-значение целиком является ссылкой на переменную, оно заменяется значением объявленного типа. Например, строка `"${serverPort}"` превращается в число `443`, а `"${streamSettings}"` — в объект. Поддерживаются строки, числа, boolean, объекты и массивы. Это преобразование структуры JSON, а не простая текстовая замена. Подстановка действует в корне, вложенных объектах и массивах, сохраняет неизвестные поля и порядок массива. Числа сохраняются без потери точности; строка `"443"` не преобразуется в number автоматически.

В форме рядом с понятной подписью отображается та же ссылка, например «Клиент · `${clientId}`». Поля строятся по определениям переменных. Для объектов и массивов нужен редактор JSON.

### Заполненность и дефолты

Отсутствующее значение и строка, пустая после `trim` по Unicode White_Space, считаются незаполненными. Проверка применяется к значению переменной целиком до проверки типа; у непустой строки пробелы сохраняются. Вложенные пустые строки внутри object/array не удаляются. Постоянные строки сырого шаблона также не обрезаются.

Незаполненное персональное значение выбирает заполненный дефолт. Пустой строковый дефолт равен отсутствию дефолта; если оба значения отсутствуют, возникает `missing_value`. Все объявленные переменные без заполненного дефолта обязательны, даже если ссылка на них пока не используется. Наличие дефолта не делает персональное значение обязательным. Заполненные дефолты проверяются и при наличии персональных значений; неверный тип нельзя скрыть возвратом к дефолту.

| Вход | Результат |
| --- | --- |
| Нет / `" \t "`, без дефолта | `missing_value` |
| `" "`, дефолт `443` для number | Число `443` |
| `"8443"` для number | `type_mismatch` |
| `false`, `0`, `{}`, `[]` | Заполненные значения соответствующих типов |
| `"  edge.example.com  "` | Заполненная строка, пробелы сохраняются |
| JSON `null` | `null_not_allowed`, без возврата к дефолту |

JSON `null` запрещён во всех входах сборки одного элемента: в сыром шаблоне, значениях и дефолтах, включая вложенные поля/элементы массивов. Отсутствие передаётся отсутствием записи, а не `null`; строка `"null"` допустима. Эта область не определяет поведение будущих несвязанных API или режима полной замены.

### Буквальные ссылки и ошибки

Частичная интерполяция отклоняется: `"https://${server.address}/path"` и `" ${server.address} "` дают `unsupported_interpolation`. Для составной строки нужно передать одно готовое string-значение. Незакрытая ссылка или недопустимое имя дают `invalid_reference`.

В исходных строковых значениях шаблона `$$` превращается в буквальный `$` за один проход: `"$${host}"` даёт `"${host}"`, а `"$$$$"` — `"$$"`. Обратная косая черта относится к JSON-экранированию и не экранирует ссылку. Ключи объектов остаются буквальными. Подставленные значения не становятся шаблонами: `${...}` и `$$` внутри данных переменной сохраняются без повторной обработки. Это не язык выражений и не механизм исполнения кода.

Сборка возвращает либо полный результат, либо ошибки без частичного конфига, сохраняя входные данные. Невалидный JSON, повторяющиеся ключи и лишний текст после одного JSON-значения отклоняются. Диагностика содержит код, ID элемента, источник, известное имя переменной и JSON-путь либо позицию синтаксической ошибки; значения и сырой JSON в неё не включаются. Проверки полноты до подключения и публикации предстоит связать с будущими прикладными сценариями.

Эволюция определений переменных у уже настроенных устройств и последствия для публикации остаются отдельными задачами; A05 определяет сборку одного элемента.

## Наследование и переопределение

Без индивидуального переопределения элемент наследуется из шаблона. Экран переопределения имеет два режима:

| Режим | Поведение |
| --- | --- |
| Только переменные | Роутер задаёт значения; структура JSON и остальные поля продолжают приходить из шаблона |
| Свой JSON | Содержимое блока полностью заменяется собственным готовым JSON; поля и переменные шаблона не подмешиваются |

В обоих режимах **ID блока совпадает с ID соответствующего блока шаблона**. Отмена переопределения возвращает наследование.

Локальный элемент добавлен только для конкретного роутера. Это отдельное понятие от полной замены общего элемента: в интерфейсе локальное содержимое имеет фиолетовую плашку, наследуемое — синюю, полная замена — янтарную.

## Роутинг и порядок

Правила имеют стабильные ID. На роутере можно добавлять локальные правила, отключать общие, заменять их содержимое и перетаскивать как общие, так и локальные правила.

Порядок хранится отдельно от содержимого. Перестановка не должна автоматически превращать наследуемый JSON в собственную копию. В интерфейсе есть действие возврата к порядку шаблона.

Расположение новых общих правил в уже изменённом локальном порядке, удаление общих элементов и разрешение конфликтов порядка остаются открытыми решениями. Нельзя молча переносить правило в произвольное место при потере привязки. Недостижимые правила после безусловного завершающего правила должны быть видны при проверке.

## Входы, выходы и зависимости

- Входы имеют вкл/выкл, идентификатор для роутинга, переопределение и удаление.
- Выходы имеют идентификатор для роутинга, переопределение и удаление.
- Вход, используемый итоговым роутингом, нельзя выключить или удалить. Интерфейс блокирует действие и показывает зависимые правила; сервер повторяет проверку при сохранении.
- Проверка использует итоговую конфигурацию с учётом шаблона, локальных изменений и собственного JSON. Она не может опираться только на значения известной интерфейсу формы.
- Для отключения или удаления используемого входа сначала изменяются ссылки на него.

Для удаления общего элемента только на одном роутере понадобится сохраняемое исключение, чтобы он не появлялся снова при следующей сборке. Формат такого исключения ещё не выбран.

Поведение интерфейса при удалении используемого выхода требует отдельного решения. Итоговая конфигурация со ссылками на отсутствующие элементы не должна считаться готовой к применению.
