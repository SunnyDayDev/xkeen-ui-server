# Первичная установка сервера Entware

G15 устанавливает центральный сервер Linux ARM64 из точного проверенного выпуска. Требуются прямой TLS, явный HTTPS origin веб-интерфейса и отдельные UID/GID. Выделите серверу другие UID и GID, чем агенту на том же устройстве. Серверный TLS-ключ размещается с доступом root и выделенной серверной группы.

Сначала получите и проверьте скрипт установки и SHA-256 манифеста. Подготовьте PEM-цепочку и приватный TLS-ключ владельца root с режимом 0600. Имя в browser origin должно быть в сертификате. [Получение проверенной версии](entware-installation-contract.md#получение-конкретной-версии-с-github).

```sh
/opt/bin/sh ./install-entware.sh install \
  --role server --version "$RELEASE_TAG" --manifest-sha256 "$MANIFEST_SHA256" \
  --run-as 65531:65531 --listen 0.0.0.0:8443 \
  --web-origin https://controller.example:8443 \
  --tls-cert /opt/etc/xkeen-ui-install/controller-cert.pem \
  --tls-key /opt/etc/xkeen-ui-install/controller-key.pem
```

Служба появляется после подтверждения собственного HTTPS-слушателя и доступности `/healthz`. Настройте администратора в локальном терминале. Команда запускает F02 от серверного UID с установленным путём SQLite.

```sh
/opt/etc/init.d/S91xkeen-ui-server admin setup
/opt/etc/init.d/S91xkeen-ui-server status
```

Автоматизированный локальный setup принимает `--password-file /absolute/path`. Файл должен быть обычным, с одной ссылкой, режимом 0600 и принадлежать UID сервера. Сам пароль вводится в терминале или читается из файла. Откройте веб-консоль по заданному origin и войдите.

`/opt/etc/init.d/S91xkeen-ui-server stop` штатно останавливает подтверждённый экземпляр. После `start` сервер использует прежние данные `/opt/var/lib/xkeen-ui/server/server.sqlite`. Точный повтор неудавшейся первичной установки использует тот же тег, манифест, адрес, права и TLS. Серверная смена версии и удаление отслеживаются отдельно. [Серверное обслуживание](https://github.com/SunnyDayDev/xkeen-ui-server/issues/120).

Для публикации нужен отдельный явно выбранный доверенный валидатор Xray. Проверка TLS/SQLite подтверждает центральный сервис, а проверка действительного каталога и подключение валидатора идут через контракт публикации. [Спецификация публикации](../openspec/specs/configuration-revision-publication/spec.md).

## Внешний исполнитель и адрес агента

Если владелец выбрал внешний валидатор F09, добавьте к первой команде установки полный набор аргументов. Доверенная CA выделена для исполнителя. Клиентский приватный ключ передаётся по пути к исходному файлу root с режимом 0600. После установки ключ защищён режимом 0640 и доступен только root и группе сервера.

```sh
/opt/bin/sh "$INSTALLER" install \
  --role server --version "$RELEASE_TAG" --manifest-sha256 "$MANIFEST_SHA256" \
  --run-as 65531:65531 --listen 0.0.0.0:8443 \
  --web-origin https://controller.example:8443 \
  --tls-cert /opt/etc/xkeen-ui-install/controller-cert.pem \
  --tls-key /opt/etc/xkeen-ui-install/controller-key.pem \
  --validator-origin https://validator.example:9443 \
--validator-ca /opt/etc/xkeen-ui-install/validator-ca.pem \
--validator-client-cert /opt/etc/xkeen-ui-install/validator-client-cert.pem \
--validator-client-key /opt/etc/xkeen-ui-install/validator-client-key.pem \
--agent-origin https://agent.example:8443
```

Последний аргумент задаёт точный адрес для F10. Браузер продолжает использовать `--web-origin`. Сертификат фактического HTTPS-слушателя должен покрывать используемые имена. Для конфигурации Docker передайте те же флаги непосредственно контейнерному серверу и смонтируйте отдельные защищённые CA и клиентскую пару только для чтения. Docker socket принадлежит worker. [Развёртывание worker](catalog-validator.md).

Если валидатор отсутствует или недоступен, приложение продолжает обслуживать HTTPS и черновики. Подтверждение публикации блокируется. Подмена установленной пары или CA блокирует следующий старт до восстановления согласованных файлов.

## Обновление и снятие службы

Укажите закреплённый выпуск, который содержит операцию обслуживания.

```sh
/opt/bin/sh ./install-entware.sh update --role server \
  --version "$version" --manifest-sha256 "$manifest_sha256"

/opt/bin/sh ./install-entware.sh uninstall --role server \
  --version "$version" --manifest-sha256 "$manifest_sha256" --confirm remove-service
```

Обновление использует установленный профиль, UID/GID и прежние пути TLS и SQLite. Сначала команда проверяет пробную миграцию отдельно от рабочего сервиса. После остановки подтверждённого процесса она сохраняет более свежий резерв в приватном каталоге `backup-*` рядом с базой и проверяет его до запуска нового поколения. Для пробных копий и резерва потребуется свободное место. Намеренно остановленная служба остаётся остановленной. Действующая служба подтверждает готовность на собственном TLS-listener.

Если проверка до запуска кандидата завершилась ошибкой, прежний сервер сохраняется. После допуска новой версии прежняя сборка возвращается только при совпадении явно заявленного формата обеих сборок и проверке фактической базы. При неизвестной совместимости сохраняется барьер запуска. SQLite и новый резерв остаются для [изолированной проверки](storage-backup.md). Команда никогда не подменяет актуальную базу старой резервной копией.

Снятие службы удаляет принадлежащие установке init.d и исполняемые поколения. Профиль, TLS, настройки валидатора, SQLite и резервы остаются. Если снятие было прервано, повторите ту же команду с подтверждением. Повторный install с тем же закреплённым профилем и версией открывает прежнюю базу.
