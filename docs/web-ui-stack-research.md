# F01. Исследование стека веб-интерфейса

Для первого UI рекомендуется **Svelte + TypeScript + Vite** с выдачей встроенных статических файлов из Go. Компонентный подход подходит для редактора с несохранённым черновиком и проверки затронутых роутеров. В синтетической пробе Svelte и htmx дали близкую оценку объёма с gzip. React дал заметно больший размер в том же сценарии. Стек остаётся предложением для согласования. Приоритет разработки — контрольная точка E08. [Issue #45](https://github.com/SunnyDayDev/xkeen-ui-server/issues/45).

## Варианты

| Вариант | Подходит для | Цена выбора |
| --- | --- | --- |
| Svelte + TypeScript + Vite | Повторное использование компонентов макета, локальный черновик, дерево состояний для порядка и предварительной проверки. | CI и разработчику нужен Node. Проверка типов и правил доступности требует отдельных шагов. Понадобится подобрать редактор и компоненты под требуемые взаимодействия. [Svelte](https://svelte.dev/docs/svelte/overview), [TypeScript в Svelte](https://svelte.dev/docs/svelte/typescript), [Vite](https://vite.dev/guide/build). |
| React + TypeScript + Vite | Те же клиентские состояния и компонентная композиция. Подходит, если команда уже сопровождает React или зависит от конкретных компонентов этой экосистемы. | Более крупный минимальный скрипт в пробе. Формы, маршруты и клавиатурные правила требуют собственных решений. [React](https://react.dev/learn), [Vite](https://vite.dev/guide/build). |
| Go `html/template` + htmx + небольшой клиентский JavaScript | Серверные списки, формы и обновление фрагментов без обязательного сборщика npm. | Для редактирования и действий до явного сохранения всё равно нужно поддерживать клиентское состояние. Замена HTML-фрагментов требует проверок буфера, фокуса и доступности. [Go html/template](https://pkg.go.dev/html/template), [htmx](https://htmx.org/docs/). |

Если рабочий объём ограничится серверными формами и списками, сложность дополнительной сборки может перевесить пользу Svelte. Текущий макет предполагает много связанных состояний в одном сеансе редактирования.

## Связь с макетом

Через MCP Pencil просмотрены группы Design System и экраны 02, 04, 06, 08 и 11. В макете повторяются `Atoms / TextArea`, `Molecules / FormField`, `Molecules / RoutingRule`, `Molecules / OverrideMode` и `Organisms / Sidebar`. Токены можно перенести в семантические CSS custom properties, а компоненты использовать повторно на экранах.

- Экраны 02 и 11 требуют сохранять текст сырого JSON отдельно от разобранного значения. Числа могут выходить за диапазон точных целых JavaScript. Операции с буфером сохраняют исходную строку, а проверка сервером остаётся авторитетной.
- Экраны 04 и 06 разделяют формы, выбранную запись, зависимости и порядок. Перетаскивание дополняется доступным с клавиатуры действием, которое сохраняет порядок по UUID.
- Экран 08 отделяет проверку, изменение черновика и явное сохранение. Ошибки и статус должны быть доступны как текст и через уведомления для вспомогательных технологий. [Дизайн-система и порядок проверки](design.md).

Проба проверяет простую перестановку и буфер текста. Проверка макета и состояний будущих форм проводится в их OpenSpec-изменениях.

## Поставка

Предлагается собирать браузерные файлы в CI через закреплённые версии и lockfile. Затем Go включает готовые файлы через `go:embed` и отдаёт их вместе с внутренними обработчиками UI. Сборка для Docker может разделять этапы Node, Go и runtime. Для Entware тот же ARM64-бинарник копируется как файл; отдельный Node-процесс на устройстве не нужен. Встраивание связывает версии обработчиков и файлов. Обновление UI требует нового бинарника. [Go embed](https://pkg.go.dev/embed), [многоэтапная сборка Docker](https://docs.docker.com/build/building/multi-stage/).

При проектировании оболочки нужно зафиксировать путь публикации, кэширование хешированных файлов и политику HTML. Браузерные адаптеры обращаются к выделенному каналу UI на том же origin. Сессии, CSRF и правила доступа относятся к F02/F03.

## Замеры

24 ноября 2026 года последний полный прогон использовал Go 1.27.1 на Darwin ARM64, Node 26.5.0, npm 11.17.0, Chrome 158.0.8127.38, Svelte 5.59.1, React 19.3.1, Vite 8.3.8 и htmx 2.0.11. Сумма gzip рассчитывалась Node для каждого файла отдельно. Измерялся один сценарий с небольшим CSS, двумя элементами списка, полем черновика и обновлением статуса. [Исходники и lockfile пробы](../openspec/changes/archive/2026-11-24-research-web-ui-stack/probe/).

| Вариант | Файлов | Исходный объём, байт | Сумма gzip, байт | ARM64 ELF, байт | Прирост к контрольному ELF, байт |
| --- | ---: | ---: | ---: | ---: | ---: |
| Go + htmx | 4 | 53 252 | 17 614 | 12 594 181 | 65 584 |
| Svelte + Vite | 3 | 43 871 | 17 182 | 12 594 181 | 65 584 |
| React + Vite | 3 | 221 177 | 68 805 | 12 790 789 | 262 192 |

Контрольный ELF с минимальным HTML занимает 12 528 597 байт. Для всех вариантов собран один и тот же пробный Go-хост со встроенной выдачей HTML и двумя обработчиками статуса. Размер ELF зависит в том числе от выравнивания секций Go. Размеры файлов зависят от окружения сборки; ранний прогон в другом рабочем каталоге дал несколько иные числа для Vite-вариантов.

В Chrome все три варианта прошли ввод точного десятичного текста, перестановку с клавиатуры, обновление статуса и проверку сохранности буфера. В Alpine и Entware ARM64 все статические ELF отдали HTML, JavaScript и ответ статуса, отклонили неизвестный ресурс и запустились без Node. [Как повторить](../openspec/changes/archive/2026-11-24-research-web-ui-stack/verification.md).

Перед выбором продуктовых компонентов нужны отдельные замеры редактора JSON и просмотра различий на реалистичных конфигурациях, а также проверка поддержки браузеров, клавиатуры, экранного диктора и сенсорного ввода. Проба охватывает ядро Docker, обычный хост и макет. Совместимость с физическими устройствами остаётся открытой.
