# A01: язык сервера и хранилище

Результат исследования [issue #2](https://github.com/SunnyDayDev/xkeen-ui-server/issues/2), 2026-09-07.

**Согласованное направление:** Go и SQLite через `modernc.org/sqlite`, без cgo. Центральный сервер должен запускаться в Docker и на роутере с Entware `aarch64`; соответствующая цель Go — `linux/arm64`. На момент исследования сервера ещё не было и версии предстояло закрепить. Последующая реализация [каркаса A03](server-skeleton.md) использует Go 1.27.1; SQLite и совместимость физического роутера ещё не проверены.

## Требования к выбору

Сервер хранит источник истины: шаблоны, персональные настройки устройств и желаемые ревизии. Требуются сохранение произвольного JSON, транзакционные изменения и работа на постоянном накопителе. Установка на роутер предполагает файлы и службу Entware `init.d`, без собственного пакетного репозитория. Архитектурные требования — [DDD, Clean Architecture, SOLID и TDD/BDD](architecture.md#принципы-разработки).

UI, язык агента и транспорт синхронизации в A01 не выбираются. Архитектура сервера не определяет архитектуры управляемых устройств; среда агента относится к A02.

## Сравнение языков и способа поставки

| Вариант | Docker | Entware aarch64 | Вывод для проекта |
| --- | --- | --- | --- |
| Go + SQLite через `modernc.org/sqlite` | Сборка исполняемого файла под целевую архитектуру; данные отдельно от образа | Сборка без cgo, без установки интерпретатора и системной SQLite для работы сервера | Выбранное направление: простая поставка и явные интерфейсы между ядром и адаптерами |
| Python + модуль `sqlite3` | Интерпретатор и зависимости входят в образ | Нужны пакеты Python и SQLite из подходящего feed; состав окружения зависит от пакетов | Рабочая альтернатива с удобной разработкой, но большим числом зависимостей на устройстве |
| Rust + SQLite через `rusqlite` | Компилируемый сервер; возможна сборка SQLite вместе с приложением | Нужно согласовать target, C toolchain для bundled SQLite и совместимость с ядром/libc | Возможный вариант, но подготовка сборки под Entware сложнее выбранного пути без cgo |

Это оценка удобства разработки и поставки, а не результат сравнения производительности. DDD, Clean Architecture и тестирование по контрактам применимы ко всем трём вариантам.

Проверенные основания сравнения:

- [`modernc.org/sqlite` v1.58.0](https://pkg.go.dev/modernc.org/sqlite@v1.58.0) предоставляет драйвер без cgo и включает `linux/arm64` в матрицу платформ. MIPS в ней отсутствует; поддержку сервера на MIPS из этого решения не выводим. Версия здесь обозначает изученную документацию, а не закреплённую зависимость проекта.
- [`sqlite3` в Python](https://docs.python.org/3/library/sqlite3.html) — опциональный модуль, использующий библиотеку SQLite. В [индексе Entware aarch64](https://bin.entware.net/aarch64-k3.10/Packages.html) найдены `python3-sqlite3` и `libsqlite3`; установка и запуск не выполнялись.
- [`rusqlite`](https://github.com/rusqlite/rusqlite) в режиме `bundled` собирает SQLite из исходников через C toolchain. Для `aarch64-unknown-linux-gnu` [Rust указывает](https://doc.rust-lang.org/rustc/platform-support.html) Linux 4.1+ и glibc 2.17+. Имя feed Entware не подтверждает версию ядра конкретного устройства.

## Выбор хранилища

| Вариант | Применимость | Решение |
| --- | --- | --- |
| SQLite | Встроенная БД, транзакции, локальное хранение без отдельной службы | Выбрана для начального сервера |
| Набор JSON-файлов | Удобен для примеров и экспорта; согласованное обновление связанных данных, блокировки и восстановление потребуют собственного протокола | Не использовать как основное хранилище сервера |
| PostgreSQL | Кандидат при необходимости нескольких экземпляров сервера и интенсивной конкурентной записи | Не добавлять отдельную службу БД в начальную поставку |

Вывод о SQLite основан на предполагаемом одном экземпляре центрального сервиса с локальной БД. Несколько подключённых агентов сами по себе не означают несколько прямых клиентов БД: доступ идёт через сервер. SQLite допускает одного писателя одновременно; ограничения нужно учитывать при проектировании транзакций и частоты сохранения контактов. При изменении требований к масштабу или отказоустойчивости выбор пересматривается. См. [область применения SQLite](https://sqlite.org/whentouse.html).

Хранилище будет внешним адаптером. Доменное ядро и прикладные сценарии не должны зависеть от SQLite-драйвера. Формат записей, миграции и границы транзакций проектируются отдельно; выбор SQL не ограничивает допустимый сырой JSON набором полей Xray.

## Ограничения и открытые риски

- **Ядро и окружение.** Для Go 1.24 и новее общий минимум Linux — 3.2; нужно проверить требования выбранной версии и фактическое ядро устройства. Сборка без cgo снимает зависимость от C ABI драйвера, но не от системных вызовов ядра. См. [требования Go](https://go.dev/wiki/MinimumRequirements).
- **Память и место.** Размер бинарника, потребление памяти и время операций не измерены. Перед заявлением поддержки нужно определить доступный бюджет ресурсов и проверить сервер вместе с обычной нагрузкой устройства.
- **Постоянное хранение.** Для БД нужен локальный накопитель с корректными блокировками и синхронизацией записи. Атомарность SQLite зависит от гарантий файловой системы и носителя; рестарт процесса не равнозначен испытанию потери питания. См. [атомарную фиксацию SQLite](https://sqlite.org/atomiccommit.html).
- **Режим журнала и резервирование.** WAL/rollback journal, таймауты блокировок, checkpoint и резервное копирование ещё не выбраны. WAL имеет дополнительные файлы и ограничения для сетевых файловых систем. При выборе версии следует проверить исправления SQLite, включая WAL-reset bug. См. [WAL](https://sqlite.org/wal.html) и [Backup API](https://sqlite.org/backup.html).
- **Зависимости и поставка.** Нужно закрепить версии Go, драйвера и транзитивных зависимостей, проверить состав бинарника и доступ к сертификатам/DNS в целевой среде. Отсутствие cgo не означает отсутствие всех внешних файлов окружения.

## Проверка и следующий шаг

В A01 выполнена проверка по первичной документации: сопоставлены `aarch64`/`arm64`, матрица SQLite-драйвера, требования Go/Rust и наличие Python-пакетов Entware. Прочитаны [результаты существующего ARM64-стенда](../lab/results/arm64.md): они подтверждают эксперимент Entware/XKeen/Xray, но не запуск будущего сервера. Тестовый сервер, сборка с выбранным драйвером, замеры и проверки физического устройства в этом исследовании не выполнялись.

План практической проверки после подготовки соответствующих спецификаций и перехода к реализации:

1. Закрепить версии и собрать исполняемый файл для `GOOS=linux`, `GOARCH=arm64`, `CGO_ENABLED=0`. Проверить архитектуру и отсутствие требуемого динамического загрузчика/библиотек у полученного ELF; записать размер файла.
2. Запустить сервер в отдельном экземпляре Entware-стенда. Проверить старт, доступность и штатную остановку; зафиксировать версии окружения. Это относится к каркасу A03 и не требует подключения БД.
3. При подключении хранилища в C01 проверить создание БД, commit/rollback, чтение после перезапуска и видимую ошибку записи. Измерить память и задержки на описанном воспроизводимом наборе безопасных данных.
4. Отдельно проверить блокировки, восстановление после прерывания и резервную копию по будущему контракту хранения. Сравнить измерения с согласованным бюджетом ресурсов.
5. Перед заявлением поддержки физического роутера повторить применимые проверки на целевом aarch64-устройстве по отдельному разрешению. Docker использует своё ядро Linux и не подтверждает совместимость с ядром и накопителем роутера.

Следующий этап для сервера — предложение OpenSpec для A03 ([issue #4](https://github.com/SunnyDayDev/xkeen-ui-server/issues/4)): минимальный каркас, запуск, проверка доступности и штатная остановка. Подключение SQLite остаётся C01. Сначала формируются сценарии и интерфейсы, затем реализация проходит Red → Green → Refactor. Само исследование A01 не создаёт контракт работающего API и не изменяет существующую спецификацию стенда.
