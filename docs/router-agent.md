# Агент роутера D04

`xkeen-agent` запускается в foreground, устанавливает исходящее HTTPS-подключение к серверу D03 и подтверждает рабочий ключ своего роутера. Первый запуск использует одноразовое приглашение от доверенного оператора. Повторный запуск проверяет сохранённый ключ и технический ID. Получение ревизий, контакты, отчёты, подписка и применение конфигурации остаются следующими этапами. [Issue #67](https://github.com/SunnyDayDev/xkeen-ui-server/issues/67).

## Сборка и запуск

При установленном Go 1.27.1 соберите Linux ARM64-бинарник.

```sh
mkdir -p .build
CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build -trimpath \
  -o .build/xkeen-agent-linux-arm64 ./cmd/xkeen-agent
```

Агенту нужен HTTPS origin серверного входа D03 и закрытый каталог состояния. Для первого запуска доверенный оператор помещает приглашение в файл `invitation` внутри каталога. Каталог должен принадлежать пользователю агента и иметь права 0700, файл приглашения — 0600. Рабочий ключ создаётся на агенте. Выдача приглашения через административный интерфейс и автоматизация установки относятся к отдельным задачам.

Пример запуска на Linux ARM64 с условными путями и демонстрационным адресом:

```sh
./xkeen-agent-linux-arm64 --server https://controller.example:8443 \
  --state-dir ./agent-state --ca-file ./controller-ca.pem
```

`--ca-file` задаёт доверенные PEM-сертификаты для приватного центра сертификации. Без этого аргумента используется системное доверие. Имя сервера должно совпадать с сертификатом. После аутентификации выводится `agent authenticated`. Процесс удерживает локальную блокировку до SIGTERM или Ctrl+C. Ошибки выводятся фиксированными сообщениями.

## Сохранение и восстановление

Перед первой привязкой агент синхронизирует файл рабочего кандидата, каталог состояния и его родительский каталог. Запись защищена правами 0600 и меняется атомарно. Успешная проверка рабочего ключа сохраняет технический ID. Параллельный процесс с тем же каталогом получает безопасный отказ.

При запуске с ожидающей записью агент подтверждает устойчивость записи и проверяет рабочий кандидат. Успешная проверка восстанавливает прежнее подключение даже после потери ответа и приглашения. Если D03 подтвердил, что кандидат пока не действует, повтор привязки использует то же пригодное приглашение и тот же кандидат. При отказе активного ключа или смене origin требуется восстановление оператором. Агент сохраняет прежнюю запись.

Ошибки сети и подтверждённая временная недоступность допускают до трёх попыток с таймаутом HTTP 5 секунд на запрос и отменяемыми задержками. Неопознанный ответ, перенаправление и ошибка доверия завершают подключение. Ответ ограничен 64 КиБ. Приглашение и рабочий ключ читаются из закрытых файлов и не включаются в аргументы, URL и диагностический вывод. [Сервер D03](server-skeleton.md#https-подключение-агента-d03), [спецификация D04](../openspec/specs/agent-enrollment-client/spec.md).

## Проверка

Нативные тесты и два статических Linux ELF (ARM64 и AMD64) проверены. Целевой тест запустил настоящий сервер D03 с TLS и SQLite и агент в Entware `aarch64-k3.10` без внешней сети. Он подтвердил исходную привязку, повторный запуск с ожидающим и затем активным состоянием, прежний ID и поколение, отказ отозванному ключу и штатную остановку. Целевые файловые тесты прошли от непривилегированного пользователя в том же контейнере. [Команды и границы лабораторной проверки](../openspec/changes/archive/2026-11-24-connect-router-agent/verification.md).
