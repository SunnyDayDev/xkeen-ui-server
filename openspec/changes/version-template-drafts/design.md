## Context

C02 хранит полный черновик по стабильному ID в `templates(id, draft)` и применяет правила A08 перед сохранением. C01 предоставляет SQLite с атомарными миграциями, одним соединением на экземпляр и транзакциями с ранним захватом блокировки записи. C04 сохраняет выбранный ID в отдельном снимке роутера. C05 определит публикацию и сохранение согласованных результатов нескольких роутеров.

## Goals / Non-Goals

- Обеспечить один успешный результат, когда две правки одного ID основаны на одной версии, и сохранить полный снимок победителя.
- Расширить прикладной контракт шаблона и оставить проверку зависимостей, согласование ссылок роутера и публикацию последующим сценариям.

## Decisions

1. **Версия относится к снимку одного шаблона.** Прикладной результат содержит полный черновик и число `int64`. Создание даёт 1, чтение получает содержимое и версию одной операцией. Замена принимает полный кандидат C02 с его стабильным ID и отдельный аргумент ожидаемой версии. Положительный счётчик удобен для сравнения и сохраняется напрямую в SQLite. Успешная запись повышает его даже для совпадающего содержимого. Это отличает каждую фиксацию, а сравнение итоговых файлов для публикации относится к C05.
2. **Одна подготовка черновика для Create и Replace.** Внутренний сервис проверяет ID и ожидаемую версию, переиспользует проверки полного набора UUID и правила подготовки элементов C02. Идентичность элемента определяется UUID. Новый UUID в прежней позиции задаёт удаление старого элемента и добавление нового. Согласование зависимых ссылок входит в C05. При известной структурной ошибке возвращается результат соответствующей проверки. Для корректного кандидата узкий порт репозитория выполняет сравнение и замену атомарно. Он различает отсутствие, конфликт версии, исчерпание и ошибку хранилища и не возвращает частичный снимок. Тип и ошибки внутреннего контракта не зависят от SQLite.
3. **Условное обновление в SQLite.** Использовать параметризованный `UPDATE templates SET draft = ?, version = version + 1 WHERE id = ? AND version = ? AND version < ? RETURNING version` в транзакции C01. Отсутствие результата проверяется чтением текущей версии в той же транзакции. Это различает отсутствующий ID, несовпадение и достижение максимума без гонки. По успешному пути вернуть подготовленный независимый снимок после commit. Сериализация выполняется до получения блокировки. Вариант чтения версии затем безусловной записи требует строгого соблюдения общей транзакции каждым вызывающим участком. Условие SQL закрепляет гарантию в самой операции записи. [SQLite RETURNING](https://sqlite.org/lang_returning.html), [транзакции SQLite](https://sqlite.org/lang_transaction.html).
4. **Эволюция схемы.** Следующая миграция добавляет в `templates` колонку `version INTEGER NOT NULL DEFAULT 1` с ограничением `CHECK (typeof(version) = 'integer' AND version >= 1)`. Номер выбирается по принятой последовательности на актуальном main. При согласованных номерах C02 v2 и C04 v3 следующий номер v4. Старые миграции сохраняют исходный SQL. Персональные снимки C04 сохраняют прежние ID и данные. [SQLite ALTER TABLE](https://sqlite.org/lang_altertable.html).

## Risks / Trade-offs

- Полная замена требует полного кандидата. Слияние правок и разрешение конфликта остаются у вызывающего сценария.
- Одновременное изменение нескольких агрегатов относится к C05. Условная замена защищает только один шаблон.
- Ошибка SQLite при записи отличается от конфликта устаревшей версии. Тест конкурентной записи использует два отдельных соединения к одной базе, чтобы проверить механизм хранения помимо синхронизации вызовов в процессе.

## Migration Plan

Открыть файл со старой схемой через механизм C01. Для каждого сохранённого черновика новая колонка даёт 1, содержимое и ID сохраняются. Проверить создание новой базы и обновление файла с принятыми миграциями. Предыдущий бинарник, поддерживающий миграции, отклоняет файл с более новым номером по контракту C01.
