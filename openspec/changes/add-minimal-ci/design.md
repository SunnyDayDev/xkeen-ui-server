## Context

Мотивация и связь с A04 — в [proposal.md](proposal.md). В репозитории ещё нет `.github/workflows/`. `go.mod` содержит `go 1.27.0` и `toolchain go1.27.1`; сторонних Go-модулей и `go.sum` нет.

Команды проверок описаны в [инструкции каркаса](../../../docs/server-skeleton.md). Тесты `internal/server` проверяют HTTP и жизненный цикл через внутренние интерфейсы; `cmd/xkeen-ui-server` собирает временный процесс и проверяет его запуск, сигналы и ошибки. Launcher-тест вызывает существующий `scripts/run-server.sh`, который пишет в `.build/` и собирает без cgo. Процессные тесты требуют Unix и loopback; IPv6 уже имеет явный skip при отсутствии поддержки.

Design нужен для выбора внешних actions, полномочий, воспроизводимой версии Go и способа проверки отказа CI. Описанные ниже решения предлагаются для реализации этого change.

По уточнению пользователя продуктовые specs описывают наблюдаемое поведение самого сервиса: входы, результаты, ошибки и продуктовые инварианты. TDD/BDD — процесс разработки; DDD, Clean Architecture и SOLID — архитектурные принципы. Их место в правилах и архитектурной документации, а применение к конкретной задаче — в design и tasks. Поэтому у A04 `skip_specs: true`, требования CI остаются в этом design и tasks, а документация готового процесса будет в `docs/ci.md`. При реализации правило разделения нужно закрепить в `AGENTS.md` и rules `openspec/config.yaml`. Пересмотр ранее существовавших specs вне объёма A04.

## Goals / Non-Goals

**Goals:** дать один понятный CI-результат для изменения, повторять существующие проверки, контролировать сборку целевого Linux ARM64 без cgo и сделать прохождение CI условием слияния в основную ветку.

**Non-Goals:** менять поведение сервера или тестовые интерфейсы, создавать универсальный CI-фреймворк, вводить матрицу ОС или переносить Docker-стенд. Состав задачи ограничен [proposal.md](proposal.md).

## Decisions

### 1. Один workflow и последовательный job

Предлагается `.github/workflows/ci.yml`, workflow `CI`, job `checks` на GitHub-hosted `ubuntu-24.04` (AMD64), `timeout-minutes: 15`. Триггеры: push любых веток и стандартные события `pull_request` (opened, synchronize, reopened), без фильтра путей. Push тегов не требуется. Изменения документации также получают CI-результат.

Для PR используется стандартный checkout проверяемого merge ref. `pull_request_target` не используется. Для PR из fork применяются штатные ограничения и возможное ожидание одобрения GitHub; обход этих ограничений не проектируется. Поведение событий описано в [GitHub Docs](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows).

Один job сохраняет последовательность тестов, использующих `.build/`, и простую диагностику. Матрица ОС и раздельные jobs пока не дают необходимого для A04 результата. При push ветки с открытым PR допустимы два запуска; дедупликация и concurrency не нужны для первой версии.

### 2. Toolchain из одного источника

Использовать официальный `actions/setup-go` с `go-version-file: go.mod`; при наличии `toolchain` action выбирает эту версию. Не задавать `GOTOOLCHAIN=local` до setup-go: его parser в этом режиме выбирает директиву `go`. Сам action устанавливает `local` после выбора SDK. Вывести `go version` и проверить совпадение `go env GOVERSION` с директивой `toolchain`; дальнейшие команды не переключают SDK автоматически. Кеш setup-go отключить (`cache: false`) для простого первого запуска без сторонних модулей. Эти входы поддерживает [setup-go](https://github.com/actions/setup-go).

Официальные `actions/checkout` и `actions/setup-go` закрепить полными commit SHA проверенных стабильных выпусков, рядом указать версии в комментариях. При реализации разрешить SHA соответствующих release tags и записать их в отчёт; использование плавающих major tags не требуется. Дублировать номер Go в YAML или выбирать `stable` не нужно.

### 3. Проверки и команды

Каждая строка таблицы — отдельный именованный шаг, выполняемый из корня checkout. Ошибка завершает шаг и job неуспешно; следующие обычные шаги пропускаются.

| Шаг | Проверка |
| --- | --- |
| Go formatting | `gofmt -l cmd internal`; напечатать найденные пути и вернуть ненулевой код при непустом списке; ошибка самого gofmt тоже фатальна. Исходники не переписывать. |
| Launcher syntax | `sh -n scripts/run-server.sh` |
| Tests | `go test ./... -count=1 -v` |
| Vet | `go vet ./...` |
| Race tests | `go test -race ./... -count=1 -v` при `CGO_ENABLED=1` |
| Build Linux AMD64 | `CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -trimpath -o .build/xkeen-ui-server-linux-amd64 ./cmd/xkeen-ui-server` |
| Build Linux ARM64 | `CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build -trimpath -o .build/xkeen-ui-server-linux-arm64 ./cmd/xkeen-ui-server` |

Перед сборками создать `.build/` явно. C toolchain нужен для race-тестов только на runner; глобальное `CGO_ENABLED=0` не задавать. Проверка race инструментирует тестируемые пакеты, но дочерний бинарник, который текущий `TestMain` собирает обычным `go build`, не становится автоматически race-бинарником. Расширять это покрытие в A04 не требуется.

Отдельный ручной запуск сервера в CI дублировал бы существующие процессные тесты. ARM64 проверяется сборкой; выполнение ARM64 и Entware остаются отдельной пробой A03. Постоянные новые интеграционные тесты и инструменты проверки всей документации не добавляются.

### 4. Полномочия и границы архитектуры

На уровне workflow задать `permissions: contents: read`, не повышать права job. Для checkout задать `persist-credentials: false`, что отключает сохранение учётных данных согласно [документации checkout](https://github.com/actions/checkout). Не использовать пользовательские secrets, PAT, реальную инфраструктуру, публикацию и upload бинарников.

Workflow — внешний адаптер процесса разработки: GitHub event вызывает существующие CLI-команды, их exit codes определяют результат проверки. `cmd/xkeen-ui-server` остаётся сборкой приложения, `internal/server` — существующим серверным пакетом; зависимости Go-кода не направляются к CI. Доменные инварианты, слой хранения, HTTP-контракты и UI этим change не затрагиваются, новые интерфейсы и абстракции в Go не вводятся. Изменения и проверка макетов не требуются.

### 5. Проверка контракта CI

До написания workflow использовать следующие приёмочные сценарии процесса. Проверки не должны сводиться к сравнению YAML с его же шаблоном.

| Вход / событие | Ожидаемый результат |
| --- | --- |
| Push корректной ветки с workflow | Запускается CI; все проверки и обе сборки проходят, job успешен. |
| Открытие или обновление PR с корректными изменениями | Запускается CI для проверяемой версии PR; результат виден в checks PR после разрешения запуска политиками GitHub. |
| Go-файл с нарушенным форматированием | Проверка форматирования печатает путь, завершается неуспешно и не исправляет файл сама. |
| Компилируемый существующий тест с намеренно неверным ожиданием | Шаг Tests и job завершаются неуспешно; журнал содержит имя теста и причину несовпадения. |
| Восстановление правильного ожидания | Новый запуск проходит все обязательные шаги, включая обе сборки. |
| Ошибка установки SDK, синтаксиса, vet, race или сборки | Соответствующий шаг и job неуспешны; ошибка не подавляется и успешный результат не заявляется. |
| Успешный run | Использован toolchain из `go.mod`, полномочия ограничены чтением contents, secrets не нужны, публикаций и загруженных бинарных artifacts нет. |

Нормальный успешный run выполняет все строки таблицы проверок из решения 3; допустимый skip IPv6 виден в тестовом выводе и не означает проверенную поддержку IPv6. Результат ARM64-сборки не означает выполнения на ARM64 или Entware.

При реализации локально воспроизвести команды и проверить YAML валидатором Actions (`actionlint`, версия записывается в отчёт). Проверку форматирования отдельно испытать на временной копии Go-файла: неверное форматирование → ненулевой код и путь, восстановление → код 0. Это проверка отказа команд, а не изменение Go-поведения.

На GitHub использовать рабочую ветку/PR реализации: сначала получить успешные запуски для push и PR, затем включить ruleset по решению 6. Временным проверочным коммитом изменить только ожидание существующего `TestHealth`, сохранив компиляцию и форматирование. Дождаться падения именно шага Tests с названием теста и причиной; проверить, что PR заблокирован обязательной проверкой. Следующим коммитом восстановить ожидание и получить зелёный результат для окончательного состояния и снятие блокировки обязательного CI. Проверочная мутация не должна остаться в итоговом коде; перед завершением проверить diff.

Предварительно описанные сценарии BDD управляют проверкой конфигурации CI. Цикл намеренного отказа/восстановления фиксируется как проверка CI, а не как test-first разработка уже существующего сервера. Отсутствие workflow, ошибка сети, установки Go или YAML не считаются подтверждением обнаружения регрессии теста. Если при реализации понадобится новая логика поведения, сначала уточнить контракт и пройти отдельный test-first Red → Green → Refactor.

Отчёт `verification.md` должен содержать команды и исходы, SHA проверенных коммитов, ссылки на GitHub runs для push/PR и отказа/восстановления, фактический Go и runner, разрешённые SHA actions, ограничения. Данные settings репозитория и токены в отчёт не копировать.

### 6. Защита main/master

На момент подготовки этой правки GitHub показывает `main` как единственную и основную ветку, `protected: false`, rulesets отсутствуют. По запросу пользователя защита входит в реализацию A04; `master` создавать не нужно.

Использовать один repository branch ruleset `Protect main and master` с `enforcement: active`, включающими условиями `refs/heads/main` и `refs/heads/master`, без исключений и bypass actors. Ruleset применяется и к будущей ветке `master`. Правила: `pull_request`, `required_status_checks`, `non_fast_forward` и `deletion`. Эти виды правил и условия поддерживает [GitHub Rules API](https://docs.github.com/en/rest/repos/rules#create-a-repository-ruleset).

PR обязателен, но число обязательных approving reviews — 0: запрос на защиту через CI не вводит обязательного второго участника. CODEOWNERS approval, last-push approval, merge queue, подписи коммитов и ограничения способа merge дополнительно не включать. Bypass отсутствует и для администраторов.

Обязательный status check привязать к фактическому имени job и GitHub App integration ID из первого успешного check run; не угадывать имя по надписи workflow в интерфейсе. Для job явно задать стабильное `name: checks`. Включить `strict_required_status_checks_policy`, чтобы проверялось состояние, актуальное относительно базовой ветки. Не включать обход проверки при создании подходящей ветки. Отсутствующая, ожидающая или проваленная обязательная проверка не даёт сливать PR.

Ruleset настроить после успешного запуска workflow в ветке/PR и до проверки отказа/восстановления. Повторно прочитать настройки перед записью: если появился подходящий ruleset, обновить его вместо создания дубля, сохранив чужие несвязанные ограничения. Административные действия выполняются через доступный авторизованный GitHub CLI вне CI; права `GITHUB_TOKEN` workflow остаются `contents: read`.

Проверить через API активность ruleset, оба условия веток, отсутствие bypass и параметры required check. API эффективных правил позволяет проверить также ещё не существующий `master`. Для PR проверить, что красный обязательный check блокирует слияние, а после восстановления зелёный check снимает именно эту блокировку. Не проверять запрет force push или удаления разрушительными попытками над main: для этих правил достаточно чтения эффективной конфигурации. В отчёт включить только относящиеся к защите параметры, ID/URL ruleset и наблюдаемые результаты проверки PR, без полного дампа settings.

## Risks / Trade-offs

- Холодная установка SDK или недоступность внешней загрузки → установка должна завершаться явной ошибкой; не подменять версию Go и не считать сбой проверкой регрессии.
- Сборки AMD64/ARM64 не подтверждают работу физического роутера → явно сохранить границу совместимости в документации.
- Один job прекращает последующие проверки при первой ошибке → именованные шаги дают причину; исправление и повторный запуск достаточны для малого проекта.
- Закреплённые SHA actions требуют обновления вручную → версии и происхождение указываются рядом с SHA; автоматизация обновлений вне A04.
- Политики GitHub могут блокировать запуск или ожидать одобрения PR → зафиксировать препятствие; issue не закрывать по одним локальным проверкам.
- Неверное имя обязательной проверки может заблокировать слияния → использовать имя и integration ID из реального run, перечитать сохранённые правила и проверить PR. При переименовании job обновлять ruleset в той же работе.

## Migration Plan

После отдельного запроса на реализацию добавить workflow и документацию, выполнить локальную проверку и успешные запуски ветки/PR на GitHub, включить защиту по решению 6 и проверить отказ/восстановление. Подготовка плана сама по себе не запускает workflow и не меняет GitHub settings.

Миграций данных нет. Откат workflow согласовать с required checks: перед удалением или переименованием job скорректировать только его требование в ruleset, сохранив PR, запрет force push/удаления и чужие правила. Затем revert workflow и связанной документации; серверные файлы и runtime не затрагиваются. После выполнения критериев архивировать change с сохранением `skip_specs`, без синхронизации процессных требований в продуктовые specs; закрытие issue #5 проверить отдельно.
