# Проект D04

## Context

D01 задаёт исходящий HTTPS. D02 задаёт срок и привязку ключа, а D03 предоставляет ограниченные enroll и identity. A02 проверила запуск статического Go ARM64 ELF в Entware `aarch64-k3.10`. D04 добавляет аутентификацию процесса; доставка и контакт используют другие операции.

## Decisions

1. **Композиция и порт.** `cmd/xkeen-agent` разбирает `--server`, `--state-dir` и необязательный файл CA. Прикладная операция получает узкие порты локального состояния и D03. Инфраструктурные адаптеры отвечают за файлы, Go TLS и HTTP. Рабочий кандидат использует общий кодировщик и генератор D03 из `internal/agentcredential`. Прикладной код не зависит от SQLite или реализации сервера.
2. **Локальная запись.** В закрытом каталоге состояния сохраняется одна запись с версией формата, нормализованным HTTPS origin, рабочим кандидатом и необязательным подтверждённым ID. Пустой ID означает pending. Приглашение оператор передаёт отдельным закрытым файлом внутри каталога. Pending хранит digest этого приглашения, чтобы повтор использовал прежнее приглашение. После подтверждения digest очищается. Проводить сетевой запрос только после записи приватного файла через создание временного файла в том же каталоге, синхронизацию, rename и синхронизацию каталога. Некорректный файл, открытые права или параллельный владелец каталога дают безопасный отказ. Эксклюзивное локальное владение предотвращает независимые первые кандидаты; Linux/Entware использует файловую блокировку. Не удалять переданное оператором приглашение автоматически.
3. **HTTPS и контракт D03.** Origin ограничен схемой, хостом и портом, без секретов, параметров и произвольного пути. Включена штатная проверка сертификата и имени с системным trust store либо явно указанным CA. Перенаправления запрещены. Используются `POST /agent/v1/enroll` с приглашением в bearer-заголовке и рабочим кандидатом в JSON и `GET /agent/v1/identity` с рабочим ключом в заголовке. Принимать только строгий ответ D03 с безопасным размером. В журнал выводятся фиксированные результаты, без произвольного тела, технических деталей TLS и секретов.
4. **Восстановление.** При новой установке прочитать приглашение, создать кандидата, записать pending и отправить привязку. После успешного enroll отдельно проверить рабочий ключ через identity и сопоставить ID ответов. При повторном запуске проверить сохранённый ключ первым запросом. Для pending точный ответ 401 `unauthorized` даёт возможность повторить enroll с тем же кандидатом и прежним приглашением после сверки digest. После истечения приглашения новое состояние подготавливается отдельным авторизованным действием. Временный ответ, обрыв и недоверенный сервер сами не запускают погашение. При подтверждении сохранить активную запись. Для активной записи 401 завершает подключение безопасно, сохранённый ID сверяется при успехе.
5. **Остановка и повторы.** Начальная операция имеет ограниченный бюджет попыток и таймаут HTTP. Повторять временную недоступность и сетевые ошибки с ограниченной задержкой, сохраняя один кандидат; прерывать работу при SIGINT/SIGTERM. После подтверждения агент остаётся в foreground, ожидая отмены. Контакт, проверка курсора, получение каталога и отчёты подключаются в D05/D06. Физический роутер и установочная интеграция остаются отдельными проверками.

## Risks / Trade-offs

- Без синхронизации каталога сбой питания может нарушить сохранность последнего rename. При ошибке локальной записи сетевой эффект запрещён. Конкретный накопитель физического устройства требует отдельной пробы.
- Закрепление origin защищает от передачи рабочего секрета при смене адреса. Перенос полномочий требует отдельной операции восстановления.
- Реальный сервер D03 выдаёт приглашение через внутренний порт. Лабораторный скрипт использует только синтетические настройки и отдельную временную базу.

## Open Questions

Число попыток, таймаут и размер ответа уточняются в реализации на основе ограничения D03. Абсолютный путь установки и управление режимом службы относятся к G12–G14.
