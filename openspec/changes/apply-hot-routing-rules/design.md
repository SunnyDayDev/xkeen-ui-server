## Context

Свежий main 43a0e1a содержит E06. Защищённый E03 supervisor самостоятельно получает авторизацию и байты D05, выполняет валидацию и держит блокировку рабочего каталога. E06 требует два неизменных контроля и третий различимый маршрут. Ответ lsrules содержит только пары тегов.

## Goals / Non-Goals

Поддерживаемая цель — управляемый direct launcher внутри отдельной Linux ARM64 сетевой среды с заранее настроенной защитой. На прочих установках доступен E03. Поведение других процессов и рабочие правила межсетевого экрана роутера не изменяются автоматически.

## Decisions

Оператор включает профиль в защищённом bootstrap и задаёт третью loopback HTTP-цель с ожидаемым маркером. Сеть изолирована собственной доверенной установкой. Все локальные процессы вне TCB имеют отдельный непривилегированный UID, без NET_ADMIN/NET_RAW и доступа к привилегированным сокетам. Supervisor — единственный уполномоченный клиент в доверенном окружении. Рабочий Xray запускается с отдельным UID. На входе в локальный TCP API допускается только supervisor: в стендовом профиле первое правило filter OUTPUT для точного IPv4 loopback адреса и TCP-порта отклоняет пакеты чужих UID. Оператор обеспечивает неизменность политики на всё время работы; один снимок правил не доказывает это условие. Запрещены внешние клиенты, форвардинг к listener, дополнительные API и изменение таблиц за спиной supervisor. При недоказанном окружении используется рестарт.

Привязать свидетельство к фактическому слушателю Xray, каталогу, boot ID, PID/start tick, проверенному исполняемому файлу, отдельному сетевому namespace, закреплённому механизму защиты и непрерывному владению, начиная с защищённого старта. Принятие уже работающего процесса после поздней установки фильтра недостаточно. При утрате истории после рестарта supervisor сначала E03 восстанавливает доверенную базу. Привилегированные команды используют проверенные бинарники, фиксированные аргументы и абсолютные пути, ограниченные таймаут/вывод, очищенное окружение и только заранее подконтрольный endpoint.

Перед эффектами повторно сверить рабочий scope, E06, область записи и актуальный D05; надёжно сохранить тип попытки и предыдущую базу. Команду запускать один раз для точного приватного файла из закреплённых байтов. Пометить риск отправки до запуска команды. После успеха сверить полную упорядоченную проекцию и три новые SOCKS-пробы с прямыми контролями, идентичность процесса и владение listener. Установить только 05_routing.json с прежними метаданными через fsync/rename/fsync родителя, повторить полную проверку и атомарно продвинуть current. Исход попытки для E08 сохраняет тот же ID. Восстановление E04 разбирает прежние журналы E03 и новые горячие фазы; частичная запись, потерянный ответ и неопределённый commit требуют перечитывания устойчивого состояния.

## Risks / Trade-offs

Положительная проба LinuxKit ARM64, Xray 26.3.27, Entware iptables v1.4.21, отдельная сеть Docker --network none: до фильтра непривилегированный клиент UID 65534 прочёл правила Xray UID 65533; после фильтра чтение тем же клиентом отказано, root выполнил полную замену на синтетическом каталоге и повторное чтение вернуло новый тег. Проверка проведена на одноразовом контейнере. Это подтверждает механизм фильтрации; корректность установки, жизненный цикл и rollback требуют отдельных end-to-end тестов. Для окружений с неподконтрольной маршрутизацией или процессами, имеющими привилегии сети, горячая стратегия недоступна.
