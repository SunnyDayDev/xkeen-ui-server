## Context

A02 выбрал направление Go без cgo на Linux ARM64. На Entware aarch64 подтверждены запуск и базовые файловые операции, а сетевые проверки агента ещё предстоят. C06.3 хранит локальный для роутера номер, проверенный профиль и полный именованный набор байтов. C07 сохраняет этот формат и предоставляет список изменённых ревизий после групповой фиксации.

## Варианты транспорта

| Вариант | Что даёт | Ограничение для первой поставки |
| --- | --- | --- |
| HTTPS с обычным опросом | Один короткий запрос за текущим состоянием. Простой контроль таймаута и повторов. | При опросе раз в минуту новая конфигурация ждёт следующего цикла. Такой опрос остаётся основой восстановления. |
| HTTPS с ограниченным long polling | Один ожидающий запрос на агент передаёт подсказку сразу после изменения. Обычный HTTP проходит через стандартный TLS и reverse proxy. | Занимает соединение и требует таймаутов посредников, отмены ожидания и защиты от частых повторов. |
| SSE | Стандартный текстовый поток от сервера с восстановлением и идентификаторами событий. | Для одного сигнала потребуются длительный поток, корректная буферизация посредниками и отдельный контроль переподключения. |
| WebSocket | Дуплексный канал после переговоров HTTP. | Добавляет протокол кадров, закрытие, отдельные ping/pong и требования к посредникам. Контакт и пересылка текущих данных уже выражаются короткими HTTP-запросами. |

Предлагается HTTPS с ограниченным long polling для уведомления и отдельным коротким чтением текущей ревизии. Он сохраняет простую периодическую сверку и даёт быструю подсказку без очереди событий. Начальный срок ожидания 25 секунд оставляет запас к типичным таймаутам посредников. Это выбор по протоколам и ограничениям, а не измерение на Entware. [RFC 6202](https://www.rfc-editor.org/rfc/rfc6202.html), [WHATWG SSE](https://html.spec.whatwg.org/multipage/server-sent-events.html), [RFC 6455](https://www.rfc-editor.org/rfc/rfc6455.html).

## Decisions

1. **Отдельный исходящий канал.** Агент использует только настроенный HTTPS origin. Проверяются цепочка доверия и имя; TLS 1.2 остаётся минимальным, TLS 1.3 предпочтителен. Системное или явно добавленное доверие к CA не отменяет проверку имени. Редиректы не выполняются, ключи не помещаются в URL. Сервер определяет устройство по авторизации запроса, IP остаётся диагностикой. Терминация TLS возможна на явно доверенном серверном входе, детали установки относятся к размещению. Формат полномочия, ротация и отзыв остаются D02/D03. [RFC 9325](https://www.rfc-editor.org/rfc/rfc9325.html), [Go net/http](https://pkg.go.dev/net/http).
2. **Текущая ревизия.** `GET /agent/v1/desired` отдаёт JSON текущей зафиксированной ревизии либо 204 при отсутствии. Успешный ответ содержит непрозрачный `ETag`, привязанный к области устройства и полному снимку. 304 на `If-None-Match` позволяет использовать полную локальную копию. Без полной копии агент делает безусловное чтение. Хранить HTTP-ответы в общих кэшах запрещено. Передаваемый положительный номер — каноническая десятичная строка в диапазоне `int64`; область номера — один роутер. Для файлов передаётся полный список `{name, contentBase64}` с точными байтами и профилем. Дубли, небезопасные имена, неполное тело, неизвестный формат или версия протокола не дают готового входа для применения. Числовые лимиты тела и таймаута загрузки определяются при D05 по измерениям. [RFC 9110, условные запросы](https://www.rfc-editor.org/rfc/rfc9110.html#section-13), [RFC 4648, base64](https://www.rfc-editor.org/rfc/rfc4648.html#section-4).
3. **Сигнал без каталога.** `GET /agent/v1/watch?after=42` сообщает последний полученный номер; `after=0` означает отсутствие известной желаемой ревизии. Если текущий зафиксированный номер отличается, сервер возвращает 200 с `{"kind":"desired_changed"}`. Если состояние не меняется за время ожидания, ответ 204 завершает цикл. Публикация отправляет подсказку только после commit и только для роутеров с новой ревизией. При запуске, восстановлении связи, подсказке и независимо раз в 60 секунд агент перечитывает текущий снимок. Начальные параметры для проверки — ожидание до 25 секунд, клиентский срок ожидания около 35 секунд, повтор при временном сбое с увеличением задержки от 1 до 60 секунд и случайным разбросом. Успешное завершение штатного ожидания начинает следующий цикл. D07 явно отменяет ожидающие обработчики перед пятсекундным drain A03, включая остановку сервера и отмену клиентского запроса. [RFC 6202, Timeouts](https://www.rfc-editor.org/rfc/rfc6202.html#section-5.5).
4. **Контакт отдельно от ожидания и применения.** `POST /agent/v1/contact` принимается по полномочиям устройства и возвращает 204. Агент отправляет контакт на старте и восстановлении, затем раз в 60 секунд независимо от ожидания сигнала, загрузки и применения. Сервер сохраняет своё время последнего принятого контакта. При возрасте 180 секунд или больше устройство вне связи. До первого контакта известен факт отсутствия наблюдения. Открытый запрос ожидания, его успешный ответ и возраст TCP-соединения не продлевают присутствие. Необязательные диагностические адреса не участвуют в идентификации. Физические часы и доступность доверенных CA в Entware проверяются при D04/D06.
5. **Отчёт переживает повтор.** Контакт может нести последнее состояние попытки; подтверждение или ошибка могут отправляться сразу с тем же типом запроса. Отчёт содержит положительный номер попытки сообщения `sequence`, номер целевой ревизии, состояние `applying`, `applied` или `failed` и при необходимости безопасные этап/код и последнее подтверждённое `appliedRevision`. Все номера локальны для устройства. Агент сохраняет монотонный счётчик и последний неподтверждённый отчёт до отправки и повторяет тот же отчёт после перезапуска. Сервер атомарно хранит последний принятый курсор и результат, которые переживают перезапуск. Точный повтор принят, меньший курсор сохраняет более новое состояние; тот же курсор с другими данными отклоняется. Ротация полномочия не сбрасывает область отчётов прежней регистрации. Восстановление после потери агентского состояния согласуется с D02/D06. Подтверждённый результат может ссылаться на известную более раннюю ревизию, когда желаемая уже сменилась. Ошибка без нового подтверждения сохраняет прежнюю применённую ревизию. Результат с меньшим применённым номером не понижает уже подтверждённый номер. E08 формирует успех после проверки записанных файлов и работающего Xray.
6. **Границы кода и проверка.** HTTP-адаптер зависит от узких прикладных операций чтения желаемой ревизии, ожидания сигнала, контакта и применения. Ядро сборки и публикация не зависят от HTTP и агентской модели. Ключи и модель статусов тестируются в D02–D08, применение проверяется на стороне агента в E. Для проверки использовать Docker/Entware, эмулируемые часы, искусственные файлы и доверенный тестовый сертификат. Физическое устройство не проверялось.

## Примеры проектных сообщений

Сигнал на ожидающий запрос:

```json
{"kind":"desired_changed"}
```

Контакт с последним сохранённым отчётом после неудачной проверки:

```json
{"report":{"sequence":"11","revision":"8","state":"failed","appliedRevision":"7","stage":"verify","code":"runtime_check_failed"}}
```

Полный ответ для синтетического снимка формы B12:

```json
{
  "revision":"8",
  "profile":"26.3.27",
  "files":[
    {"name":"01_log.json","contentBase64":"ewogICJsb2ciOiB7fQp9Cg=="},
    {"name":"02_api.json","contentBase64":"e30K"},
    {"name":"03_inbounds.json","contentBase64":"ewogICJpbmJvdW5kcyI6IFtdCn0K"},

    {"name":"05_routing.json","contentBase64":"ewogICJyb3V0aW5nIjogewogICAgInJ1bGVzIjogW10KICB9Cn0K"}
  ]
}
```

## Risks / Trade-offs

- Обрыв TLS, остановка сервера, потеря подсказки и смена ревизии во время передачи компенсируются сверкой актуального состояния. Скачанный снимок не считается применённым.
- Один ожидающий запрос на экземпляр агента требует ограничения ресурсов сервера. Проверка поведения reverse proxy, таймаутов и массового переподключения относится к D07/D08.
- Применение и его отчёт имеют отдельную устойчивость. Порядок файлового журнала и поведение после потери локального состояния остаются открытыми задачами.
