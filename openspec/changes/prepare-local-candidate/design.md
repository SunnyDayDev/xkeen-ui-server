## Context

E01 (#77, исходный проект `93bc656`) требует явно управляемую рабочую область, первую проверенную локальную базу и полный локально проверенный кандидат до устойчивого намерения. D05 возвращает полные именованные байты проверенного снимка и хранит кэш в области HTTPS origin и ID. Новый результат D05 может заменить кэш независимо от E02. C06.2 проверяет серверный кандидат в отдельно доверенном серверном Docker-воркере.

В одноразовом контейнере `xkeen-router-lab:dev` наблюдались Xray 26.3.27 и Entware `aarch64-k3.10` на Linux ARM64 с ядром `7.0.14-linuxkit`. `/opt/sbin/xray` существует; текущий `/opt/etc/xray/dat` пуст. BusyBox Entware содержит `chroot`, без `unshare` и `timeout`. Probe с отключённой сетью и `--cap-drop=ALL` показала `NoNewPrivs=1`, `Seccomp=2`, нулевые действующие capabilities. Эти наблюдения описывают контейнер; наличие требуемых средств на прошивках и возможность вложенной изоляции предстоит проверить.

## Goals / Non-Goals

E02 выдаёт независимую проверенную базу и точный кандидат с доказательствами для E03. Изменение рабочего каталога, намерение с правом на изменение, остановка/старт, API runtime, recovery и отчёт E08 принадлежат последующим этапам. Операторское принятие передаётся локальной доверенной настройкой; пользовательский интерфейс и установщик остаются отдельными задачами.

## Decisions

1. **Первая база.** Локальный оператор явно задаёт корень, допущенный профиль, разрешённые управляемые имена и политику проверки живой базы. План по умолчанию использует пять файлов B12 и допустимое необязательное имя. Под общей блокировкой прочитать ровно фактически загружаемый набор, проверить типы, имена, владельца/права, наличие достаточного места и границу одного писателя. Сверить манифест до и после read-only проверки живого PID, времени старта и заданного доверенного контрольного трафика с независимым положительным контролем. Проба не вызывает изменение через API и не берёт адреса из загруженного JSON. Неожиданный загружаемый JSON/JSONC, ссылочный/необычный файл, иное содержимое между чтениями или недоказанное владение дают отказ. Несчитываемые Xray сторонние данные сохраняются. База получает локальный ID, манифест точных байтов, старые UID/GID и режимы, и сведения о пройденной проверке. После существующей принятой базы проверить её соответствие текущему диску и runtime по доказательствам E01; автоматически принимать отличившийся каталог нельзя.
2. **Приватный набор.** Прикладной порт получает подтверждённую D04 область и проверенный снимок D05. При переносе копирует точные файлы в закрытую отдельную область, проверяет номер/профиль, полный список, SHA-256 именованных байтов и, при источнике из кэша, повторно проверяет ETag. Запись пакета использует закрытый долговременный корень, обычные файлы без ссылок, атомарное продвижение временного имени и fsync файлов и затронутых директорий. Не использовать кэш D05 как резерв. В артефакте подготовки есть привязка к origin, ID, номеру и профилю, идентификатор базы, полный манифест и идентификатор проверенного доверенного профиля. При отмене, прерывании, отказе проверки или записи готовая запись не опубликована; последующий запуск убирает только однозначно принадлежащий попытке временный staging. Существующую базу и материалы возможного незавершённого E01-намерения сохранять.
3. **Доверенный профиль локального Xray.** Бинарник, версия, ожидаемая контрольная сумма, исчерпывающий перечень разрешённых ресурсов с проверяемой целостностью, предельные ресурсы и среда запуска выбираются локальной доверенной настройкой. Кандидат не передаёт команды, флаги, пути на хосте или права. Первый стендовый профиль — статический Xray 26.3.27 и фиксированный набор B12 без внешних geoassets. Дополнительные доверенные файлы требуют явного локального профиля, включая проверку соответствия профилю рабочего Xray. Окружение очищается, команда фиксирована `xray run -test -format json -confdir <изолированный-каталог>`. Версия проверяется в той же доверенной среде; stdout/stderr и созданные журналы не возвращаются агенту и не сохраняются после попытки.
4. **Изоляция агента.** Порт локальной проверки принимает только запечатанный staged набор и идентификатор профиля. Кандидат не передаётся серверному валидатору и валидация на сервере не заменяет локальную. План первого адаптера — доверенный Linux ARM64 supervisor с отдельными mount, network и PID пространствами имён, собственной корневой иерархией, приватной propagation и drop uid/gid, supplementary groups, capabilities, унаследованных файловых дескрипторов и повышений привилегий. Профиль проверяет обязательное отсутствие доступа к сети и к рабочему каталогу, состоянию агента, устройствам, сокетам и процессам хоста. Бинарник, заданные ресурсы и каталог ревизии доступны внутри только для чтения, одноразовый scratch для лога ограничен. После перехода границы проверяется идентичность профиля и весь список байтов, затем запускается точная команда. Хостовая операция создания границы работает только с доверенными привилегиями и API фиксированной формы. Наличие `chroot`, временного каталога или `-test` само по себе недостаточно. Контракт адаптера допускает другую доверенную платформенную реализацию после тех же поведенческих доказательств. [Linux mount namespaces](https://man7.org/linux/man-pages/man7/mount_namespaces.7.html), [network namespaces](https://man7.org/linux/man-pages/man7/network_namespaces.7.html), [No New Privileges](https://origin.kernel.org/doc/html/v5.15/userspace-api/no_new_privs.html).
5. **Пределы и результаты.** Профиль доказывает принудительное ограничение времени, памяти, CPU, PID, открытых файлов и объёма writable scratch до запуска, а deadline и отмена прекращают всю группу процессов. Вход ограничен потолком D05 8 МиБ точных файлов. Отправная точка пробы — 12 секунд wall time, 128 МиБ памяти проверяющей группы, 48 процессов и 1 МиБ scratch по проверяемым ограничениям серверного стенда; отдельно измерить фактический расход Xray и агентского процесса на ARM64. Значения и поддержку закрепить по измерению, а не по имени Entware feed. Неоднозначный исход, несовпадение профиля, невозможность доказать границу, недостающий доверенный ресурс или достижение ресурсного предела дают `validation_unavailable`; явный отказ Xray в доказанной среде даёт `configuration_invalid`. Отказ приватной записи и неверная область имеют самостоятельный безопасный статус. Поздний результат, отмена или несвязанный манифест не дают готовой записи. Настоящие значения, пути, вывод Xray, бинарный код и секреты исключены из диагностики.
6. **Связь с E03.** Результат подготовки возвращается через локальный внутренний порт. До намерения E03 заново сверяет отпечаток рабочей базы, доступность runtime-проверок, неизменность кандидата и применимость текущего профиля. Успех E02 не обновляет рабочие файлы, состояние процесса и статус «применено». При отсутствующем желаемом снимке E02 не выдаёт кандидата и не запускает проверку. Периодическое получение остаётся D07, статус контакта — D06.

## Risks / Trade-offs

- Имена feed и модели, а также `aarch64` не гарантируют kernel flags, права, поддерживаемую файловую систему и пределы. Доступность изоляции сначала проверяется отдельным синтетическим запуском. Если штатный профиль не проходит её, агент безопасно отказывает перед запуском Xray и перед созданием готовой записи.
- Docker используется для изоляции лаборатории и проверки, а не как обязательная зависимость агента. Позитивная лабораторная проверка должна исполнить именно адаптер агента во вложенной одноразовой среде. Проба с одним внешним Docker только проверяет реакцию на недоступность либо свойства лабораторной обвязки.
- Принятие первой базы требует доверенного источника доказательств работающего трафика и исключительного управления. Первоначальная установка без работающей базы относится к подготовке устройства и не выдаёт вымышленную точку отката.
