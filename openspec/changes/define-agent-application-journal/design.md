## Context

[B12](../../specs/configuration-xray-catalog/spec.md) задаёт пять обязательных имён и при необходимости дополнительный файл. [C05](../../specs/configuration-revision-publication/spec.md) публикует проверенные байты. [D05](../../specs/agent-revision-synchronization/spec.md) связывает полный приватный снимок и ETag с origin, техническим ID, ревизией и профилем. Кеш D05 может обновиться независимо от применения. Копии, на которые опирается незавершённая транзакция, должны пережить это обновление.

В Compose volume смонтирован непосредственно в `/opt/etc/xray/configs`. Лабораторный образ содержит Entware aarch64, `S05xkeen`, XKeen e461c4e и Xray 26.3.27. Существующая проба проверяет замену всего списка правил, трафик и отдельную запись одного файла. Она не подтверждает атомарность каталога, надёжность носителя или восстановление при отключении питания. [Конфигурация стенда](../../../lab/compose.yaml) · [Сценарий](../../../lab/verify.sh)

## Decisions

1. **Границы владения.** Локальный оператор явно назначает управляемую область и даёт согласие на принятие текущих разрешённых имён в управление. Перед первой заменой проверить полную фактически загружаемую конфигурацию, защищённость директории, исключительность писателя, работу процесса и согласованные контрольные запросы. Первая база получает локальный ID и сохраняет исходные права доступа, владельца и байты; серверный номер появляется только после реального успешного применения. При неизвестном загружаемом JSON/JSONC, конфликте имени с неуправляемым файлом, символьной ссылке, внешнем писателе или недостаточном резерве — остановка до записи. Незагружаемые сторонние файлы остаются на месте. Сбой восстановления не разрешает очистку или принудительное принятие текущего каталога. Для установки с уже существующими чужими конфигами перенос, импорт или удаление выполняется только отдельной явно выбранной операцией владельца. Автоматическое применение на пустом устройстве без рабочей базы относится к установке/подготовке и не обещает отката к несуществующему состоянию.
2. **Носитель и журнал.** Приватный долговременный каталог, доступный одному агенту, содержит рабочую подтверждённую базу, предыдущую базу для незавершённой попытки, независимо закреплённый кандидат и запись намерения. Изолировать от `confdir`, других UID и очищаемого tmp. Запись включает версию формата, локальную область (origin, ID, профиль), ID попытки, исходное и целевое поколение, точные манифесты, прежние права, способ применения, стадию и ожидаемые проверки. Для каждого поколения хранить восстанавливаемые байты всех файлов. Отдельно хранить подтверждённый результат, пригодный для повторной передачи E08. Родительские директории и файлы временных записей синхронизировать до и после замены ссылок/имён; при изменении двух директорий синхронизировать обе. Файлы заменять через временное имя в той же файловой системе. Не завершать стадию при ошибке fsync/rename. Для неподходящей FS или неподтверждённой возможности безопасного старта отказ до рабочих эффектов. [rename(2)](https://man7.org/linux/man-pages/man2/rename.2.html) · [fsync(2)](https://man7.org/linux/man-pages/man2/fsync.2.html)
3. **Последовательность.** Один эксклюзивный владелец области охватывает штатную работу и recovery. До намерения проверить актуальность базы, свободное место, полный D05-кандидат и Xray на устройстве. Ограничить файловые эффекты `-test`: фиксированные бинарник/профиль и разрешённые read-only ресурсы, одноразовое место для журналов. Невозможность безопасной проверки даёт недоступность. После надёжной записи намерения разрешается первый внешний эффект, включая остановку службы или API-команду. Записать стадии `prepared → intent → changing → disk/runtime verified → committed`. Стадия указывает последний надёжно подтверждённый рубеж; реальный эффект может опережать запись. Для hot/restart порядок между диском и runtime различается. Итог и указатель подтверждённой базы составляют одну долговременную точку фиксации (например, атомарная замена единственной записи). Ресурсы освобождаются только после фиксации и только если больше не нужны для recovery/повторной передачи. Очередные D05/D07 сигналы коалесцируются; новая ревизия не вытесняет материалы незавершённой попытки. Проигранный рестарт агента/службы и ручная правка также требуют повторной сверки.
4. **Рестарт на существующем layout.** Установить барьер до штатного старта/рестарта XKeen, подтвердить его до начала изменения; остановить службу, дождаться действительного завершения процесса. Только тогда установить производное от полного нового манифеста множество файлов. Вначале резервируется весь старый набор. Источник каждого восстановления проверяется по старому манифесту. При восстановлении возможна ожидаемая смесь старых, новых и отсутствующих управляемых файлов; обнаружение иного содержимого/посторонней записи блокирует перезапись. Старый опциональный файл удаляется из рабочего набора только при подтверждённом владении и наличии точной копии. Перед разрешением старта сверить множество, байты и разрешения. Запускать только по полной проверенной конфигурации. На стенде recovery должно предшествовать и entrypoint, и автозапуску `S05xkeen`; остановка одного текущего PID не даёт барьера. Если адаптер не контролирует эти пути, он не допускается. Для другого размещения возможен доказанный селектор поколений с фиксацией выбора на весь запуск; переход на него потребует осознанной миграции.
5. **Горячая замена.** Определяет E06 по старому и новому полным снимкам. Вне `05_routing.json` все именованные байты должны совпасть; внутри него прочие JSON-значения сравнивать без потери точности. Изменение одного форматирования без изменения списка правил не доказывает применимость hot. Поддерживаемая версия, полный replace, живой API, проверяемая семантика и отдельные доказательства обязательны. После намерения E07 отправляет весь список, проверяет его и положительный/целевой трафик при том же PID и времени запуска, затем атомарно записывает точный файл и проверяет окончательный диск и runtime. При неопределённом исходе уже отправленной команды нельзя автоматически повторить её как первый шаг. Откат выполняет полную остановку/восстановление/запуск и проверку прежней базы. Успех API отдельно от фиксации файла никогда не завершает попытку.
6. **Доказательства и отчёт.** До изменения убедиться, что проверка выполняема для прежнего и желаемого профиля. Ожидаемые разрешённое/запрещённое поведение задаёт доверенный профиль проверки, адреса для проб не извлекаются из произвольного JSON. На изолированном стенде используют искусственный HTTP endpoint и контролируемый разрешённый маршрут через работающий прокси, отдельный от запрещённого маршрута; один отказ соединения не отличает блокировку правилом от упавшего inbound. Для hot проверить API-представление полного списка в доступной семантике, идентичность процесса и свежие соединения. Для restart проверить новый процесс, загрузку согласованного каталога и реальный трафик. Если профиль не позволяет доказать результат, E08 не сообщает успех. D06 может отдельно сообщать контакт, стадию, ошибку и историческую последнюю подтверждённую ревизию. После сбоя отката runtime неизвестен. Только E08 передаёт устойчиво записанный успех с соответствующим курсором D06; повтор после потери ответа сохраняет идентичность отчёта в правилах D06.
7. **Сохранённая фиксация.** Если до сбоя был надёжный commit и прежнее намерение снято, не откатывать новую базу только из-за пропущенного отчёта. Перепроверить диск и процесс, затем повторить отчёт. Если доказательство актуальности не восстанавливается, отметить ошибку/неизвестный runtime и сохранить историю. Противоречивые или повреждённые записи, внешние изменения и неопределённый rollback требуют вмешательства. Устойчивый отказ проверки при восстановлении не должен порождать бесконечный цикл рестартов.

## Матрица отказов

| Момент | Что разрешено наблюдать | Действие после прерывания |
| --- | --- | --- |
| 1. Проверка, резерв или подготовка кандидата до устойчивого намерения | Рабочая база и процесс прежние | Не менять рабочие файлы; убирать только однозначно принадлежащий агенту временный материал. |
| 2. Намерение надёжно, внешнего эффекта ещё нет | Полная старая база | При доказанном отсутствии воздействия сверить базу/процесс, завершить прерванную попытку. При неоднозначности перейти к полному откату. |
| 3. Остановка, замена одного из файлов, удаление опционального файла, ошибка fsync его родителя | Рабочий каталог может быть смешанным | До старта проверить обязательные доказательства, восстановить весь прежний набор и прочитать его вновь. |
| 4. Новый диск готов, запуск или проверка runtime не завершились | Наличие новых байтов не определяет рабочий трафик | Полный откат к прежней проверенной базе и положительная проверка трафика. |
| 5. Горячий запрос мог быть исполнен с потерей ответа; либо API приняло правила до записи файла | Процесс и диск могут различаться | Сохранить намерение, восстановить прежний набор полным restart-путём и проверить его. |
| 6. Кандидат выглядит рабочим, итоговая отметка или её parent fsync не подтверждены | Долговременный статус неясен | При запуске читать точку фиксации и обе базы. Целая действительная запись commit требует повторной проверки новой базы; надёжное незавершённое намерение требует консервативного отката. При противоречии остановиться. |
| 7. Commit устойчив, подтверждение E08/D06 не отправлено либо ответ потерян | Доказанный текущий результат сохранён локально | Повторная сверка, затем доставка сохранённого исхода по правилам D06 без нового изменения runtime. |
| 8. Ошибка отката, повреждённый журнал, утраченная предыдущая база, внешний конфликт | Текущее состояние нельзя подтвердить | Сохранить доказательства и последнее историческое подтверждение. Остановить автоматическое применение, сообщить безопасный диагностический результат. |

## Поставки до E08

| Этап | Наблюдаемая поставка и необходимые проверки |
| --- | --- |
| E02 | Подготовка из принятого D05: первая проверенная база, безопасный полный кандидат, проверка на локальном Xray; негативные сценарии не меняют диск/трафик. |
| E03 | Журнал, запись намерения и запуск по полной ревизии restart-путём; доказать барьер стартов и изменение поведения на изолированном стенде. |
| E04 | Полный откат к прежней базе при отказе запуска/трафика, отдельный неуспех отката. Резервы, исчезновение/возврат дополнительного файла и сохранность чужих данных. |
| E05 | Восстановление до обычного старта после прерывания. Проверять выбранные точки матрицы в отдельных одноразовых каталогах, повторный recovery идемпотентен. |
| E06 | Самостоятельная классификация hot/restart после E03. Изменения структуры, полей routing, остального набора или неподтверждённая поддержка требуют restart. |
| E07 | После E04 и E06 реализовать API replace правил с сохранением файла и проверкой процесса/трафика; инъекция сбоя между API и диском должна восстановить прежнюю базу. |
| E08 | Отдельная интеграция после E05, E07 и D06. Передавать проверенный устойчивый исход, включая потерянный ответ, неизвестный runtime и отсутствие ложного «применено». |

## Ограничения

Docker со встроенными ресурсами позволяет проверить программные состояния и прерывание процессов. Успех стенда не доказывает поведение физического накопителя при потере питания. Рабочие volumes, устройства, резервные копии пользователей и внешние адреса не входят в поставку.
