## Context

Прототип §12 и описание API согласовали независимые переключатели. Исходные требования оставили начальные значения, форму токена и его жизненный цикл открытыми. Сессия владельца F03 и полномочия агента D02 работают в разных областях. Текущий C02/C03 задаёт точное чтение и атомарную условную запись редактируемых снимков.

## Решения для ревью

- **Дефолты.** Предложение для чистой установки и обновления без настроек — выключенный API, включённое требование авторизации, токен отсутствует. Включение API в таком состоянии закрывает доступ до выпуска токена. Выключенное требование авторизации по умолчанию создаёт риск открыть управление одним последующим действием. Включённый API по умолчанию допускает неожиданный сетевой вход после добавления токена. Действующие сохранённые значения при перезапуске не переопределяются. Окончательный выбор ожидает решения владельца.
- **Токен F20.** Предложение для первой версии — один непрозрачный 256-битный токен, канонический base64url, представляемый только в заголовке Bearer. Сервер хранит хэш и поколение. Администратор получает секрет один раз при успешном выпуске/замене. При потерянном ответе выдача нового токена выполняется явной командой, потому что копию секрета сервер восстановить не может. Замена без периода перекрытия исключает старое полномочие сразу; несколько автоматизаций должны обновиться синхронно. Альтернатива — несколько независимо отзываемых токенов, требующих списка, именования, правил диагностики и отдельного дизайна. Переключение требования авторизации сохраняет токен неактивным до повторного включения; отключение требования в активном API явно показывает немедленный доступ с сети. Внешний токен не позволяет менять режим доступа или выпускать полномочия D02. [Семантика Bearer](https://www.rfc-editor.org/rfc/rfc6750.html#section-2.1).
- **Допуск.** При выключенном API маршруты внешней области отвечают 404. При включённой авторизации недействительный или отсутствующий заголовок получает общий 401 и Bearer challenge. При выключенной авторизации Bearer не требуется и не меняет объём полномочий. Отдельный namespace `/api/v1` доступен по HTTPS с проверкой реального TLS, без доверия forwarded-заголовкам. Ответы без кэша и CORS, строгий JSON у записи. Браузерные cookies, ключи агента и внешний токен не взаимозаменяемы. Сетевой режим API не меняет bind, проброс, сертификат или синхронизацию. Диагностика исключает заголовки авторизации, конфигурацию и значения.
- **Рубеж записи.** Изменение доступа и токена относится к подтверждённому владельцу F03. Между проверкой и эффектом API повторно проверяются поколение допуска, необходимость Bearer и актуальность токена в той же writer-транзакции, что изменение шаблона. Выключение или отзыв, произошедшие до записи, исключают эффект. Снимок для чтения и проверка доступа имеют общую точку чтения. Сборка и публикация отделены от редактирования.
- **F21 и F22.** Предварительный срез — `GET` и `PATCH` одного шаблона по точному ID из query, без списка и произвольного массового изменения. GET возвращает полный редактируемый снимок C02 с точным сырым текстом и десятичной строкой версии. PATCH меняет исходный JSON одного существующего UUID через тот же узкий прикладной сценарий, что F07. `If-Match` связывает запись с выбранным снимком, а C03 проверяет версию под writer. Проектный ответ отсутствующего предусловия 428, конфликт версии 412, синтаксис конверта 400, ошибка структуры правки 422, отсутствие ресурса 404, ошибка сервиса 503. Повтор после потери успешного ответа получает конфликт; клиент перечитывает снимок. Сильный ETag относится к детерминированным байтам представления, посредник их не преобразует. [Условные запросы](https://www.rfc-editor.org/rfc/rfc9110.html#name-if-match), [код 428](https://www.rfc-editor.org/rfc/rfc6585.html#section-3).
- **Разделение работ.** F20 реализует переключатели и допуск без операций шаблонов. Только макеты и реализация контролов F20 используют настройки владельца UI. F21 открывает чтение одного шаблона. F22 открывает один вид его правки после F07 и F21. Остальные операции требуют отдельного контракта.

## Risks / Trade-offs

Работа без авторизации — явное распространение полномочий на сетевой контур, который контролирует оператор. Проксирование и сетевые ограничения не заменяются заголовками приложения. Поддержка одного токена упрощает изоляцию и отзыв, но вводит краткую координацию ротации для нескольких потребителей.
