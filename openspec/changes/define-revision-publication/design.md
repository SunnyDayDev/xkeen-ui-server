## Context

B07/B08 описывают полный порядок до исключений и блокировку общего сохранения при ошибке одного роутера. B12 даёт детерминированные именованные файлы, доменные ошибки и привязку диагностики к исходным записям. C03 версионирует шаблон, C04 хранит редактируемый снимок роутера. Действия экрана 08 описаны в прототипе. C05 уточняет их серверный контракт.

## Decisions

1. **Отдельный путь публикации.** Сохранение черновика через C03/C04 само по себе не публикует. Сценарий явного «Сохранить» принимает кандидат правки и исходные версии либо запрашивает публикацию уже сохранённого черновика в допустимом объёме. Принятая новая правка, изменения порядка и указатели желаемых ревизий входят в общую атомарную запись. Не принятый кандидат остаётся у вызывающего; ранее отдельно записанный черновик доступен после отказа.
2. **Источник действующего назначения.** Хранить подтверждённую связь «роутер → шаблон» с настройками активного контекста на сервере. Рабочий снимок C04 с ID другого шаблона сам по себе не меняет эту связь и не заменяет действующие персональные настройки. Для A→B настройка B хранится отдельно от активного контекста A до явного подтверждения. Состав участников общей публикации определяет подтверждённая связь, а не последний опубликованный payload и не текущий текст черновика. Для первого назначения до успешного подтверждения у устройства нет действующей связи. C06 готовит публикацию под явно действующее назначение; G01/G02 определяют установление/смену профиля как отдельный сценарий, включая перенос, проверку значений и согласование данных после отказа. C05 обещает только изоляцию ожидающей смены и контроль конкуренции.
3. **Основание пересчёта.** Вместе с персональным порядком хранить ID шаблона, известную версию источника и полный список общих UUID, относительно которого персональный порядок был согласован. Полный список даёт B08 исходные данные без истории версий и без разбора прежних файлов, из которых исключённые и отключённые позиции могли исчезнуть. При записи C04 до появления такого поля отсутствие основания не восстанавливать догадкой. Пользователь может передать явно согласованный полный порядок для актуальной версии; тогда он проверяется B08 как новый. Для наследования нет персонального списка и основания. При изменении шаблона пересчитать персональные порядки из их сохранённых оснований и зафиксировать новое основание вместе с успешной правкой, включая случай без новой ревизии.
4. **Контракты сборки и проверки.** Прикладной сценарий читает полный согласованный снимок, строит группы B12, вызывает ядро B08/B12 и передаёт полные файлы инфраструктурному порту проверки. Полностью загруженные отсутствующие обязательные секции нормализуются в шесть явных пустых групп; отсутствие шаблона/настроек или ошибка чтения остаются ошибками. Произвольный JSON дополнительных секций остаётся в границах B12. Согласованный начальный профиль соответствует закреплённому Xray 26.3.27 из B12. Порт принимает каталог и профиль, возвращает успешную проверку именно этих байтов либо один из результатов: конфигурация отвергнута, выполнение проверки невозможно. Адаптер C06 должен создать отдельный временный каталог, проверить версию, ограничить время исполнения, применить `-test` к полному снимку и исключить из внешней диагностики сырой вывод процесса. Проверка не запускает рабочий Xray. Источник валидатора и установка для Docker/Entware уточняются в C06; при отсутствии валидатора публикация запрещена. Агент проверяет на своём устройстве отдельно.
5. **Идентичность и CAS.** Равенство проверяется по имени и байтам, независимо от порядка перечисления файлов. Хеш можно добавить как ускорение, без подмены точной проверки. Идентификатор ревизии локален для роутера, payload после фиксации неизменяем. Итог предыдущей публикации и проверенная версия Xray сохраняются отдельно от состояния применения. Чтение снимка и предварительные проверки выполняются вне блокировки записи после получения согласованного снимка. Транзакция финализации сравнивает версии C03 и монотонные токены активных настроек/назначений, основания порядка и текущей желаемой ревизии, а для общего сценария повторно сверяет полный состав подтверждённых назначений. Изменение состава, в том числе появление нового участника, даёт конфликт. Обновления из других сценариев должны участвовать в тех же токенах. Схему и узкий порт записи определяют C06/C07. Уведомление возможно после commit; сверка агентом восстанавливает доставку при пропуске. Ключи повторной команды HTTP остаются вопросом API.
6. **Разделение работ.** C06 публикует валидированный результат одного явно заданного роутера с действующим назначением. C07 добавляет общую правку, обнаружение всех участников, согласование B08 и атомарную групповую запись. G01/G02 владеют подтверждением назначения, переносом персональных данных и жизненным циклом смены. Смена формата payload, поддержка нескольких Xray-профилей, сетевой транспорт, пользовательские экраны и `exclude_ips` требуют своих изменений.

## Risks / Trade-offs

- Обязательная проверка каждого участника может удлинить общую публикацию. Проверка до транзакции позволяет не держать блокировку на время запуска Xray. Повторная сверка защищает результат от устаревания.
- У старых персональных списков может отсутствовать записанное основание. Явное согласование сохраняет человеческий выбор и исключает скрытую перестановку.
- До выбора способа поставки валидатора способность публиковать в конкретной среде остаётся непроверенной.

## Migration Plan

C05 меняет только контракт. C06/C07 фиксируют модель хранения и проверяют существующие данные C03/C04 в своих изменениях. История применения и восстановление на роутере остаются задачами агента.
