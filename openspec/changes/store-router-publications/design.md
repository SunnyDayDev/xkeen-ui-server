## Context

C05 разделяет подготовку точных файлов и атомарную запись проверенного результата. C03 хранит текущий редактируемый шаблон и его версию. C04 хранит один редактируемый снимок роутера. Ни одна из этих записей сама по себе не даёт действующего назначения или принятого общего снимка. C06.1 готовит каталог и `OrderBasis`, C06.2 проверяет точные файлы, C06.4 управляет командой.

## Decisions

1. **Порт прикладного слоя.** В `internal/application/publication` определить узкий контракт чтения и фиксации. Чтение получает идентификатор роутера и, для первого подтверждения, выбранный ID шаблона. Оно возвращает независимые значения и точные токены ожидаемого состояния. Принятый общий снимок использует существующее представление `templates.Snapshot`, активный персональный — `routersettings.Draft` и `OrderBasis` из C06.1. Запрошенные рабочие черновики возвращаются отдельно. Снимок явно различает «отсутствует», «не запрошен» и «есть запись». Сборку, проверку Xray, определение равенства именованных байтов и выбор нужных входов делает прикладная операция C06.4 с существующими портами. Хранилище получает уже подготовленный план фиксации с ожиданиями использованных входов и необязательной новой ревизией. Необязательная ревизия означает сохранение уже существующей желаемой записи, а при первом подтверждении обязательны проверенные файлы новой ревизии. Данные портов не содержат SQL-типы.
2. **SQLite-представление.** Принятый общий снимок — копия полных неизменяемых данных с ID и исходной версией C03. Хранить запись отдельно от изменяемого `templates`. Действующий контекст адресуется ID роутера и хранит подтверждённое назначение, полный активный снимок, полный персональный порядок/основание и монотонный токен. Редактируемая запись C04 остаётся отдельной; добавить к ней монотонную версию, которую увеличивает каждое успешное `Save`. Желаемые ревизии хранят неизменяемую запись (ID роутера, возрастающая локальная версия, полный именованный набор и проверенный профиль), запись наибольшей версии является текущей. Это достаточно для C06, который не перематывает состояние. Хранить файлы как байты, например в одном внутреннем кодированном наборе, сохраняя различие имён и точное содержимое. Не изменять исходное кодирование элементов A08. Режимы истории, удаления и смены профиля проектируются отдельно.
3. **Согласованное чтение.** Взять значения шаблона, принятых записей, действующих настроек и текущей ревизии в одной короткой SQLite-транзакции. При необходимости читать только затребованные редактируемые записи и сохранить обязательные токены. Открытое чтение завершается до передачи снимка в B08/B12 и Xray. Применить строгий разбор хранимых записей, возвратить безопасную ошибку вместо частичного снимка при повреждении. Повторно использовать существующие кодеки C02/C04 в адаптере.
4. **Атомарная фиксация.** Транзакция с ранним захватом блокировки записи сравнивает токены принятого снимка, активных настроек с их порядком/основанием, желаемой ревизии и каждого использованного или обновляемого черновика. Отсутствующий вход — отдельное проверяемое ожидание, не прежнее значение по умолчанию. Ожидания C03/C04 включаются только если сценарий использовал запись или меняет её. Транзакция обновляет действующие настройки и при необходимости добавляет ревизию. Успех возвращается после commit. Сценарий A с ожидающим B обновляет только активные поля A. Не соединять записи нескольких роутеров внешним циклом: C07 должен координировать общий набор ожиданий и записей в одной будущей транзакции.
5. **Первое подтверждение.** Отдельный режим проверяет отсутствие действующего назначения и желаемой ревизии роутера. Если общий снимок уже принят, проверяется его ожидаемый токен. Если нужен bootstrap, под той же блокировкой проверяются исходная версия C03, отсутствие принятого снимка и отсутствие действующих назначений на шаблон. Сохраняется копия именно сверенного снимка, затем действующий контекст только указанного роутера и его первая ревизия. Два конкурента на первый общий снимок несовместимы после commit первого; второй должен заново загрузить принятый снимок, а не переписывать победителя.
6. **Миграция и ошибки.** Следующая свободная миграция после C03 (план v5) создаёт таблицы принятого, действующего и желаемого состояния и версию редактируемой строки C04. Уже существующим редактируемым снимкам назначается исходный токен без изменения JSON. Подтверждение и ревизии не выводятся из старых черновиков. Безопасные ошибки различают конфликт, повреждение, отсутствие и невозможность операции, не содержат данных каталога и сырого вывода SQLite. Проверка переполнения версий выполняется до изменения данных.

## Risks / Trade-offs

- Полный снимок и набор файлов могут быть объёмными. Хранилище фиксирует проверенные байты без запуска внешнего процесса в транзакции. Отдельная политика удержания давних ревизий требует будущего решения.
- Совпадение ID в редакторе и действующем состоянии недостаточно для CAS: токен черновика нужен при реальном использовании, активный токен нужен отдельно. Счётчики проверяются совместно с идентичностью записей.
- Ожидание занятой БД отличается от установленного несовпадения версий. Интеграционные тесты используют независимые подключения к одному файлу.

## Migration Plan

Этап 1 добавляет миграцию и согласованное чтение, включая восстановление точных данных и независимых идентичностей. Этап 2 добавляет CAS текущего назначения, сохранение изменений/no-op и тесты отката. Этап 3 добавляет первое подтверждение и конкурентный bootstrap. После миграции открыть тот же файл и проверить C03, C04 и новые записи через независимые подключения. C06.4 подключает реальную подготовку и проверку после принятия порта; C07 добавляет групповую запись отдельно.
