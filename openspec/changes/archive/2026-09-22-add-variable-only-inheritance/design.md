## Context

Мотивация и трекер — в [proposal](proposal.md), поведение — в [дельте](specs/configuration-content-inheritance/spec.md). До реализации B04 код наследования отсутствовал; описанный ниже интерфейс теперь реализован, фактические проверки приведены в verification.md. Design нужен для новой модели ссылки на источник, контракта операции и объединения двух существующих видов диагностики.

Проверенная база:

- [Element и ElementLocation](../../../../internal/configuration/element.go) представляют редактируемый элемент и контекст. `RestoreElement` проверяет сохранённую запись; это не готовность к сборке.
- [AssembleElement](../../../../internal/configuration/assemble.go) уже соединяет B01/B02. Его ID — диагностический, UUID и владельцы там не проверяются. [Тесты](../../../../internal/configuration/assemble_test.go) покрывают переменные, дефолты, синтаксис и независимость JSON.
- [Проверки идентичности](../../../../internal/configuration/identity_set.go) используют `ValidElementID` из модели элемента, проверяют владельца/позицию и полный набор. Они не представляют персональную ссылку и не обнаруживают повторные переопределения.
- [B03](../2026-09-21-define-content-inheritance/design.md) передаёт B04 актуальный шаблон и персональные значения; B05 — переходы режимов и полную замену; B06 — объединение и исключения.

## Goals / Non-Goals

**Goals:** дать ядру чистую границу одного элемента, которая проверяет источник перед B02, возвращает идентичность вместе с независимым JSON и добавляет контекст к диагностике. Текущие снимки данных передаёт вызывающая сторона.

**Non-Goals:** загрузка «последнего» шаблона из БД, транзакции и сохранение персональных настроек; универсальная модель роутера; обработка набора или режимов B05/B06. Операция не принимает порядок и поэтому не может его менять. Она предназначена для уже выбранной наследуемой ветви: будущая полная замена или исключение должны выбирать свою ветвь до её вызова.

## Decisions

### 1. Отдельная доменная операция поверх B02

Реализованный интерфейс в `internal/configuration` (контракт, по которому написаны тесты):

```go
type ElementSource struct {
    TemplateID string
    ElementID  string
}

type VariableOverride struct {
    Source ElementSource
    Values map[string]json.RawMessage
}

type InheritedContent struct {
    Source  ElementSource
    Content json.RawMessage
}

type InheritanceIssue struct {
    Issue
    Location ElementLocation
}

func AssembleInheritedElement(
    element Element,
    templateLocation ElementLocation,
    routerLocation ElementLocation,
    personal *VariableOverride,
) (*InheritedContent, []InheritanceIssue)
```

`templateLocation.Owner` имеет вид `Owner{Kind: "template", ID: "template-a"}`, `routerLocation.Owner` — `Owner{Kind: "router", ID: "router-a"}`. ID владельцев — непустые корректные UTF-8 строки, без нового требования UUID. Позиции следуют существующим правилам A08: пустая строка либо JSON Pointer с корректным экранированием. `ElementSource` относится только к общему элементу; самостоятельный локальный элемент не получает фиктивный шаблон.

Источник результата формируется из владельца переданного шаблона и `element.ID`, а не копируется из непроверенной персональной записи. `personal == nil` означает отсутствие записи. Непустая ссылка с `Values == nil` или пустой картой означает запись без заполненных значений; ссылка всё равно проверяется. Непустой набор не создаёт отдельную копию исходного JSON.

Возвращаем либо ненулевой результат и пустые ошибки, либо `nil` и хотя бы одну ошибку. Имя файла для реализации — `inheritance.go`, тесты — `inheritance_test.go` в существующем внешнем пакете `configuration_test`. Новые типы не добавляются в формат `elementjson`.

**Альтернативы:** расширение `AssembleElement` контекстом роутера меняет низкоуровневый контракт без необходимости. Передача только карты значений оставляет источник непроверенным. Операция полного набора преждевременно вводит объединение B06. Отдельный интерфейс сервиса или репозиторий не нужны: у этой операции нет I/O или сменяемого адаптера.

### 2. Проверить контекст и источник до переменных

Порядок проверок:

1. Валидировать оба контекста и ожидаемые виды владельцев существующими примитивами. Неверный контекст даёт `invalid_element_record` с пустой `Location`; некорректные входные поля не копируются. Корректный UUID исходного элемента указывается, невалидный — опускается.
2. Проверить UUID исходного элемента. Неверный — `invalid_element_id`, контекст шаблона, без ошибочного UUID в диагностике.
3. Если запись есть, проверить непустой UTF-8 `Source.TemplateID` и канонический `Source.ElementID`. Ошибки — `invalid_element_record` или `invalid_element_id`, контекст роутера, допустимый UUID исходного элемента.
4. Сравнить UUID ссылки с UUID элемента: `element_id_mismatch`. Затем сравнить `TemplateID`: `source_mismatch`. Если неверны оба компонента, первая ошибка — несовпадение UUID. Совпадение `tag` не участвует в проверках.
5. Только после успеха вызвать `AssembleElement(element.ID, rawContent, element.Variables, values)`.

Коды и приоритет ошибок идентичности дополняют контракт B02, а не меняют порядок его внутренних ошибок. `Source: "record"` используется для ошибок контекста/идентичности; путь переменной для них не выдумывается.

**Альтернативы:** игнорирование чужой записи с переходом к дефолтам скрывает ошибку привязки. Пользователь подтвердил отказ при несовпадении источника. Сначала собирать JSON нецелесообразно: ошибки переменных чужого контекста не должны скрывать несовпадение источника.

### 3. Повторная сборка использует новый снимок без миграции данных

Операция не хранит состояние между вызовами. Повторный вызов с изменённым `Element` и тем же `VariableOverride` использует новые JSON, определения и дефолты. Нет преобразования сохранённого JSON, копии унаследованного шаблона или слияния готовых JSON-объектов. B02 сохраняет собственные правила, в том числе проверку неиспользуемых определений, лишних значений и неверного дефолта при заполненном персональном значении.

Входы только читаются. Буфер готового JSON уже принадлежит результату B02; оболочка результата содержит только значения строк и этот буфер. Нет необходимости возвращать подготовленные значения или изменённую персональную запись. Последовательные тесты подтверждают, что дефолт не превращается в персональное значение, а ошибка не удаляет пользовательские данные.

`RestoreElement`/`PrepareElement` не вызываются как дополнительная стадия сборки: первый меняет порядок и вид диагностики JSON относительно B02, второй также автообъявляет переменные при сохранении. Здесь нужны отдельные проверки идентичности и существующий полный контракт B02. Успех сборки не гарантирует точное форматирование исходного JSON, но гарантирует значения, типы, точность чисел и порядок массивов.

### 4. Дополнить диагностику владельцем, сохранив ошибки B02

`InheritanceIssue` включает существующий `Issue` и `Location`; новые поля не нужны в низкоуровневом `Issue` или `ElementIssue`. Для ошибок B02:

| Источник ошибки | Контекст |
| --- | --- |
| `template`, `definition`, `default` | `templateLocation` |
| `value`, включая `missing_value` без персональной записи | `routerLocation` |

`Path`, `Offset`, `VariableName`, `ExpectedType` и `Code` сохраняются. Позиция элемента в `Location.Position` и путь внутри JSON/значения в `Issue.Path` — разные координаты. Ошибки не включают карты, определения или сырой JSON. Тесты проверяют отсутствие специально заданных значений-маркеров во всей диагностике, а не только её строковом представлении.

Ядро владеет проверкой привязки и инвариантами сборки. Будущий прикладной слой передаст согласованные снимки и будет решать, сохранять ли черновик или публиковать ревизию; HTTP/БД-адаптеры зависят от ядра. Ссылки на существующий шаблон и принадлежность настроек конкретному роутеру загружает вызывающая сторона. Эта операция не устанавливает авторизацию и не ищет удалённый источник.

### 5. Проверить наблюдаемое поведение по сценариям

Тесты вызывают новый публичный интерфейс, не подменяя B02. Для каждого небольшого сценария сначала написать тест и подтвердить поведенческий Red; допускаются минимальные объявления и заглушка для компиляции. Затем минимальная логика для Green, рефакторинг и повторная целевая проверка. Если композиционный сценарий сразу проходит после предыдущего шага, отметить фактический первоначальный Green, не заявляя вымышленный Red и не ломая рабочую логику ради него.

Группы: базовая сборка; неверный источник; изменение JSON/дефолтов; эволюция определений; диагностический контекст; независимость буферов и регрессии B02. Набор сценариев и проверки перечислены в [tasks](tasks.md).

Связанные будущие экраны — 10 (только переменные), 07/08 (результат и ошибки). Этот change не меняет UI и не реализует эти экраны; актуализация и проверка макета через Pencil остаётся обязательной частью отдельного изменения UI. Здесь макет не объявляется проверенным.

## Risks / Trade-offs

- «Актуальный шаблон» можно ошибочно понимать как автоматическую загрузку → документировать снимок как вход и проверять последовательные вызовы с разными снимками.
- Успех одного элемента можно принять за проверку всего роутера → явно ограничить результат; не добавлять проверки `duplicate_override` в API с одной записью.
- Новая обязательная переменная или удалённое определение блокирует сборку → возвращать обычную ошибку B02, оставляя данные для исправления; миграция значений не входит в B04.
- Дополнительная модель может превратиться в сериализацию роутера → оставить узкие типы ядра без методов хранения и полей будущих режимов.

## Migration Plan

Данных B04 в хранилище ещё нет, миграция не требуется. После реализации и проверок обновить статус в документации, сверить критерии отдельной issue B04, синхронизировать дельту и архивировать change по workflow завершения. Закрытие issue проверяется отдельно от архива; частичная реализация не закрывает задачу. Откат кода B04 до интеграции с хранилищем не требует миграции устройств.
