## Context

Мотивация и трекер — в [proposal](proposal.md); наблюдаемое поведение — в [дельте](specs/configuration-content-inheritance/spec.md). Design необходим из-за новой модели персонального состояния и разделения перехода режима и сборки.

Проверенная база:

- [inheritance.go](../../../../internal/configuration/inheritance.go) содержит `ElementSource`, `VariableOverride`, `InheritedContent`, `InheritanceIssue` и `AssembleInheritedElement`. B04 сначала проверяет контекст и источник, затем вызывает B02. Режимов и переходов нет.
- [element.go](../../../../internal/configuration/element.go) и [identity_set.go](../../../../internal/configuration/identity_set.go) дают проверку UUID/владельцев/позиций и диагностический `ElementIssue` с `OtherLocation`. Проверка самостоятельных ID не проверяет повторные переопределения.
- [json.go](../../../../internal/configuration/json.go) оборачивает `internal/jsonvalue`: один JSON, UTF-8, повторные ключи, точные числа. Запрет `null` и интерпретация ссылок находятся выше синтаксического парсера.
- [inheritance_test.go](../../../../internal/configuration/inheritance_test.go) проверяет публичную границу из внешнего пакета, сохраняет снимки входов, включая неверный JSON, и сравнивает безопасную диагностику. Этот подход подходит для B05.
- [Design B03](../2026-09-21-define-content-inheritance/design.md) передаёт B05 замену, возврат/сброс/отмену и повторные переопределения; B06 получает объединение и исключения. B03 требует явно передавать содержимое при повторной активации замены, не обещая восстановления черновика редактора.

Допустимость корневого и вложенного `null` подтверждена пользователем 2026-09-22. Пользователь выбрал реализацию change; описанные ниже интерфейсы теперь реализованы. Фактические проверки приведены в [verification.md](verification.md).

## Goals / Non-Goals

**Goals:** чистые границы выбора одного элемента и получения кандидата персонального состояния; общие проверки источника без изменения диагностики B04; отдельная проверка списка ссылок для последующей композиции B06.

**Non-Goals:** загрузка источника, хранение после перезапуска, формат HTTP/БД, редактирование переменных, история черновиков и транзакция публикации. Операции принимают уже выбранный существующий источник. Состояние порядка и исключения остаётся снаружи; смена профиля и удалённый источник не маскируются локальным элементом.

## Decisions

### 1. Отдельная модель состояния и результат выбранной ветви

Реализованные публичные типы в `internal/configuration`, файл `content_override.go`:

```go
type ContentMode string
const (
    ContentModeVariables ContentMode = "variables"
    ContentModeReplacement ContentMode = "replacement"
)

type ContentOverride struct {
    Source ElementSource
    Mode ContentMode
    Values map[string]json.RawMessage
    Content json.RawMessage
}

type SelectedContent struct {
    Source ElementSource
    Mode ContentMode
    Content json.RawMessage
}

func SelectElementContent(
    element Element,
    templateLocation, routerLocation ElementLocation,
    personal *ContentOverride,
) (*SelectedContent, []InheritanceIssue)
```

`personal == nil` означает наследование без значений; непустая запись обязана иметь явный известный `Mode`. Пустая карта в режиме переменных использует дефолты. `SelectedContent.Mode == variables` обозначает наследуемую ветвь независимо от заполненности карты; для отдельной плашки UI вызывающая сторона имеет исходное состояние. В полной замене `Content` содержит готовое буквальное JSON-значение, а `Values` сохраняет неактивные данные. Нет определений переменных полной замены.

Выбор возвращает либо ненулевой результат без ошибок, либо nil и ошибки. Корневой JSON `null` — ненулевой результат с байтами `null`, а не nil-результат и не отсутствие элемента. `Content` в режиме переменных не участвует в выборе; контракт хранения неактивного собственного черновика не вводится.

Новые типы не расширяют `Element`/`elementjson` и не заменяют публичные типы B04. Альтернатива с помещением полной замены в `Element` создаёт ненужные определения и риск автообъявления `${name}`; универсальная модель всего роутера преждевременна.

### 2. Сначала идентичность, затем только активная ветвь

Порядок выбора:

1. Проверить оба контекста и виды владельцев, UUID общего элемента и персональную ссылку в точности как B04. Приоритет — контексты, UUID элемента, структура ссылки, UUID ссылки, несовпадение UUID, несовпадение шаблона. Для неверного контекста возвращать пустую `Location`, невалидный UUID опускать.
2. Проверить режим непустой записи: неизвестный даёт `invalid_element_record`, `Source: record`, контекст роутера.
3. Для отсутствующей записи или `variables` вызвать B04, преобразовав запись в `VariableOverride`. Сохранить ошибки без изменений и обернуть успешное содержимое в `SelectedContent`.
4. Для `replacement` проверить только персональный `Content` через существующий `parseJSON`. Не вызывать B01/B02, `PrepareElement` или `RestoreElement`. После синтаксического успеха вернуть копию исходных байтов собственного JSON и источник, сформированный из проверенного шаблона/UUID.

Общую проверку источника можно извлечь из B04 в приватную функцию в `inheritance.go`, используемую тремя операциями. Сначала подтвердить тесты B04; извлечение не меняет его интерфейс или приоритет ошибок. Повторная проверка при вызове B04 допустима; сложный внутренний обход валидации ради её устранения не нужен.

Парсер проверяет синтаксис, а `bytes.Clone` сохраняет числа, массивы, форматирование и буквальные строки. Побайтовое форматирование результата не становится новым продуктовым обещанием; это простой способ не потерять данные. Не выполнять маршалинг через `float64`. Разбор без запрета `null` относится только к полной замене; `null_not_allowed` B01/B02 и правила черновиков A08 остаются прежними.

Ошибки собственного JSON переиспользуют `InheritanceIssue`: код/путь/смещение парсера, `Source: content`, `Location: routerLocation`, корректный UUID. Значения, текст JSON и невалидные идентификаторы не копируются. Наличие неизвестных полей или `_xkeenUiId` в собственном JSON не запускает проекцию: они пока остаются буквальными данными.

Альтернатива «сначала собрать шаблон, затем заменить» отвергнута: ошибочная обязательная переменная и `null` неактивного шаблона блокировали бы корректную замену.

### 3. Переход возвращает кандидат, сборка вызывается отдельно

```go
type ContentActionKind string
const (
    ActivateReplacement ContentActionKind = "replace"
    ReturnToVariables ContentActionKind = "variables"
    ResetContentOverride ContentActionKind = "reset"
)

type ContentAction struct {
    Kind ContentActionKind
    Content json.RawMessage
}

func TransitionContentOverride(
    elementID string,
    templateLocation, routerLocation ElementLocation,
    current *ContentOverride,
    action ContentAction,
) (*ContentOverride, []InheritanceIssue)
```

Идентичность проверяется против явных `elementID` и владельца шаблона; полное содержимое `Element` не требуется. Существование источника обеспечивает вызывающая сторона. Сначала проверяется идентичность, затем известность прежнего режима и действия, затем только новый JSON для `replace`. Прежнее содержимое и значения не проверяются по шаблону; это позволяет возврат и сброс из неготового состояния.

| Действие | Кандидат | Проверка |
| --- | --- | --- |
| `replace` | Исходный источник, режим replacement, копия явно переданного JSON, глубокая копия прежних Values | Один корректный JSON, `null` допустим |
| `variables` | Исходный источник, режим variables, глубокая копия прежних Values, Content nil | Без сборки; отсутствие прежней записи допустимо |
| `reset` | nil — отсутствие персонального состояния | Не требует готовности шаблона; повторный сброс допустим |

`nil, nil` является успешным сбросом; nil с ошибками — отказ. Этот контракт отличается от выбора JSON, где nil без ошибок не допускается. Для `variables`/`reset` аргумент `action.Content` не используется и не проверяется. При `replace` nil, пустой буфер и пробелы дают `invalid_json`, а байты `null` валидны. Повторный `replace` обновляет JSON, сохраняя Values. Отдельное действие записи значений переменных сюда не добавляется.

Копировать карту и каждый `RawMessage`, сохраняя nil/пустые значения без нормализации. Содержимое неактивных Values может быть неготовым к B02; копирование не должно скрыто проверять, исправлять или удалять его. После возврата вызывающая сторона получает кандидат и отдельно вызывает `SelectElementContent`: `type_mismatch`, `unknown_variable` или `missing_value` не уничтожают этот кандидат.

Техническое решение: кандидат `variables` не хранит собственный JSON; повторный `replace` требует явного содержимого согласно design B03. Сохранение черновика UI остаётся отдельной возможностью и не обещается здесь. Полный сброс дополнительно удаляет Values. Отдельной команды `cancel` нет: вызывающая сторона отбрасывает кандидат, прежний снимок остаётся цел. Проверить это и независимость вложенных буферов через публичную границу.

Порядок и исключение не входят в тип: будущий агрегат заменяет только поле персонального содержимого. Сброс возвращает отсутствие содержимого, а не приказ удалить весь агрегат вместе с исключением. Поведение сброса под исключением проверяется интеграционно в B06; B05 не объявляет его реализованным.

Альтернатива «переход + обязательная успешная сборка» нарушает B03: сброс не должен откатываться из-за отсутствующего обязательного значения. Мутация входа мешает отмене правки и безопасной обработке ошибок.

### 4. Повторные переопределения проверяются отдельным списком ссылок

```go
type OverrideRef struct {
    Source ElementSource
    Position string
}

func ValidateOverrideSources(
    template, router Owner,
    overrides []OverrideRef,
) []ElementIssue
```

Это узкая проверка метаданных в `override_sources.go`, не сборка набора. Используются существующие `ElementIssue` и `OtherLocation`. Проверить виды/валидность владельцев, затем каждую запись в порядке передачи: позицию роутера, непустой UTF-8 TemplateID, UUID, совпадение шаблона, повтор UUID. Вернуть первую ошибку; у повтора `Location` — текущая позиция, `OtherLocation` — первая. Источник ошибки — `record`; допустимый UUID указывается, неверный — нет. Невалидный контекст не копируется.

Один вызов относится к одному роутеру и шаблону. После проверки TemplateID ключом повтора достаточно UUID. Пустой список допустим, но не отменяет проверку владельцев. Передаются все действующие записи, включая пустые значения и полные замены; режим вообще не участвует в идентичности. Состояние вне вызова не сохраняется.

Нет списка существующих общих элементов: проверка не обещает их наличия. Проверку явно указанного источника одного элемента выполняет выбор/переход; полный набор и разрешение ссылок относятся к B06. Альтернатива встроить список в выбор одного элемента расширяет его ответственность; отложить все повторы до B06 оставляет непроверенным сценарий, переданный B05 контрактом B03.

### 5. Архитектура и проверки

Инварианты режимов, источника, буквальности и независимости данных принадлежат `internal/configuration`. Узкий `internal/jsonvalue` остаётся синтаксическим примитивом. Прикладной слой позднее загрузит согласованные снимки и сохранит выбранный кандидат; адаптеры будут зависеть от этих контрактов. Новые сервисные интерфейсы, репозитории, внешние библиотеки и I/O не нужны для текущей задачи и не добавляются.

Тесты в `content_override_test.go` и `override_sources_test.go` используют внешний пакет `configuration_test`. Сценарии разделяются на небольшие циклы: тест публичной границы по spec, подтверждённый поведенческий Red, минимальная логика Green, рефакторинг и повторный запуск. Допустимы минимальные объявления/заглушки для компиляции. Если композиционный сценарий сразу Green благодаря B04, это явно записывается; отсутствие компиляции или запрет окружения не считаются Red.

Кроме новой дельты, обязательны существующие сценарии B03 из [основной spec](../../../specs/configuration-content-inheritance/spec.md): `Values return after switching back`, `Type change is diagnosed on return`, `Removed definition leaves a visible error`, `New required value is missing on return`, все четыре сценария полного сброса/отмены. Проверить их через новые операции, а не только напрямую через B04. Перестановку проверять как сохранность внешнего состояния при замене кандидата; алгоритм порядка B07/B08 здесь не появляется.

Безопасность данных проверять маркерами в собственном JSON, дефолтах, неактивных Values и неверных идентификаторах; исследовать всю структуру ошибки. Проверить обе стороны независимости для результатов выбора и перехода, включая массивы, карту значений и отдельные буферы. Регрессии B04 подтверждают неизменность его диагностики после извлечения общей проверки.

Связанные будущие экраны — 10/11 (режимы, возврат, сброс), 07/08 (результат/ошибки). UI этим change не меняется; макет не объявляется проверенным. При реализации UI соответствующее изменение сначала обновит и проверит эти состояния через Pencil, затем выполнит тесты и код интерфейса согласно [порядку UI](../../../../docs/design.md).

## Risks / Trade-offs

- Корневой `null` можно спутать с отсутствием записи → режим и ненулевой результат выбора различают их; отдельные тесты для nil/пустого ввода и JSON `null`.
- Возврат может потерять неактивные значения → глубокое копирование без проверки, последовательные сценарии смены определений и сброса.
- Успех синтаксиса можно принять за готовность Xray → результат называется выбранным содержимым, не конфигурацией устройства; межэлементные проверки остаются отдельными.
- Рефакторинг источника может изменить B04 → полный существующий набор тестов наследования до и после; сохранять коды, контексты и приоритет.
- B05 включает несколько границ → tasks разделены на выбор, переходы и список ссылок с отдельными проверками; не добавлять БД, исключения или редактор в эти части.

## Migration Plan

Хранимых данных B05 нет, миграция не требуется. Критерии связаны с [issue B05 #21](https://github.com/SunnyDayDev/xkeen-ui-server/issues/21). После выполнения сценариев и проверок обновить предметную документацию и статус доступного кода, синхронизировать дельту и архивировать change по workflow завершения. Основной контракт сейчас не перезаписывается. Закрытие issue и архивирование проверяются отдельно; обзорная #1 остаётся открытой. Откат до подключения хранилища — удаление новых возможностей ядра без миграции устройств.
