## Context

Мотивация и зависимости — в [proposal](proposal.md). Код содержит только `cmd/xkeen-ui-server` и `internal/server`; тесты handler используют внешний пакет `server_test`. Предметного пакета и потребителей сборки ещё нет. `go.mod` закрепляет Go 1.27.1, CI уже выполняет тесты, vet, race и сборки Linux AMD64/ARM64 без cgo.

[A05](../2026-09-08-define-variable-contract/design.md) предложил будущую полную операцию `ResolveElement`, но явно оставил её Go-интерфейс для A06. Пользователь подтвердил более узкую границу: подстановка получает готовые типизированные значения, а B01 выбирает персональное значение или дефолт. [Основная спецификация](../../../specs/configuration-variables/spec.md) сохраняет полный контракт; [дельта](specs/configuration-variables/spec.md) добавляет наблюдаемую границу подготовленной подстановки.

Design нужен для первого модуля ядра, выбора точного JSON-представления и отделения ошибок отсутствующей ссылки от будущей проверки обязательности.

## Goals / Non-Goals

**Goals:**

- Определить вызываемую и тестируемую границу до логики, без зависимости от HTTP и хранилища.
- Сохранить произвольный JSON и точные числа на входе, при обходе и на выходе.
- Сделать диагностику пригодной для будущего сборщика без передачи содержимого конфигурации в сообщения ошибок.

**Non-Goals:**

- Проектирование агрегата элемента, генератора ID, определения переменной или DTO для API/БД.
- Внедрение полной `ResolveElement`, подключение операции к server handler или публикации.
- Изменение UI, макетов или лаборатории: у задачи нет затронутых экранов и инфраструктурных адаптеров.

## Decisions

### 1. Пакет и направление зависимостей

Добавить `internal/configuration`. Он владеет инвариантами подстановки: точным поиском, сохранением JSON-типов, атомарным результатом и местом ошибок. Пакет импортирует только стандартную библиотеку; не зависит от `internal/server`, файловой системы, БД, Xray или запуска процессов.

```text
Future application use case
             |
             v
Value preparation (B01)
             |
             v
Prepared substitution (A06)
             |
             v
Full validation before publication (requires B02 and later work)
```

Схема показывает ответственности, а не окончательный порядок всех проверок: проверки B02, которым нужен исходный шаблон, выполняются до утраты его синтаксиса. Полная сборка позднее координирует эти стадии.

Функциональной границы достаточно: интерфейс репозитория, универсальный движок шаблонов и отдельный интерфейс на парсер не нужны. Альтернатива разместить подстановку в HTTP-пакете создала бы неверное направление зависимостей и мешала независимой проверке ядра.

### 2. Предлагаемый интерфейс A06

Технический контракт для тестов через внешний пакет `configuration_test`:

```go
func SubstituteValues(
    elementID string,
    template json.RawMessage,
    values map[string]json.RawMessage,
) (json.RawMessage, []Issue)
```

Это план декларации, ещё не существующий код и не внешний API. `json.RawMessage` хранит закодированное JSON-значение; тип определяется JSON, поэтому `443` и `"443"` различаются. Операция не принимает объявленный тип и не может проверить соответствие ему: это ответственность подготовки B01.

Набор содержит только готовые значения одного элемента; имена уже прошли проверку определений. В нём нет записи «объявлено, но не заполнено». Поэтому отсутствующее имя в ссылке даёт `unknown_variable`; будущая подготовка отдельно возвращает `missing_value` для незаполненного определения. Лишние относительно определений имена и их дубликаты B01 проверяет до построения map. Неиспользуемое подготовленное значение допустимо, но его JSON также разбирается. Пустая и nil map равнозначны пустому набору; пустые JSON-байты не являются отсутствием значения и дают `invalid_json`.

Входы не изменяются, выход — самостоятельный буфер. Успех возвращает JSON и пустой набор ошибок; ошибка — nil JSON и непустой набор диагностик. ID используется только для диагностики: правила его формата и уникальности относятся к A07.

Альтернативы:

- Принимать `map[string]any` от вызывающего кода — легко потерять точность чисел ещё до входа и получить произвольные Go-типы, которых нет в JSON.
- Уже сейчас принимать определения и дефолты — расширяет задачу до B01 и смешивает подстановку с выбором значений.
- Ввести собственный публичный AST — увеличивает поверхность API без потребности текущих потребителей. Внутреннее дерево остаётся деталью пакета.

### 3. Разбор JSON и точность

Предлагается небольшой внутренний рекурсивный разбор на `encoding/json.Decoder.Token` с `UseNumber`: числа сохраняются как `json.Number`, без `Float64`/`Int64`. `UseNumber` сохраняет числовое представление, а `RawMessage` представляет закодированный JSON; см. [документацию Go](https://pkg.go.dev/encoding/json#Decoder.UseNumber) и [RawMessage](https://pkg.go.dev/encoding/json#RawMessage).

При реализации перед обходом токенов проверяются UTF-8 и грамматика через `RawMessage`: это сохраняет исходные позиции синтаксических ошибок и не теряет повторные ключи. Затем для каждого объекта разбор ведёт собственный набор декодированных ключей; повтор обнаруживается до записи значения в map. Это сохраняет возможность выдать `duplicate_json_key`, включая `"a"` и `"\u0061"`. После одного корневого значения требуется конец ввода с допустимыми JSON-пробелами. Этот же разбор используется для шаблона и каждого значения.

Объекты и массивы не декодируются в структуры известных полей Xray. Пустые контейнеры создаются как пустые объекты/массивы, чтобы последующая сериализация не превращала их в null. Большие целые, длинные десятичные дроби и большие экспоненты проходят без числовых вычислений.

Обычного декодирования в `map[string]any` недостаточно для выбранных гарантий: нужны сохранение чисел и явный контроль дубликатов. Более новый JSON API стандартной библиотеки — допустимая будущая замена внутреннего парсера, но сейчас достаточно знакомой границы с явными проверками; контрактные тесты не привязываются к ней. Сторонняя библиотека не требуется.

### 4. Обход и граница B02

Обходить исходное дерево шаблона. Для строки, целиком равной корректной ссылке, искать готовое значение по полному имени и помещать его в результат. Для объектов обходить значения, для массивов — элементы в исходном порядке. Не выполнять текстовую замену в исходных байтах: она усложняет экранирование и подстановку контейнеров.

Вставленный объект, массив или строка являются данными и не запускают повторный обход подстановки. Ключи не преобразуются. Это направление реализации совместимо с A05; отдельные сценарии полного синтаксиса и однопроходности остаются в B02.

Область A06 — корректные целые ссылки и обычные константы, подготовленные значения пяти типов. Поведение частичной/невалидной ссылки, `$$`, null и невалидных определений не закрепляется как успешное поведение A06 и не покрывается тестами, требующими пропускать такие входы. Эти данные нельзя считать допустимыми для полной сборки. До B01/B02 операция доступна только как внутренний шаг и не подключается к пользовательскому вводу или публикации.

### 5. Диагностика без содержимого

Предлагаемый `Issue` содержит код, `ElementID`, `Source`, необязательное `VariableName`, необязательный `Path` и необязательный `Offset`. Для пути и позиции нужны признаки присутствия: пустой путь — корректное обозначение корня, а не отсутствие информации.

| Ошибка A06 | Источник | Место |
| --- | --- | --- |
| `invalid_json` | `template` или `value` | Байтовая позиция внутри соответствующего JSON |
| `duplicate_json_key` | `template` или `value` | JSON Pointer к повторному ключу |
| `unknown_variable` | `template` | JSON Pointer к строке-ссылке |

Для `value` указывается имя подготовленного значения. С позиции Go-парсера берётся только числовое смещение, не текст ошибки. В Go-интерфейсе использовать offset от нуля; для неожиданного конца ввода — длину буфера. Смещения исходного парсера нормализуются к этой системе. Для структурных ошибок путь формируется при обходе: `~0`, `~1`, индексы массива, пустой корневой путь.

Текст сообщения, если нужен, строится из фиксированного описания кода. Не вкладывать исходную ошибку парсера, входные байты, выбранные значения или сериализованный результат. Допустим отказ при первой найденной проблеме; порядок обхода map и количество накопленных ошибок не фиксируются тестами.

### 6. Проверки и размер работы

Каждый небольшой сценарий дельты проходит через `configuration_test`: тест → запуск с подтверждённым Red → минимальная логика → Green → рефакторинг и повторная проверка. Начальные декларации и заглушка допустимы только для запуска теста; ошибка компиляции или окружения не является Red.

Числовые проверки не декодируют ожидаемый и фактический результаты в `float64`: использовать точное сравнение чисел, например `math/big.Rat` для выбранных конечных примеров, и семантическое сравнение остального дерева. Формат JSON и порядок ключей не проверять как контракт. Неизменность входов проверять побайтово, включая успешный корневой результат и ошибку после доступной подстановки.

Текущий CI автоматически подхватит пакет через `./...`. Поскольку сервер пока его не импортирует, одна сборка `cmd/xkeen-ui-server` не проверяет кросс-компиляцию нового пакета: дополнительно собрать тестовый бинарник `internal/configuration` для Linux AMD64 и ARM64 без cgo. Это проверка компиляции, не запуска на Entware. Docker и физический роутер для чистого ядра не нужны.

При подготовке proposal команда `go` не найдена в текущем PATH. Перед Red потребуется доступный toolchain согласно [инструкции каркаса](../../../../docs/server-skeleton.md); это ограничение среды планирования, не результат теста и не разрешение менять закреплённую версию. Установка или поиск SDK не заменяет проверки поведения.

Объём ограничен одной функцией, внутренним парсером и диагностикой. Проверки сгруппированы в короткие циклы, а не один общий Red на весь механизм. Если при реализации появится необходимость полного резолвера или отдельного универсального AST, остановить расширение и пересмотреть размер задачи до такого кода.

## Risks / Trade-offs

- Частичный шаг можно принять за готовую сборку → явное имя и описание границы, отсутствие HTTP-подключения, отдельный статус A06/B01/B02 в документации.
- Преобразование чисел в машинный тип потеряет значение → сохранять `json.Number` до сериализации и проверять точные примеры независимо от реализации.
- Контроль дубликатов после создания map потеряет исходную неоднозначность → обнаруживать их при чтении ключей в каждом объекте.
- Сообщение низкоуровневого парсера может раскрыть фрагмент входа → отдавать код и числовую позицию с фиксированным текстом.
- Размер памяти растёт с деревом и выходом → не обещать ограничений по ресурсам, пока нет целевой нагрузки; лимиты пользовательского ввода определить перед внешним подключением. Существующие технические ограничения парсера сохраняются.

## Migration Plan

Миграций данных и развёртывания нет: у новой операции ещё нет потребителей. При реализации добавить пакет и тесты, обновить README, `docs/configuration-model.md` и `docs/roadmap.md` с фактической поддержкой A06 и оставшимися B01/B02; не менять согласованные правила полной сборки.

Фактические Red/Green и итоговые проверки записать в `verification.md` этого change при apply. После всех критериев сверить issue #7, синхронизировать дельту и архивировать change при завершении. Закрытие issue и архивирование проверяются отдельно; подготовка плана не является основанием для них. Откат до появления потребителей состоит в удалении добавленного пакета и соответствующем исправлении статуса документации.
