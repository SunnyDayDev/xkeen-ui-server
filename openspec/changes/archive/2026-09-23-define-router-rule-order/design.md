## Context

Мотивация и граница B07 указаны в [proposal](proposal.md); наблюдаемое поведение — в [дельте](specs/configuration-rule-order/spec.md). Сейчас SelectRouterElements в internal/configuration/selection.go принимает полный снимок и возвращает набор EffectiveElement по UUID без порядка. B06 проверяет идентичности и источники до исключений, а результат сохраняет происхождение и режим содержимого. Действующая configuration-content-inheritance отделяет наследование содержимого от порядка. Хранения порядка, публикации ревизий и кнопки «Сохранить» пока нет.

## Goals / Non-Goals

**Goals:** определить полный и видимый порядок правил по UUID, вставку и перемещение по числовому индексу, согласование с изменениями шаблона, возврат порядка и явную границу сохранения перед публикацией. Контракт должен позволить B08 реализовать доменную операцию без БД и Xray, а C05–C07 — координировать сохранение и публикацию для затронутых роутеров.

**Non-Goals:** готовые Go-сигнатуры, формат SQLite, HTTP-контракты, реализация UI, проекция _xkeenUiId, анализ межэлементных зависимостей, генерация Xray-файлов и доставка ревизий агенту. Этот change изменяет только плановые артефакты; макет, документация продукта и код должны обновляться в соответствующих задачах.

## Decisions

### 1. Полный список UUID — источник порядка

Шаблон хранит упорядоченный список общих UUID. Роутер без персонального порядка следует актуальному шаблону. Персональный полный список роутера содержит все общие UUID шаблона и все локальные UUID роутера ровно один раз, включая исключённые общие правила. Из него после проверки строится видимый список с удалением исключённых UUID. Снятие исключения возвращает правило в прежнюю позицию. Ни Xray-тег, ни JSON, ни порядок обхода карты B06 не определяют эту позицию.

Концептуальные данные:

| Область | Данные | Владелец |
| --- | --- | --- |
| Шаблон | Упорядоченный список общих UUID | Шаблон |
| Роутер | Персональный полный список общих и локальных UUID либо отсутствие персонального порядка | Роутер |
| Результат | Независимые полный и видимый списки UUID с происхождением | Доменная операция |

Разделение «персональный порядок есть / нет» нужно, чтобы обычное изменение порядка шаблона автоматически доходило до роутера по умолчанию и не отменяло сделанную человеком перестановку. Локальное правило задаёт персональный полный список. Данные содержимого и порядок остаются независимыми.

### 2. Индексы и перемещения

Индексы отсчитываются с нуля. Вставка локального UUID разрешена от 0 до текущей длины включительно. При перемещении существующий UUID сначала изымается, затем индекс применяется к укороченному списку, включая позицию в конце. Например, перенос A из A, B, C на индекс 2 даёт B, C, A. Остальные UUID сохраняют относительный порядок. Позиция не меняет происхождение, содержимое, значения, замену или исключение.

Повтор UUID, индекс вне диапазона и ссылка на отсутствующий элемент отклоняются до выдачи результата. Проверка использует полный снимок и полный список, поэтому исключённое правило не может скрыть ошибку.

### 3. Обновление шаблона по числовым позициям

Роутер без персонального порядка получает актуальную последовательность шаблона. Для персонального списка новое общее правило вставляется на тот же числовой индекс, который оно заняло в новом шаблоне, с обычным сдвигом элементов вправо. Например, шаблон A, B, C становится A, X, B, C; персональный список C, A, B становится C, X, A, B. Локальные правила участвуют в сдвиге наравне с общими.

Удалённый из шаблона общий UUID просто убирается из полного порядка. При пакетной правке сначала убираются все исчезнувшие общие UUID, затем новые вставляются по возрастанию их позиций в новом шаблоне. Так несколько новых правил сохраняют относительный порядок шаблона. Перестановка уже известных общих UUID в шаблоне не меняет персональный список. Остальные UUID сохраняют относительный порядок, кроме необходимого сдвига при вставке.

Удаление UUID из порядка не является очисткой сохранённого переопределения или исключения. B06 по-прежнему сообщает об отсутствующем источнике; кандидат с такой ошибкой нельзя публиковать как готовую ревизию. Действующий запрет на удаление входа, используемого итоговым роутингом, остаётся отдельной проверкой зависимостей.

### 4. Возврат порядка шаблона

«Вернуть порядок шаблона» заменяет последовательность общих UUID актуальной шаблонной последовательностью, занимая ими прежние слоты общих правил. Локальные UUID остаются на тех же числовых индексах и в том же относительном порядке. Для полного списка B, L, A, C и шаблона A, B, C результат — A, L, B, C. Исключённые общие UUID занимают слоты в полном списке. Сброс не трогает локальный JSON, значения, переопределения или исключения.

### 5. «Сохранить» отделяет правку от публикации

Экран редактирования держит изменения шаблона и затронутых роутеров как кандидатов с предпросмотром итогового порядка. До явного действия «Сохранить» желаемые ревизии роутеров и сигналы агентам остаются прежними. При сохранении прикладной сценарий проверяет полный порядок всех затронутых роутеров; ошибка любого из них блокирует передачу всего набора в публикацию и даёт позиционную диагностику для исправления. После успешной проверки согласованный набор передаётся сценарию публикации. Атомарность записи, конкурирующие правки, другие причины отказа и расчёт затронутых ревизий задаются C05–C07. Подтверждённое применение агентом остаётся отдельным состоянием; недоступный роутер получит актуальную желаемую ревизию после восстановления связи.

Доменное ядро отвечает за инварианты списка и безопасные ошибки. Прикладной сценарий координирует снимки и публикацию. Адаптеры хранения, UI и агента не определяют правила перестановки. B06 выбирает содержимое и происхождение по UUID; B08 должен вернуть порядок поверх этого результата, не разбирать JSON повторно.

### 6. Отображение и проверка

Новый сценарий требует обновить применимые экраны 06 и 08 в Pencil: перестановку, предварительный результат для нескольких роутеров, ошибки и явную кнопку «Сохранить» с состоянием несохранённых правок. По правилам проекта макет и его визуальная проверка предшествуют UI-коду. Продуктовые документы должны ясно отличать согласованный контракт от работающей функции.

Перед логикой B08 нужны тесты через публичную доменную границу: исходный и персональный порядок, вставка/перенос, пакетные изменения шаблона, исключение, сброс, ошибки и независимость результата. Каждый сценарий проходит подтверждённый Red, минимальный Green и Refactor с повторной проверкой. C05–C07 потребуют отдельных проверок согласованного сохранения нескольких роутеров и разграничения желаемой и применённой ревизий. Эти работы не выполняются в B07.

## Передача сценариев B08

Публичная доменная граница B08 принимает проверенный контекст владельцев, текущий список шаблона, полный снимок общих и локальных UUID, персональный список либо признак его отсутствия, исключения и требуемое действие. Она возвращает независимый полный и видимый порядки с происхождением либо безопасные ошибки без частичного результата. B06 предоставляет выбранное содержимое по UUID; B08 не зависит от БД, HTTP, агента и разбора Xray JSON. Конкретные Go-типы и разбиение функций выбираются при реализации.

| Небольшой цикл B08 | Сценарии дельты и первый тест | Минимальный Green и повторная проверка после Refactor |
| --- | --- | --- |
| Исходный порядок | Шаблон A, B, C без персонального списка; пустой результат; общий и локальный UUID в одном списке; исключённый UUID остаётся в полном порядке и исчезает из видимого | Вернуть два независимых списка; повторить тесты и проверки B06 после рефакторинга |
| Вставка и перемещение | Вставка L в начало, середину и конец; перенос общего через локальное; индекс после изъятия; отрицательный и слишком большой индексы, повторный UUID | Сдвигать только позиции; дать invalid_order_index или duplicate_order_element без мутации; повторить граничные тесты |
| Изменение шаблона | Добавление X на шаблонный индекс 1 в персональный C, A, B; сдвиг локального; удаление B; пакет X/A/Y/C; перестановка прежних общих правил при персональном порядке и без него | Сначала удалить исчезнувшие UUID, потом вставить новые по возрастанию индекса; проверить сохранение персонального порядка и действующую ошибку B06 для оставшейся ссылки |
| Возврат порядка | Шаблон A, B, C и персональный B, L, A, C; полная замена и исключение общего B | Заменить только слоты общих UUID; повторить проверку JSON, исключения и локальных позиций |
| Ошибки и независимость | Отсутствующий либо пропущенный UUID, повтор в исключённом правиле, неверный владелец, изменение результата вызывающей стороной | Отказать без частичного результата и опасных данных в диагностике; повторить весь набор и убедиться, что входы и B06-результат не изменились |

Для каждой строки порядок работы одинаков: сначала сценарий и тест через публичную границу, затем запуск с подтверждённым **поведенческим Red**, минимальная логика до **Green**, рефакторинг и повторный запуск. Сбой окружения не считается Red, а тесты, написанные после логики, не называются test-first. Фактические команды и результаты фиксируются в отчёте B08, не в B07.

## Передача хранения и публикации

| Будущая работа | Проверяемый сценарий |
| --- | --- |
| C04 | После перезапуска сохранённый полный список, локальные UUID и исключения восстановлены; отсутствие персонального списка отличается от сохранённого пустого списка при пустом шаблоне. Только отсутствие списка означает наследование будущего порядка шаблона. |
| C05 | Экран может показать кандидаты нескольких роутеров до «Сохранить» без изменения желаемых ревизий. Ошибка порядка одного кандидата блокирует передачу всего набора; C05 отдельно определяет атомарность записи, конкурентные правки и прочие ошибки публикации. |
| C06–C07 | После успешного сохранения рассчитаны затронутые ревизии каждого роутера; неизменный итог не вызывает повторного применения. Недоступный роутер получает актуальную желаемую ревизию при подключении, а статус «применено» появляется только после подтверждения агента. |

## Risks / Trade-offs

- Числовая позиция нового общего правила может оказаться неожиданной рядом с локальными правилами конкретного роутера. Предпросмотр затронутых полных и видимых списков позволяет увидеть результат до сохранения.
- Удаление общего источника может оставить сохранённое переопределение или исключение. Действующие ошибки B06 блокируют публикацию такого кандидата; очистка этих данных требует отдельного решения.
- Несколько роутеров меняются одной правкой шаблона. Проверка полного набора до передачи в C05–C07 предотвращает частичную публикацию из-за ошибки порядка; атомарность самой публикации проектируется там.
- Простота индексов означает, что положение нового правила выражается числом и может сдвинуть локальные правила. Это принятый результат для модели из двух слоёв. Предложенные ранее связи, группы и разрешение неоднозначностей не входят в контракт.

## Migration Plan

Текущих записей порядка нет, поэтому миграция данных B07 не требуется. Будущее хранение C04 должно различать отсутствие персонального порядка и сохранённый полный список; при первой загрузке без персональной записи применяется порядок шаблона. Формат записи и миграции будущей БД определяются в C04.
