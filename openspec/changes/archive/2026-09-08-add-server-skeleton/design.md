## Context

Мотивация и границы описаны в [proposal](proposal.md), поведение — в [server-lifecycle](specs/server-lifecycle/spec.md). В репозитории пока нет Go-модуля, кода сервера и тестового каркаса. Есть изолированный Entware/XKeen/Xray-стенд; его образ `xkeen-router-lab:dev` можно использовать для отдельной пробы. Рабочий Compose-проект и его volumes не нужны этой пробе.

В A01 выбран Go, SQLite без cgo и целевой сервер Entware aarch64. В A03 SQLite ещё не подключается. DDD/Clean Architecture/SOLID и TDD/BDD задают порядок разработки; предметные сущности появятся в последующих задачах. Design нужен сейчас для определения первых границ, интерфейсов и поведения остановки до написания кода.

Во время подготовки предложения `go version` завершился с `command not found`; toolchain для реализации нужно подготовить. Никаких запусков будущего сервера это предложение не подтверждает.

## Goals / Non-Goals

**Goals:** отделить CLI и обработку сигналов от проверяемого HTTP-жизненного цикла, сделать старт и завершение наблюдаемыми, дать воспроизводимые проверки локально и в Entware ARM64.

**Non-Goals:** создавать доменную модель ради каркаса, универсальный DI-контейнер, интерфейсы БД, отдельный readiness-протокол или фреймворк веб-приложения. Остальные исключения — в proposal. UI не затронут, проверка и редактирование `.pen` в этом change не требуются.

## Decisions

### 1. Стандартная библиотека и закреплённый toolchain

Предлагается Go 1.27.1 — стабильная версия в [официальном списке загрузок](https://go.dev/dl/?mode=json), проверенном при подготовке change. В `go.mod` задать модуль `github.com/SunnyDayDev/xkeen-ui-server`, языковую версию `go 1.27.0` и toolchain `go1.27.1`; проверки выполнять именно Go 1.27.1, поскольку директива toolchain сама по себе не запрещает более новый установленный Go. Добавление сторонних runtime-модулей не требуется.

Использовать `net/http`, `net`, `context`, `os/signal`, `flag` и `testing`. Альтернатива — HTTP/CLI-фреймворк; для одного маршрута и параметра он не даёт необходимого поведения сверх стандартной библиотеки. Настройки HTTP: `ReadHeaderTimeout` 5 секунд и `IdleTimeout` 30 секунд; срок graceful shutdown — отдельно 5 секунд.

### 2. Минимальные границы и интерфейсы

| Область | Контракт и ответственность | Проверка |
| --- | --- | --- |
| `cmd/xkeen-ui-server` | Composition root: разобрать аргументы, установить обработку SIGINT/SIGTERM, открыть TCP listener, сообщить его фактический адрес, вызвать сервер и отобразить результат в код завершения | Проверки parser и запуск настоящего бинарника |
| `internal/server`, HTTP handler | Конструктор возвращает `http.Handler`; реализует только HTTP-контракт из спецификации | `httptest`, статус, заголовки и JSON, включая ошибочные методы/пути |
| `internal/server`, lifecycle | Операция `Serve(ctx context.Context, listener net.Listener, handler http.Handler, shutdownTimeout time.Duration) error`; владеет переданным listener и закрывает его на любом пути выхода | Настоящий listener на loopback-порту 0; управляемые тестовые handlers |
| `scripts/run-server.sh` | Из корня проекта собрать бинарник в игнорируемый каталог `.build/`, затем выполнить `exec` с исходными аргументами; ошибка сборки прекращает запуск | Проверка wrapper и непосредственного запуска бинарника |

`Serve` возвращает `nil` после успешной остановки по отмене контекста, ошибку при неожиданном завершении обслуживания или истечении срока. Для истёкшего срока сохраняется возможность `errors.Is(err, context.DeadlineExceeded)`. Уже отменённый входной контекст приводит к закрытию переданного listener и успешному возврату без начала обслуживания. Параметр срока — точка настройки и тестирования внутреннего интерфейса, отдельного CLI-флага для него нет.

Зависимость кода направлена от `cmd` к `internal/server`; обратной зависимости нет. Здесь создаётся инфраструктурный адаптер HTTP, а не доменное ядро. В дальнейшем прикладные сценарии и ядро не будут импортировать этот пакет. Новые доменные инварианты A03 не вводит: будущие правила шаблонов, переменных и ревизий сохраняют владельцев, заданных архитектурой проекта.

Альтернатива — всё в `main`; она затрудняет тестирование остановки и вынуждает связывать тесты с сигналами процесса. Противоположная альтернатива — заранее создавать слои и пустые интерфейсы для будущих возможностей; для текущего поведения они не нужны. Стандартные `http.Handler` и `net.Listener` уже дают необходимые точки подстановки.

### 3. Параметры и наблюдаемость старта

Использовать отдельный `flag.FlagSet` с возвратом ошибок. `--listen` проверяется до bind как IP literal и числовой порт; hostnames и адрес без host не входят в этот минимальный контракт. Допускаются явные wildcard-адреса `0.0.0.0` и `[::]`, если оператор хочет сетевой доступ. По умолчанию используется loopback; hostname/DNS и переменные окружения можно спроектировать отдельно.

После успешного `net.Listen` вывести в stderr одну JSON-запись с полями `event: "listening"` и `address: <фактический host:port>`. Проверка готовности всё равно выполняется HTTP-запросом: bind и успешный ответ — разные наблюдения. Для ошибок достаточно диагностической записи в stderr; тесты не привязываются к дословному системному тексту. `--help` выводится в stdout.

CLI-коды: 0 — помощь или успешная остановка, 2 — неверные аргументы, 1 — ошибка bind/serve/shutdown. Конфигурация не включает файлы, БД, токены и product API. `/healthz` — техническая проверка процесса, не внешний API управления и не обещание его авторизации.

### 4. Остановка без потери результата

После сигнала или отмены контекста вызвать `http.Server.Shutdown` с отдельным контекстом ожидания: использовать уже отменённый контекст запуска для ожидания нельзя. Дождаться завершения `Serve` и `Shutdown`; обычный `http.ErrServerClosed` при штатной остановке нормализовать в успех. Истечение срока требует `Close` для оставшихся соединений и возврата ошибки. Не оставлять фоновую goroutine ожидать сигнал после ошибки обслуживания. Описание семантики — [Server.Shutdown](https://pkg.go.dev/net/http#Server.Shutdown) и [signal.NotifyContext](https://pkg.go.dev/os/signal#NotifyContext).

Сигналы обрабатываются на границе процесса. Тесты медленного/зависшего запроса передают собственный handler в lifecycle; они не добавляют маршруты задержки в продукт. Синхронизация каналами подтверждает, что handler уже начал работу до отмены контекста. Для проверки истечения срока задаётся короткий внутренний timeout; финальная процессная проверка использует штатную настройку. После принудительного закрытия тест освобождает handler и проверяет завершение, не оставляя зависших goroutines.

### 5. Проверки от контракта

Последовательность работы — небольшие циклы по сценариям спецификации: тесты и фактический Red, минимальная логика для Green, рефакторинг с повторным запуском. Минимальные сигнатуры/заглушки допустимы для компиляции теста до логики; отсутствие toolchain или ошибка компиляции не является Red.

| Сценарии | Уровень и существенная проверка |
| --- | --- |
| Health и ошибочные запросы | Табличные тесты handler: точный путь, GET/HEAD/POST, код, Allow и семантика JSON |
| Аргументы и помощь | Parser: default, IPv4/IPv6, порт 0, пустые/неверные параметры, help; без открытия listener |
| Успешная остановка и срок | Lifecycle на реальном TCP listener: отмена, активный запрос, принудительное закрытие, освобождение порта; управляемые handlers и короткий timeout |
| Неожиданная ошибка обслуживания | Тестовый `net.Listener` с невосстанавливаемой ошибкой Accept: ошибка возвращается и ресурсы закрыты |
| CLI и запуск | Собранный бинарник как дочерний процесс: readiness через HTTP с ограниченным ожиданием, SIGINT и SIGTERM отдельными подслучаями, exit code, повторный bind, занятый порт, неверные аргументы и help |
| Wrapper | Запуск одной командой; `exec` оставляет сервер на PID wrapper после стадии сборки; передача аргументов и exit code, остановка после готовности |

Тесты используют временные каталоги и случайные свободные порты. Занятый порт удерживается отдельным listener на протяжении проверки. Readiness проверяется повторными запросами с общим дедлайном, а не фиксированным sleep. Для проверки default-address достаточно parser плюс отдельная ручная проба при свободном порте 8080. IPv6-проба при отсутствии IPv6 отмечается как пропущенная с причиной; основной цикл не зависит от IPv6.

Базовые команды будущей проверки: `go test ./...`, `go vet ./...`, `CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build -o .build/xkeen-ui-server-linux-arm64 ./cmd/xkeen-ui-server`. Нативные тесты проверяют запускаемый нативный бинарник; кросс-сборка проверяется отдельно.

### 6. Проба Entware ограничена одним контейнером

Использовать уже существующий ARM64-образ лаборатории с переопределённым entrypoint, без запуска XKeen. Бинарник монтируется read-only; порты хосту не публикуются, рабочие volumes не подключаются. Не требуются `NET_ADMIN`, privileged или host network. Внутри контейнера последовательно проверить запуск, loopback-запрос имеющимся curl, SIGTERM с `wait`/кодом 0 и новый запуск на том же адресе. После проверки удалить временный контейнер, включая путь ошибки. Сохранить воспроизводимую команду пробы в инструкции проверки каркаса.

Это использует окружение лаборатории, но не изменяет её entrypoint, Compose-файл и Xray-тесты. Если образ ещё не собран, потребуется его документированная сборка. Нового продуктового Dockerfile в A03 нет: артефакт проверки — бинарник в Entware-образе. Альтернатива с полноценным deployment сейчас расширила бы задачу до упаковки и установки.

## Risks / Trade-offs

- Отсутствующий Go → подготовить Go 1.27.1 перед Red; факт установки не засчитывать как проверку поведения.
- Недоступный Docker/ARM64-образ → явно оставить пробу и её задачу незавершёнными; успешной кросс-сборкой её не заменять.
- Docker использует собственное ядро → результат отмечать как лабораторный; совместимость с физическим роутером и ресурсный бюджет остаются отдельной проверкой.
- `/healthz` может быть ошибочно воспринят как готовность продукта → документировать, что он проверяет только HTTP-процесс.
- Процессная проверка сигналов зависит от ОС → выполнить её на Unix-среде и повторить SIGTERM в Linux/Entware; Windows в контракт A03 не входит.
- Работа расширится за одну сессию → отделить новый объём до реализации; не исключать заданные сценарии для формального завершения A03.

## Migration Plan

Миграции данных отсутствуют. При реализации добавить файлы каркаса и инструкцию запуска, игнорировать `.build/`, обновить README, архитектуру и статус A03. Указать точные команды и результаты проверок в записи реализации; не заявлять готовность БД, API управления или установки на роутер. Для отмены локальной пробы достаточно остановить процесс и удалить её временные артефакты; конфигурация существующего стенда не меняется.
