## Context

A03 запускает сервер из `cmd/xkeen-ui-server` и передаёт listener в `internal/server.Serve`; HTTP-проверка зависит только от процесса. A01 выбрал SQLite без системной библиотеки и один экземпляр сервера с локальным файлом. [Исследование A01](../../../docs/server-stack-research.md).

## Goals / Non-Goals

- Подготовить дисковую базу и атомарно зафиксировать начальную версию до начала обслуживания.
- Оставить доменные таблицы и прикладные интерфейсы хранения задачам с первыми потребителями, C02 и C04. Надёжность при потере питания, резервное копирование и поддержка нескольких экземпляров проверяются отдельно.

## Decisions

1. **Точка сборки владеет ресурсом.** `cmd/xkeen-ui-server` открывает SQLite после разбора аргументов и до bind; после завершения HTTP закрывает базу, включая ветвь ошибки bind. В `internal/storage/sqlite` разместить открытие и миграции. `internal/server` сохраняет HTTP и остановку, `internal/configuration` остаётся без I/O. Контракт адаптера для этой задачи — открыть и подготовить диск по пути, вернуть закрываемый ресурс либо ошибку. Интерфейс репозитория появится у прикладного потребителя.
2. **Флаг принимает файловый путь.** По умолчанию `state/xkeen-ui-server.sqlite` от рабочего каталога. Сервер создаёт отсутствующий каталог `state` с правами 0700, при явно заданном пути оператор готовит родительский каталог. SQLite проверяется на возможность записи после открытия. Путь кодируется как имя файла, чтобы `?`, `#`, пробелы, `file:` и `:memory:` в имени не могли поменять режим SQLite. Файл создаётся с правами 0600 без изменения прав существующих файлов. Настройку пути можно использовать для локального volume Docker или накопителя Entware.
3. **Закреплённый драйвер `modernc.org/sqlite`.** Проверить версию из A01 и применимые исправления, зафиксировать драйвер и транзитивные модули в `go.mod` и `go.sum`. Подтвердить Linux ARM64 и AMD64 с `CGO_ENABLED=0`. Использовать стандартный `database/sql`, одно открытое соединение на экземпляр и стандартный rollback journal новых файлов для первого однопроцессного сценария. Режим журнала существующего файла при подготовке не меняется. Ограничить ожидание блокировки и использовать ранний захват блокировки записи в миграции, чтобы проверка версии и применение не могли разойтись при одновременных запусках.
4. **Первая миграция создаёт журнал версий.** Таблица хранит номера последовательно применённых миграций. Для v1 создание таблицы и запись номера образуют первую транзакцию. Для следующих версий отдельная транзакция объединяет SQL миграции и запись версии. Проверка истории происходит под той же блокировкой; обнаружение неизвестной версии, разрыва последовательности, невалидной структуры или пустого журнала, триггера на журнале либо пользовательских объектов без журнала останавливает запуск. Вариант `PRAGMA user_version` проще по объёму, но журнал позволит проверить последовательность после добавления следующих миграций. SQL принадлежит адаптеру и входит в бинарник.
5. **Проверка отката через тот же механизм.** В тесте передать миграцию с корректным SQL и последующей ошибкой, затем повторно открыть файл и прочитать прежние данные и историю. Отдельно запустить реальный бинарник и проверить ненулевой выход и stderr на файле с несовместимой историей. Команды для лаборатории используют временные файлы и синтетические данные, включая чтение после перезапуска, commit/rollback и ожидаемый отказ записи.

[Документация драйвера](https://pkg.go.dev/modernc.org/sqlite@v1.58.0), [транзакции SQLite](https://sqlite.org/lang_transaction.html), [служебные параметры SQLite](https://sqlite.org/pragma.html).

## Risks / Trade-offs

- Второй писатель → короткое ограниченное ожидание блокировки и видимая ошибка при конфликте. Один экземпляр остаётся целевой конфигурацией.
- Каталог или накопитель недоступен → показать этап открытия либо миграции и завершить запуск. Проверка использует локальную файловую систему с рабочими блокировками.
- Контейнер использует ядро хоста → записать версию окружения, размер ELF, пиковую память и время проверочных операций по описанному набору данных. Результат ограничен стендом.

## Migration Plan

При обновлении с A03 оператор запускает новый бинарник, при необходимости указывая путь на локальном постоянном накопителе. Бинарник применяет v1 до открытия порта. При ошибке транзакция откатывается, оператор устраняет причину и повторяет запуск с тем же файлом. Более старый бинарник, поддерживающий миграции, отклоняет файл с более новой версией. A03 можно запустить для восстановления HTTP-проверки при сохранённом файле базы, поскольку он с SQLite не взаимодействует.
