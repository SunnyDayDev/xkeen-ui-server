# Design

## Context

См. [proposal.md](proposal.md) и дельту `configuration-routing-dependencies`. B10 уже проверяет полный снимок правил и входов, собирает только действующее содержимое и возвращает безопасные места ссылок. B11 использует те же доменные проверки, но разрешает исходящие ссылки через активные выходы и достижимые балансировщики внутри выбранного элемента `routing`.

## Goals / Non-Goals

**Goals:**

- Дать чистую доменную границу для полного снимка одного роутера с отдельными секциями правил, выходов и `routing`, порядком правил, исключениями и отключением правил.
- Различать структурную ошибку, неразрешённую ссылку допустимого черновика и разрешённую связь; возвращать независимый результат с готовностью только области исходящих ссылок.
- Переиспользовать проверки B06/B08/B10 без изменения их публичных контрактов.

**Non-Goals:**

- Не фиксировать черновик, не публиковать ревизию и не проверять полный каталог Xray.
- Не добавлять БД, HTTP, агент или UI. Проверка макетов потребуется перед будущей реализацией UI.

## Decisions

### 1. Полный снимок и выбор действующего содержимого

Новая операция `AnalyzeOutboundDependencies` в `internal/configuration` принимает снимок одного роутера: `RouterSelectionInput` для правил, выходов и содержащей балансировщики секции `routing`; полный порядок правил; отдельные отключённые UUID правил; метаданные прочих секций. В каждой секции сначала проверяются владельцы, UUID, источники, переопределения и исключения. Объединённый набор проверяется на межсекционные повторы UUID. B08 проверяет полный порядок правил до исключений и отключений. Только затем выбираются действующие правила и выходы через общий шаг B06, не собирая содержимое скрытых правил. Элемент `routing` выбирается с теми же правилами наследования и замены; вложенные балансировщики не получают UUID.

Проверка полноты загруженного снимка и согласованности ревизии принадлежит будущему прикладному сценарию. Домен проверяет весь *переданный* набор и не объявляет его подтверждённой загрузкой. Альтернатива — передать только отфильтрованные записи в B06 — потеряла бы проверку идентичности скрытых элементов и полного порядка.

### 2. Явный граф исходящих ссылок

Действующее правило разбирается как JSON-объект. Корневые `outboundTag` и `balancerTag` проверяются по типу независимо от того, какое поле победит. Непустой `outboundTag` создаёт прямую связь; иначе непустой `balancerTag` выбирает балансировщик. Другие ключи не интерпретируются. Активные выходы индексируются по итоговому корневому `tag`, а не по UUID. Повторный активный тег — структурная неоднозначность с местами обоих выходов и действующих ссылок.

Для выбранного `routing` читается только его корневой массив `balancers`. По `tag` находятся объекты, запрошенные действующими правилами. Недостижимые объекты не создают исходящих зависимостей; повторный запрошенный `tag` даёт ошибку неоднозначности с путями обоих вложенных объектов и правила. Достижимый объект проверяет `selector` как массив строк или строку через запятую без trim; каждый префикс сопоставляется со всеми активными выходами. `fallbackTag` проверяется как прямая ссылка независимо от совпадений селектора. Нулевое число совпадений селектора даёт находку; разрешённый fallback оставляет эту причину готовой, отсутствие рабочего fallback делает её неготовой. Отсутствующий балансировщик или выход остаётся находкой черновика.

Альтернатива — искать одноимённые ключи рекурсивно — дала бы ложные связи из пользовательского JSON. Выбор первого совпавшего тега по порядку скрывал бы неоднозначность.

### 3. Места, ошибки и границы слоёв

Результат содержит полный проверенный порядок правил, упорядоченные ссылки с UUID, владельцем, позицией, относительным JSON Pointer, видом, найденными UUID выходов и статусом, а также `Ready` только для исходящих связей. Для вложенной ссылки место содержит UUID и позицию родительского `routing`; путь имеет вид `/balancers/<индекс>/selector[/<индекс>]` или `/balancers/<индекс>/fallbackTag`. Публичная диагностика не включает текст тега, сырой JSON и значения переменных. Ошибка метаданных, формы или неоднозначности возвращает `nil`-результат и `SelectionIssue`; отсутствующая цель возвращает результат с находкой и `Ready=false`. Все выходные срезы и указатели независимы от входа.

Инварианты графа принадлежат домену. Будущий прикладной сценарий собирает согласованный снимок и решает, можно ли готовить публикацию; адаптеры отображают диагностические коды. Новых портов и инфраструктурных зависимостей в B11 нет. Контракт публичной операции фиксируется тестами до логики: исходы, ошибки, отсутствие частичного результата и мутации, владельцы и пути.

## Risks / Trade-offs

- [Выбор только действующего содержимого может разойтись с B06/B10] → Переиспользовать общий шаг выбора и проверить регрессии наследования, замены, исключений и порядка.
- [Повторный тег может скрыться из-за порядка обхода map] → Обходить записи в исходном порядке, проверять конфликты явно и возвращать обе позиции.
- [Успех частичного графа можно принять за готовность Xray] → Назвать `Ready` готовностью исходящих ссылок и сохранить явную границу B12 в документации.

## Migration Plan

Сохраняемые данные и протокол не меняются. Новая чистая операция подключается будущим прикладным сценарием после появления хранения; откат не требует миграции.
