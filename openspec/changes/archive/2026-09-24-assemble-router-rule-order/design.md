## Context

См. [proposal.md](proposal.md) и [дельту](specs/configuration-rule-order/spec.md). B06 `SelectRouterElements` принимает полный снимок общих и локальных элементов, переопределений и исключений, проверяет метаданные до фильтрации и возвращает `map[UUID]EffectiveElement` только для видимых элементов. Порядок из этой map вывести нельзя. Основная [спецификация B07](../../specs/configuration-rule-order/spec.md) задаёт полный и видимый списки UUID, операции по индексу и правила изменения шаблона; хранение и публикация остаются будущими задачами.

## Goals / Non-Goals

**Goals:**

- Проверять порядок по полному снимку правил и возвращать видимую последовательность уже выбранного содержимого с происхождением.
- Разделить редактирование полного порядка, согласование с новой версией шаблона и сборку текущего результата. Отсутствие персонального списка отличать от существующего пустого списка.
- Держать инварианты UUID, индексов, исключений и независимости результата в доменном ядре, без БД и Xray.

**Non-Goals:**

- Не проектировать формат хранения персонального списка, транзакции и конкурентные правки C04–C07.
- Не добавлять HTTP, UI-код, публикацию ревизий, семантику отключения правил или проверку межэлементных ссылок.

## Decisions

### 1. Доменная граница и направление зависимостей

Публичная граница B08 в `internal/configuration` будет принимать типизированные снимки владельцев, UUID и позиций, а также существующий вход B06 для выбора содержимого. Ядро владеет проверкой полноты и уникальности порядка, индексами, согласованием шаблона и фильтрацией видимого списка. B06 остаётся единственным владельцем выбора JSON и проверки привязок. Обёртка сборки вызывает B06 один раз и упорядочивает его результат по проверенному полному списку; сырой JSON не разбирается и переменные не подставляются повторно.

Выход содержит два независимых значения: полный порядок записей с UUID и происхождением, а также видимые записи с UUID, происхождением и выбранным `json.RawMessage`. Для исключённого общего UUID в полном результате нет собранного содержимого. При любой ошибке возвращается nil результата и безопасные ошибки с владельцем/позицией и валидным UUID, когда он известен. Входы и другие результаты не мутируют. Конкретные имена Go-типов и функций определяются тестами через публичную границу.

Альтернатива — сортировать B06 map или читать Xray-теги/JSON. Она не сохраняет исключённые позиции и смешивает идентичность с содержимым, поэтому не подходит.

### 2. Полный порядок проверяется до скрытия исключений

Проверка сопоставляет полный список с полным снимком общих UUID текущего шаблона и локальных UUID роутера, включая исключённые. Каждый UUID должен встретиться ровно один раз. Используются действующие проверки корректности владельца и канонического UUID; повтор в порядке даёт `duplicate_order_element`, отсутствующий в снимке либо пропущенный из порядка UUID — `order_element_not_found`, недопустимый индекс — `invalid_order_index`. Для ошибок сохраняются позиции записи порядка и, где применимо, исходной записи. Невалидный UUID и исходный JSON не попадают в диагностику.

Отсутствующий персональный порядок означает следование текущему шаблону. Если локальное правило уже есть, ему нужна позиция в явно заданном персональном полном списке: добавление локального правила создаёт такой список. Пустой сохранённый список при пустом снимке допустим и остаётся именно заданным списком; он не превращается в отсутствие настройки. Персональный порядок с пропуском локального или общего UUID отклоняется.

Альтернатива — проверять только видимые UUID. Она теряет место исключённого правила и разрешает скрытые повторы.

### 3. Изменение и согласование порядка возвращают кандидаты

Вставка нового локального UUID использует индекс в полном списке от 0 до длины включительно. Перемещение известного UUID сначала изымает его, затем использует индекс оставшегося списка. Возврат к шаблону заменяет общие UUID в общих слотах последовательностью текущего шаблона, не сдвигая числовые слоты локальных UUID. Все действия создают новый кандидат и не меняют входной список или содержимое.

Для изменения шаблона недостаточно только нового списка: пропущенный UUID может означать как новую запись, так и повреждённый персональный порядок. Поэтому согласование получает прежний и новый полные списки шаблона и прежний валидный полный порядок роутера. Оно сначала проверяет прежний список относительно прежнего снимка, удаляет исчезнувшие общие UUID, затем вставляет новые UUID по возрастанию индекса нового шаблона. Перестановка старых общих UUID не меняет персональный порядок. Для роутера без персонального списка итог напрямую следует новому шаблону. После преобразования кандидат проверяется относительно нового полного снимка; привязки к удалённому источнику по-прежнему могут дать ошибку B06 и не очищаются автоматически.

Альтернатива — молча считать каждый отсутствующий в персональном списке UUID новым. Это скрывает испорченный сохранённый список и делает ошибки непроверяемыми.

### 4. Соединение с B06 и порядок отказа

Для сборки результата сначала выполняется B06 на том же полном снимке. Его ошибки идентичности, привязок и активного содержимого передаются без частичного результата. Затем проверяется полный порядок и строится видимая последовательность по UUID из B06; исключённые общие UUID остаются только в полном порядке. Отсутствие выбранного активного UUID считается ошибкой, а не поводом заново собрать или подменить содержимое. Никакое поле `enabled` и никакой Xray-тег не фильтруют результат B08.

Этот порядок даёт B06 ответственность за первичную проверку метаданных и содержимого, затем B08 — за порядок. При одновременных ошибках вызывающая сторона получает ошибку первой неуспешной стадии; контракт не обещает собрать все независимые ошибки сразу. При проверке только порядка без сборки содержимого доступна отдельная чистая операция над UUID.

### 5. Проверка до реализации

Тесты пишутся через публичную доменную границу по сценариям основной B07 и дельты B08: исходный/персональный/пустой список, исключения, вставка и перенос, пакетные изменения шаблона, возврат с локальными позициями, B06 содержимое и безопасные ошибки. Для каждого нового поведения сначала подтверждается поведенческий Red, затем минимальный Green и повторная проверка после рефакторинга. Существующие тесты B06 остаются регрессией. Форматы БД и HTTP в тестах не нужны.

## Risks / Trade-offs

- Числовая вставка общего правила может сдвинуть локальное; предпросмотр будущего UI должен показывать результат B07. B08 возвращает обе последовательности для такой проверки.
- Сборка B06 перед проверкой порядка может первым показать ошибку содержимого. Это сохраняет одну ответственную границу выбора содержимого; отдельная проверка UUID порядка позволит диагностировать порядок без сборки.
- Удаление общего источника оставляет переопределение или исключение. B06 продолжает выдавать `source_not_found`; B08 не удаляет персональные данные.
- Копирование списков и JSON увеличивает выделения памяти. Небольшие наборы правил и требование независимости результата оправдывают это; измерение ресурсов целевой среды остаётся будущей проверкой.

## Migration Plan

Сохранённых записей порядка пока нет, поэтому миграции B08 нет. В будущем C04 должно записывать признак отсутствия персонального порядка отдельно от сохранённого пустого списка. Откат B08 не затрагивает данные на диске.
