# Design

## Context

Мотивация и объём — в [proposal.md](proposal.md); поведение — в [дельте](specs/configuration-xray-catalog/spec.md). Issue: [B12 #34](https://github.com/SunnyDayDev/xkeen-ui-server/issues/34).

В `internal/configuration` уже есть `RouterSelectionInput` и B06, полный/видимый порядок B08, отдельные снимки B10/B11 и общий строгий разбор `internal/jsonvalue`. `Element` хранит UUID и сырой текст независимо от назначения секции. B06 возвращает словарь эффективного JSON; он не задаёт порядок массивов и не проецирует метку. B10/B11 фильтруют отключённые записи до сборки содержимого, но подтверждают только свои области ссылок. В частности, B11 не собирает `routing`, если нет достижимого балансировщика: полный каталог должен отдельно собирать все действующие секции.

Стенд закрепляет Xray 26.3.27 и содержит пять исходных файлов. Его `lab/check.sh` проверяет собственные примеры и runtime; B12 нужна отдельная проверка файлов, полученных из доменной сборки. Хранилища и сохранённых ревизий пока нет.

## Goals / Non-Goals

**Goals:** дать проверяемые контракты чистой сборки, позиции проекции и безопасных ошибок; переиспользовать текущие правила без повторной интерпретации готового содержимого; проверять точный кандидат каталога внешним Xray в изолированной среде.

**Non-Goals:** production-адаптер запуска Xray, универсальный импорт готовых конфигов, управление рабочими файлами, применение через API, транзакции, конкурентные правки, серверные маршруты и UI. B12 не выбирает формат хранилища или сообщений агента. Наличие экземпляра Xray не требуется для доменных тестов.

## Decisions

### 1. Отдельный вход каталога поверх существующей модели

Предлагаемый интерфейс: `AssembleXrayCatalog(CatalogInput) (*XrayCatalog, []CatalogIssue)` в `internal/configuration`. Новые типы описывают состав операции, не расширяя сохраняемый `Element` полями Xray или именами файлов.

`CatalogInput` содержит общих владельцев `Template`, `Router`; обязательные указатели на группы `Log`, `API`, `Inbounds`, `Outbounds`, `Routing`, `Rules`; `TemplateOrder`, `PersonalOrder`, `DisabledRules`, `DisabledInbounds`; optional `Stats`, `FakeDNS`, список дополнительных секций и `OtherShared`/`OtherLocal` для идентичностей за пределами JSON-каталога. Группа использует `RouterSelectionInput`; её владельцы должны совпадать с владельцами каталога. `nil` обязательной группы означает отсутствие и даёт `missing_catalog_section`; непустой указатель на пустую группу означает явную пустоту. Для optional-групп `nil` означает отсутствие соответствующего корневого ключа.

`CatalogSectionInput` дополнительной секции содержит её корневое имя и группу выбора целого значения. Дополнительные имена не получают имена файлов и не используются как пути файловой системы. `stats`, `fakedns` и пять базовых ключей принадлежат своим выделенным группам; повтор этих назначений через список дополнительных секций отклоняется. Пустое имя или попытка передать текстовый `exclude_ips` дают `invalid_catalog_record`. Две дополнительные секции с одинаковым корневым именем дают `duplicate_catalog_section`. Для известных дополнительных секций `dns`, `policy`, `observatory` требуется объект; неизвестная секция допускает любое корректное JSON-значение, включая буквальный `null`.

Группы `log`, `api`, настроек `routing`, `stats` и дополнительных целых секций имеют ноль или один действующий элемент. `inbounds`, `outbounds`, `rules`, `fakedns` — коллекции. Несколько сохранённых записей целой секции допустимы в переданном снимке, пока после исключений не остаётся больше одного действующего элемента; сборщик не осуществляет слияние объектов. FakeDNS выделен как коллекция для UUID отдельных пулов согласно A07.

Альтернатива — словарь готовых файлов или большой тип со всеми полями Xray. Первый теряет контекст наследования и полного набора ID, второй ограничивает неизвестный JSON. Отдельный контракт групп оставляет эти обязанности в текущем ядре.

### 2. Явные контейнеры и стабильная раскладка файлов

| Файл | Содержимое |
| --- | --- |
| `01_log.json` | `log`: выбранный объект или `{}` явно пустой группы |
| `02_api.json` | `api`, если есть действующий элемент; `stats`, если optional-группа объявлена и не скрыта; иначе `{}` |
| `03_inbounds.json` | `inbounds`: массив действующих входов, включая `[]` |
| `04_outbounds.json` | `outbounds`: массив выбранных выходов, включая `[]` |
| `05_routing.json` | `routing`: настройки секции и собранный `rules`, включая `[]` |
| `06_extra.json` | Только явно объявленные дополнительные секции и коллекция `fakedns`; файл отсутствует, если ни одного такого корневого значения нет |

Это предложенное размещение optional-секций сохраняет пять согласованных базовых файлов и добавляет единственный стабильный файл для расширений. Отдельные файлы для каждой произвольной секции усложнили бы безопасность имён и стабильность нумерации без потребности текущей задачи.

Пустая группа API означает отсутствие ключа `api` в существующем файле. Активный элемент API с JSON `{}` сохраняется как `api: {}` и может быть отвергнут Xray; сборщик не придумывает обязательный `tag`. Причина — [APIConfig.Build в Xray 26.3.27](https://github.com/XTLS/Xray-core/blob/v26.3.27/infra/conf/api.go) отклоняет пустой API-тег. Это уточнение представления пустого файла сохраняет намерение пользователя видеть все файлы даже при отсутствии настроек.

Для optional-целой секции отсутствие группы означает отсутствие ключа, объявленная пустая группа — пустой объект. Исключение последнего элемента обязательной группы оставляет пустой контейнер; для optional-группы с исключённым последним элементом ключ опускается. Явно пустая коллекция FakeDNS сохраняет `fakedns: []`. У пустого контейнера без действующего элемента нет UUID, его нельзя маркировать чужим UUID или генерировать новый.

`Routing` содержит настройки секции, `Rules` передаёт управляемый список правил. Сборщик создаёт конечное поле `rules` из этого списка. Структурная проверка входа отклоняет корневой `rules` в объекте настроек как `invalid_catalog_record` у `/rules`, сохраняя исходную запись. Остальные настройки `routing` сохраняются полностью.

Для коллекций входов, выходов и FakeDNS используется существующая последовательность `Shared`, затем `Local`, с пропуском скрытых записей. Порядок словаря B06 не используется. Только правила используют полный/видимый порядок B08 и персональные перестановки. Это сохраняет фактическую последовательность выходов, не вводя новый сценарий управления их порядком.

### 3. Единый подготовленный снимок и проверки до публикации результата

Последовательность в памяти:

```text
Complete CatalogInput
        |
        v
Group shape + all owners/UUIDs/sources/order/disable records
        |
        v
Select active content once, keep original provenance
        |
        v
Placement shape + B10/B11 dependency rules
        |
        v
Project identities + construct section containers
        |
        v
Serialize all files + map original/output locations
```

Проверки присутствия/назначения групп и всех метаданных предшествуют содержимому. Набор ID объединяется из всех групп и `OtherShared`/`OtherLocal`; переопределения не включаются как самостоятельные элементы. Полный порядок и отключения проверяются до исключения неактивных записей. После этого B04/B05/B06 выбирают действующее содержимое; отдельные отключения правил и входов применяются до его сборки. Все действующие целые секции проверяются независимо от того, читает ли их текущий анализ зависимостей.

Подготовленный внутренний снимок хранит UUID, `EffectiveElement`, принадлежность к секции и исходное место. Разрешение переменных выполняется только на исходной выбранной ветви; готовый JSON не передаётся повторно как шаблон. Для B10/B11 можно выделить package-private анализ подготовленных элементов из текущих функций: публичные анализаторы продолжают самостоятельно готовить свои входы и возвращать прежние находки/`Ready`. Общие помощники не должны менять приоритет `outboundTag`, префиксы селектора, fallback, достижимость или безопасные места диагностики. Регрессии обязательны до и после такого рефакторинга.

Блокирующие находки обеих областей преобразуются в `CatalogIssue{Code: unresolved_dependency}` с исходными UUID/местами/путями и видом зависимости; выдача файлов прекращается. Неблокирующие находки селектора с работающим fallback включаются в результат отдельно. Ошибки формы/неоднозначности сохраняют существующие коды. Проверка не вызывает `GuardInboundChange`: здесь анализируется итоговый снимок, а не создаётся кандидат выключения входа.

Альтернатива — вызывать отдельные публичные анализаторы и затем ещё раз выбирать весь JSON. Это не обязательно меняет результат, но повторяет работу и затрудняет доказательство, что зависимости проверены по тем же элементам, которые записаны. Подготовленный снимок делает эту связь явной и сохраняет места происхождения.

### 4. Проекция идентичности реализует A07

Предлагаемый чистый интерфейс `ProjectElementIdentity` принимает внешний UUID, `ElementLocation`, назначение позиции, профиль совместимости и готовый JSON; возвращает независимый JSON либо `SelectionIssue`. Точный тип входа можно выбрать при первом тесте, сохранив перечисленный контракт. Версия и назначение передаются явно, а не выводятся из знакомых ключей JSON.

Таблица поддерживаемых позиций берётся из `configuration-element-identity`: вход, выход, правило, пул FakeDNS, целые `log`, `dns`, `routing`, `policy`, `stats`, `observatory` для 26.3.27. API и неизвестные позиции не маркируются; одноимённое поле вне поддержанных позиций сохраняется как пользовательские данные. Самостоятельная проекция для другой версии возвращает независимые данные без автоматической вставки; B12 проверяется на закреплённом профиле 26.3.27.

Строгий разбор и `json.Number` сохраняют точность. Метка добавляется только в корень действительного объекта; совпадение идемпотентно, несовпадение возвращает `identity_marker_conflict` с путём `/_xkeenUiId`. Проекция не влияет на standalone-подстановку A06 и сохранение A08. UUID родительской секции `routing` не копируется в балансировщики или правила; правила получают свои метки.

Вводить новый генератор UUID или импорт связи из метки не требуется. UUID исходного элемента уже проверен в полном снимке, а standalone-проекция отдельно проверяет свой вход.

### 5. Независимый результат, сериализация и диагностика

`XrayCatalog` содержит `Files []CatalogFile` с `Name` и `Content`, `Elements []CatalogElementLocation` и безопасные неблокирующие `DependencyFindings`. У результата нет признака полного `Ready` или `Applied`. `CatalogElementLocation` связывает UUID, происхождение, источник/режим, исходное `ElementLocation`, имя файла и выходной JSON Pointer. У пустых контейнеров без элемента нет записи происхождения.

Файлы всегда идут 01–05, затем 06 при наличии. Объектные ключи сериализуются детерминированно, с отступом в два пробела и одним завершающим LF; массивы не сортируются, `json.Number` не преобразуется во float64. Точное исходное форматирование гарантируется сохранением A08, а не конечной сериализацией. Все буферы, указатели источников и места результата независимы.

`CatalogIssue` сохраняет поля `SelectionIssue`, добавляя контекст группы/вида зависимости без текста тега или значений. Отсутствие группы адресуется известной позицией входа; повтор секции — обеими позициями; невалидный UUID не копируется. Любая ошибка возвращает `nil` вместо каталога, даже если более ранние файлы уже можно было собрать в памяти.

### 6. Проверка точного каталога на границе стенда

Добавить небольшую демонстрационную точку входа `cmd/xkeen-config-demo`, которая строит безопасный снимок через доменные интерфейсы и записывает результат в явно переданный пустой каталог. Это демонстрационный адаптер, не API чтения пользовательского хранилища. Он не копирует `lab/configs`. Для проверки утраты неизвестных полей снимок содержит вложенное расширение и число `9007199254740993`; также включает переменную, полную замену, локальное правило, исключение, отключение и персональный порядок. Протоколы и адреса демонстрационные; успешный пример имеет валидный API-тег и явные службы. Отрицательный вариант отличается известным неверным протоколом активного выхода, который доменная сборка не обязана знать.

`lab/check-catalog.sh` создаёт собственный временный каталог, вызывает демонстрацию, проверяет точный набор/контрольные суммы файлов и запускает уже собранный образ с `--entrypoint /opt/sbin/xray`, монтируя кандидат только для чтения. Проверка выполняется через `xray run -test -format json -confdir <candidate>`. Перед ней фактическая версия сравнивается с 26.3.27. Не используются обычный сервис стенда, его volume, `lab/entrypoint.sh` с копированием примеров или запуск runtime. Скрипт удаляет только свои временные ресурсы; отсутствие Docker/образа или несовпадение версии считается невыполненной проверкой.

В [main/run.go Xray 26.3.27](https://github.com/XTLS/Xray-core/blob/v26.3.27/main/run.go) `-test` загружает каталог и создаёт сервер, завершаясь до `server.Start()`. Проверка подтверждает допустимость точных файлов для этой версии, но не проверяет трафик, занимаемость портов или применение. Сырой вывод Xray не становится диагностикой production-сервиса; сохранённый публичный отчёт содержит только результаты безопасных примеров.

## Risks / Trade-offs

- [Явно пустой файл можно принять за рабочую конфигурацию] → Разделить кандидат и факт проверки; пустая группа API даёт `{}`, а неполные действующие настройки остаются на проверку Xray.
- [Неизвестные поля пройдут Xray, который их игнорирует] → Отдельно проверить сохранность выходного JSON; успех Xray не доказывает поддержку неизвестного расширения.
- [Снимок B11 не читает неиспользуемый `routing`] → Всегда собирать все действующие секции каталога; полная проверка Xray получает все их поля.
- [Преобразование результата через float64 потеряет числа] → Использовать строгий существующий разбор с `json.Number` и отдельный пример большого числа.
- [Общий рефакторинг затронет B10/B11] → Извлекать только помощники подготовки/анализа, сохраняя публичные контрактные тесты и места ошибок.
- [Объём B12 превышает одну сессию] → До реализации разделить задачи на последовательные сессии: проекция, форма/сериализация, объединение выбора и зависимостей, демонстрация/стенд. #34 закрывается после всей приёмки; частичный этап не объявляется завершением B12.

## Migration Plan

Постоянной схемы данных и развёрнутого управления конфигурацией нет. Новые операции вводятся добавочно; публичные интерфейсы B01–B11 и адаптер A08 сохраняются. Реализация проходит перечисленные независимые циклы, затем регрессии, отдельную проверку каталога и обновление документации. Основная spec синхронизируется при завершении; архивирование change и закрытие #34 выполняются отдельно после всех критериев. Для возврата достаточно убрать новый вызывающий код; рабочие данные или volume стенда не мигрируют.
