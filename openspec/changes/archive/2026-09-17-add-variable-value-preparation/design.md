## Context

Мотивация и связь с B01 — в [proposal.md](proposal.md). Контракт — в [дельте](specs/configuration-variables/spec.md) и существующей [спецификации A05/A06](../../../specs/configuration-variables/spec.md).

Проверенный исходный код содержит:

- `Element` и `VariableDefinition` в `internal/configuration/element.go`. `Default == nil` означает отсутствие; семантически ошибочные, но структурно корректные определения допускаются при сохранении.
- `PrepareElement` и `RestoreElement` сохраняют состояние редактора. Обнаружение имён использует `validVariableName` из `declarations.go`; оно не выбирает значения.
- `SubstituteValues` принимает только готовый `map[string]json.RawMessage`; `Issue` уже содержит код, ID, источник, имя, путь и позицию ошибки.
- `internal/jsonvalue.Parse` проверяет UTF-8, один JSON-корень и дубликаты декодированных ключей, сохраняет числа через `json.Number`; `parseJSON` переносит ошибку в `configuration.Issue`.
- Тесты A08 явно допускают сохранение `null`, повторных определений и неверных типов. Тесты A06 проверяют точность чисел, неприкосновенность входов и безопасную диагностику.

Дизайн нужен для определения границы новой операции, представления отсутствия и приоритетов проверок до кода. Ни база данных, ни транспорт, ни UI этой границы не касаются.

## Goals / Non-Goals

**Goals:**

- Доменная операция без I/O, пригодная для будущих прикладных сценариев сборки и переопределения переменных.
- Использование уже сохранённых определений без повторного объявления и изменения модели записи.
- Независимые результаты и диагностика, которую можно передать будущему UI/API без значений переменных.

**Non-Goals:**

- Не вводить преждевременно `AssembleElement`: успех B01 не гарантирует корректность сырого шаблона.
- Не переносить доменные правила в `elementjson` или в общий синтаксический парсер: сохранение допускает черновики, которые ещё не готовы к сборке.
- Не добавлять интерфейс хранилища, сервисный объект, фреймворк валидации или новое представление определений ради одной чистой операции.

## Decisions

### 1. Отдельная операция в доменном пакете

Предлагаемый контракт Go, проверяемый тестами до логики:

```go
func PrepareValues(
    elementID string,
    definitions []VariableDefinition,
    personal map[string]json.RawMessage,
) (map[string]json.RawMessage, []Issue)
```

Успех возвращает самостоятельную ненулевую map, включая пустой набор, и пустые ошибки. Отказ возвращает `nil` и как минимум одну ошибку. ID передаётся для диагностики; проверка UUID и области уникальности остаётся у существующих операций A08. Функция не принимает `Element.Content`, не читает другие элементы и не имеет скрытого состояния.

Альтернатива — расширить `SubstituteValues` определениями — смешала бы уже проверенный контракт A06 с выбором дефолтов и усложнила независимые циклы тестирования. Альтернатива — вызывать `PrepareElement` — меняла бы набор определений и связывала сборку с сохранением. Вместо этого будущий сценарий получает сохранённые определения, вызывает `PrepareValues`, затем этапы проверки шаблона и подстановки.

Граница DDD: обязательность, типы и запрет `null` принадлежат `internal/configuration`. Направление зависимостей остаётся к ядру: будущие сценарии и адаптеры вызывают доменную операцию; ядро использует только стандартную библиотеку и существующий внутренний парсер. Тесты выполняются без БД, HTTP и роутера.

### 2. Отсутствие отличается от неверного JSON

На входе `personal` отсутствие означает только отсутствие ключа. Присутствующий ключ с `nil` или пустым `RawMessage` — пустой JSON-документ, то есть `invalid_json`. В `VariableDefinition.Default` сохраняется контракт A08: `nil` означает отсутствие дефолта, ненулевой пустой буфер — `invalid_json`. JSON `""` и строки из Unicode White_Space распознаются после успешного разбора как незаполненность для любого объявленного типа. JSON `null` всегда является данными, подлежащими запрету.

Так не смешиваются отсутствие записи, пустая строка пользователя, испорченный JSON и `null`. Автоматическое преобразование пустого буфера в отсутствие скрывало бы ошибки вызывающего кода.

### 3. Проверки определений и данных разделены

Сначала проверяются UTF-8 имени, `validVariableName`, точный тип и дубликаты в переданном списке; затем наличие определения для каждого персонального ключа. Типы принимаются строго как `string`, `number`, `boolean`, `object`, `array`. Невалидный UTF-8 имени необходимо проверять явно: обход runes сам по себе заменяет неверные байты и не гарантирует корректный исходник. Существующее обнаружение имён A08 менять ради B01 не требуется.

Для каждой объявленной переменной проверяются оба присутствующих входа, включая невыбранный дефолт:

1. Строгий разбор через существующий `parseJSON`.
2. Рекурсивный поиск `null` с путём через существующий `appendPath`.
3. Проверка незаполненности корневой строки по Unicode White_Space; вложенные строки не обрезаются.
4. Проверка корневого JSON-типа заполненного значения без преобразований.
5. Выбор заполненного персонального значения, иначе заполненного дефолта, иначе `missing_value`.

Это порядок внутри проверки конкретного JSON, а не обещание глобального порядка ошибок разных переменных. Полное накопление ошибок не требуется; первая найденная конкретная причина достаточна. Если в объекте одновременно есть `null` и несовпадение корневого типа, после успешного разбора возвращается `null_not_allowed`. Синтаксические ошибки и повторные ключи обнаруживаются раньше обхода `null`.

Запрет `null` остаётся локальным доменным обходом. Добавлять его в `jsonvalue.Parse` нельзя: это изменит сохранение A08 и контракт низкоуровневой A06. Общий запрет в сыром шаблоне будет обязан обеспечить B02.

### 4. Сохраняем числовую точность и отделяем владение буферами

Разбор используется для проверки и выбора. Итоговые `RawMessage` копируются из выбранного входа в новую map с независимым буфером для каждой записи. Это сохраняет точность чисел без конвертации в `float64` и не требует повторной сериализации. Сохранение форматирования не становится новым продуктовым требованием; контракт результата остаётся семантическим.

Определения и входные map/slice не меняются. Вложенные `${...}` и `$$` остаются данными: обход проверяет `null`, но не ищет ссылки. Возврат исходных буферов был бы дешевле, однако позволил бы последующему изменению результата менять сохранённые дефолты.

### 5. Расширяем существующую диагностику минимально

Используется `Issue`, к которому добавляется необязательное поле `ExpectedType string` для `type_mismatch`; пустая строка означает неприменимость. A06 по-прежнему возвращает прежние коды и поля. Новый тип ошибки и произвольные тексты парсера не нужны.

| Код | Source | Локализация |
| --- | --- | --- |
| `invalid_variable_name` | `definition` | `/i/name` в переданном списке определений |
| `duplicate_variable` | `definition` | `/i/name` повторного определения |
| `invalid_variable_type` | `definition` | `/i/type` |
| `unknown_variable` | `value` | переданное имя; путь не требуется |
| `missing_value` | `value` | объявленное имя; путь не требуется |
| `invalid_json` | `value` / `default` | байтовая позиция от нуля |
| `duplicate_json_key` | `value` / `default` | JSON-путь повторного ключа |
| `null_not_allowed` | `value` / `default` | JSON-путь `null`, включая пустой корневой путь |
| `type_mismatch` | `value` / `default` | пустой корневой путь и `ExpectedType` |

Здесь `i` — индекс от нуля; например, второе повторное имя имеет путь `/1/name`. Для дефолта и персонального значения путь отсчитывается от их собственного корня, а не от списка определений. `VariableName` передаётся, когда имя является корректной UTF-8 строкой, включая пустое/семантически неверное имя; для невалидного UTF-8 имя опускается, место остаётся известным по пути определения. Путь и имя могут содержать пользовательские ключи по существующему контракту A05, но диагностические поля не содержат содержимого значений, дефолтов или исходного JSON. Произвольный введённый тип не копируется; ожидаемый тип берётся только из проверенного определения.

Альтернатива с полным новым DTO ошибок не оправдана: необходимые различия уже выражаются источником и путём. Изменение пути в зависимости от источника документируется и проверяется тестами, чтобы вызывающий код не трактовал `/1/name` как путь внутри значения.

### 6. Проверки до реализации

Каждая группа [сценариев](specs/configuration-variables/spec.md) проходит отдельный цикл тест через экспортируемую операцию → подтверждённый Red → минимальный Green → рефакторинг и повтор. Для первого Red допустима только компилируемая заглушка интерфейса; ошибки окружения/импорта не считаются Red.

Состав проверок: определения и точные имена; выбор и все пять типов; строгий JSON и рекурсивный `null`; пути и отсутствие данных в ошибках; отсутствие aliasing в обе стороны; композиция с A06 на корректном целом шаблоне. Отдельная регрессия подтверждает: один и тот же черновик с `null` допустим в A08 и отклоняется подготовкой значений. Существующие тесты хранения и подстановки остаются обязательными.

UI не изменяется: экранов или состояний для правки в Pencil у B01 нет. Подключение этой операции к пользовательским сценариям остаётся будущей работой.

## Risks / Trade-offs

- Успех B01 могут принять за полную валидацию → имя и комментарий операции, документация и тест с невалидным содержимым подчёркивают отсутствие проверки шаблона; готового API публикации не добавляем.
- Формулировка старой очереди относит весь `null` к B02 → при реализации уточнить документацию и issue: данные переменных проверяет B01, сырой шаблон и синтаксис — B02. Согласованный полный запрет A05 не ослабляется.
- Повторный разбор подготовленных данных в A06 → оставить простую композицию; оптимизация общего разобранного представления не нужна без измеренного ограничения.
- Неопределённый порядок ошибок при обходе map → тестировать наличие конкретной причины на изолированных нарушениях и отсутствие результата; не обещать сортировку или все ошибки сразу.
- Дополнительное копирование буферов → принять ради независимости результата; не создавать общий кэш или разделяемое изменяемое состояние.

## Migration Plan

Изменение добавляет внутреннюю операцию и поле диагностики, не меняет сохранённый формат и не требует миграции данных. После реализации обновить описания текущего состояния и границы B01/B02, выполнить проверки, затем отдельно синхронизировать/архивировать change и закрыть выделенную issue B01 по критериям. Обзорная #1 остаётся открытой до завершения общего плана. Откат реализации не требует преобразования сохранённых элементов.
