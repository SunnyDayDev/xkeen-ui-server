## Purpose

Определить условия применения полной ревизии на роутере, сохранения рабочей конфигурации и безопасного восстановления при прерывании.

## ADDED Requirements

### Requirement: The owner establishes the managed scope and first working baseline

Агент SHALL менять только явно переданные под управление файлы после подтверждения полноты и работоспособности предыдущей локальной базы.

#### Scenario: First adoption
- **WHEN** владелец явно передал каталог под управление и действующие файлы и поведение проверены
- **THEN** агент сохраняет точные прежние имена, байты, сведения для восстановления и результаты проверки как локальную базу без вымышленного номера серверной ревизии

#### Scenario: Unmanaged or ambiguous existing configuration
- **WHEN** принадлежность файла не доказана, есть конфликт считываемого Xray файла, неожиданный тип записи или невозможно подтвердить исходное состояние
- **THEN** агент блокирует изменение, сохраняет исходные данные и запрашивает устранение причины
- **AND** посторонние данные, собственные журналы пользователя и текстовые настройки XKeen сохраняются

### Requirement: The complete candidate is checked locally before live effects

Агент SHALL проверять полный кандидат для своего сервера, устройства и профиля локальным Xray до изменения рабочих файлов и процесса.

#### Scenario: Invalid or unavailable candidate
- **WHEN** полный снимок повреждён, профиль несовместим, проверка Xray отказала либо безопасная проверяющая среда недоступна
- **THEN** агент различает ошибку кандидата и недоступность проверки, прежние файлы, процесс и рабочий трафик сохраняются

#### Scenario: Download or no desired revision
- **WHEN** D05 возвращает отсутствие желаемой ревизии, условное совпадение или успешно сохраняет приватный снимок
- **THEN** сам результат чтения не меняет рабочий каталог и не подтверждает применение

### Requirement: Durable intent precedes all live effects

Агент SHALL допускать одну изменяющую попытку на рабочую область и сохранять восстанавливаемое намерение с полной предыдущей базой до первого воздействия на диск или runtime.

#### Scenario: Failed preparation or concurrent notification
- **WHEN** сохранение кандидата, резерва или намерения не завершилось надёжно либо параллельно поступил новый сигнал
- **THEN** незавершённая подготовка не меняет рабочее состояние, вторая попытка не вмешивается в первую
- **AND** после разрешения первой попытки агент снова сверяется с актуальной желаемой ревизией

#### Scenario: Interrupted intent survives restart
- **WHEN** агент перезапускается с незавершённым намерением и получает более новую ревизию
- **THEN** он сначала разрешает прежнюю попытку по журналу и полным сохранённым данным

### Requirement: Restart application exposes a complete working generation

При замене нескольких файлов агент SHALL исключить чтение службой смешанного набора, установить точный полный каталог и проверить запущенный на нём runtime.

#### Scenario: Optional file disappears
- **WHEN** новая ревизия исключает ранее управляемый дополнительный файл
- **THEN** он отсутствует в новом действующем наборе, а его точная прежняя копия доступна для отката

#### Scenario: Startup races with replacement
- **WHEN** агент прерывается между установкой двух файлов или параллельно запрашивается автозапуск
- **THEN** штатный запуск допускается только после восстановления полного согласованного каталога

### Requirement: Hot replacement is limited to proven rule changes

Агент SHALL применять горячую замену только для совместимого изменения полного списка правил с проверяемым результатом работающего Xray.

#### Scenario: Only supported rules differ
- **WHEN** исходный и новый каталоги различаются только поддерживаемым списком правил, доступна полная замена через API и проверка результата
- **THEN** после устойчивого намерения агент заменяет правила целиком, подтверждает их и трафик в прежнем процессе, устанавливает точный файл и сверяет полный каталог

#### Scenario: Runtime restarts during hot replacement
- **WHEN** защита от параллельного рестарта утрачена или идентичность процесса меняется во время горячей операции
- **THEN** агент не подтверждает результат и восстанавливается по сохранённому намерению

#### Scenario: Restart is required
- **WHEN** меняются настройки routing вне списка правил, любой другой файл или предварительно нельзя доказать применимость горячего пути
- **THEN** агент выбирает путь рестарта до изменения runtime

### Requirement: Recovery resolves ambiguous effects conservatively

При незавершённой или неоднозначной попытке агент SHALL восстановить полную доказанную прежнюю базу и проверить её на диске и в runtime до следующего применения.

#### Scenario: API response or file durability is uncertain
- **WHEN** горячая команда могла исполниться без ответа, записи файлов частичны либо фиксация нового состояния не подтверждена
- **THEN** агент восстанавливает прежний каталог и проверяет рабочий процесс полным путём восстановления, даже если наблюдаемое поведение уже похоже на новое
- **AND** успешный откат завершает неудачную попытку без подтверждения желаемой ревизии

#### Scenario: Durable completion awaits reporting
- **WHEN** новая база надёжно подтверждена локально, но сервер ещё не получил сообщение
- **THEN** агент сохраняет результат, перед повтором подтверждает соответствие диска и runtime и передаёт тот же исход без повторного изменения рабочей службы

#### Scenario: Corrupt evidence or rollback fails
- **WHEN** журнал или резерв непригоден, обнаружена конфликтующая внешняя правка либо восстановление и проверка прежней базы не удались
- **THEN** агент сохраняет доступные доказательства, прекращает автоматическую запись и сообщает неизвестное рабочее состояние и безопасную стадию ошибки
- **AND** последнее историческое подтверждение остаётся отдельным от текущего неизвестного runtime

### Requirement: Applied requires durable disk and runtime evidence

Агент SHALL подтверждать применённую ревизию только после проверки точного полного каталога, соответствующего работающего процесса, ожидаемого трафика и надёжной записи результата.

#### Scenario: Insufficient evidence
- **WHEN** получен ответ API, успешно выполнен `-test`, обнаружен PID либо получен одиночный отказ проксируемого запроса
- **THEN** этой отдельной проверки недостаточно для статуса «применено»

#### Scenario: Application succeeded
- **WHEN** подтверждены полный диск, состояние процесса и ожидаемый результат трафика с независимым положительным контролем, а итоговая отметка записана надёжно
- **THEN** E08 может передать отдельный успешный результат с идентификатором ревизии через D06 без конфигурации, паролей и сырого вывода процесса

#### Scenario: A committed result crosses the reporting boundary only once
- **WHEN** сбой происходит после локального commit, постановки отчёта в очередь либо при потере ответа после принятия сервером
- **THEN** E08 восстанавливает передачу по постоянному идентификатору попытки с единственным назначенным курсором и неизменным телом
- **AND** уже подтверждённая передача не создаёт нового отчёта об этом же результате
