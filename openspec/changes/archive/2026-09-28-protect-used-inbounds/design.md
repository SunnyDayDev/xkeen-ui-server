# Design

## Context

См. [proposal.md](proposal.md) и [дельту](specs/configuration-routing-dependencies/spec.md). `SelectRouterElements` (B06) проверяет метаданные полного переданного набора, затем собирает содержимое всех неисключённых элементов; `SelectOrderedRouterElements` (B08) соединяет этот результат с полным и видимым порядком. Самостоятельного состояния отключения правила в этих входах нет. Поэтому прямой вызов B08 для B10 потребовал бы собрать отключённое, но неисключённое правило и мог бы вернуть `missing_value` вместо ответа о действующих ссылках. `AssembleRuleOrder` уже проверяет полный порядок без чтения JSON. В проекте пока нет хранилища, прикладного сценария изменения входа и HTTP/UI операций.

## Goals / Non-Goals

**Goals:**

- Получить чистую проверяемую границу для ссылок на входы одного роутера с полными метаданными и эффективным JSON только действующих правил.
- Разделить структурную ошибку снимка, неразрешённую ссылку в допустимом черновике и отказ конкретного действия над входом.
- Сохранить гарантии B06/B08 и возможность использовать тот же набор находок в B11 и будущих сценариях публикации.

**Non-Goals:**

- Хранить состояния отключения, менять правила B06/B08 для их существующих вызовов, фиксировать кандидат или проверять несколько роутеров атомарно.
- Разбирать ссылки на выходы и балансировщики, подтверждать валидность полного Xray-каталога или применять изменения на агенте.
- Реализовать рабочий UI; подготовленные в B09 макеты остаются проектным ориентиром.

## Decisions

### 1. Полные метаданные раньше отбора действующего содержимого

Новая доменная граница принимает полный снимок одного роутера с явной секцией каждого элемента: общие/локальные правила, входы и идентичности остальных переданных секций, порядок правил, переопределения, исключения и самостоятельное состояние отключения. Сначала существующие проверки UUID/владельцев/источников и `AssembleRuleOrder` проверяют полный набор, включая исключённые и отключённые записи. Список отключённых UUID также проверяется на существование и повторы, а не применяется по принципу последней записи.

Затем формируется отдельная проекция действующих правил: из видимого после исключений порядка пропускаются отключённые записи; только для оставшихся выбирается содержимое по B05/B06 и разбирается `inboundTag`. Отключённое правило остаётся в полном порядке, но его переменные и JSON не собираются ради этого анализа. Для уже выбранного активного содержимого повторной подстановки нет. Нужный общий внутренний шаг выбора одного элемента можно извлечь из B06 без изменения его публичной семантики; B06 по-прежнему собирает все неисключённые записи своего входа.

Альтернатива — передавать в B06 только действующие записи — теряет проверку полного набора и ломает согласование B08 по полному порядку. Альтернатива — ослабить B06 для всех потребителей — меняет принятый контракт B06 без необходимости.

### 2. Разделить анализ ссылок и проверку действия

Предполагаемая чистая граница анализа получает согласованный снимок и возвращает упорядоченные находки по действующим ссылкам входов, неразрешённым тегам и ошибкам формы либо отсутствие успешного результата при структурной ошибке. Находка содержит UUID и исходную позицию правила, относительный JSON Pointer поля, вид ссылки и, внутри домена, ключ тега для сопоставления; публичная диагностика не раскрывает сырой JSON и значения переменных. Результат анализа не называется готовой Xray-конфигурацией.

Отдельная чистая проверка выключения/удаления принимает идентичность целевого входа до действия и снимок **итоговых правил кандидата**. Целевой UUID не подменяется тегом; тег целевого входа извлекается из выбранного содержимого входа до удаления, а его активность проверяется отдельно. Если в итоговых правилах есть действующие ссылки на этот тег, проверка возвращает отказ со всеми местами ссылок и без кандидата. Когда той же правкой ссылка удалена, правило отключено или исключено, результат допускает действие. Возвращаемый кандидат и находки не разделяют изменяемые буферы с входами.

Для выключения/удаления общего входа на нескольких роутерах будущий прикладной сценарий должен собрать согласованные снимки всех затронутых устройств и потребовать успеха каждого до фиксации. B10 подтверждает только один переданный снимок; защита от конкурентной правки относится к C03–C05/C07.

Альтернатива — сравнивать ссылки только с исходными правилами — ошибочно запрещает совместную правку, уже убравшую последнюю ссылку. Альтернатива — проверять действие в UI — допускает обход через другие каналы управления.

### 3. Ограниченный разбор Xray и явные виды результата

Активное правило должно быть JSON-объектом. Только корневой `inboundTag` читается как массив строк или строка, разделённая запятыми без trim, по закреплённому контракту Xray 26.3.27 из B09. У массива путь отдельной ссылки — `/inboundTag/<индекс>`, у строки — `/inboundTag` с отдельным порядковым номером части. Вложенные одноимённые ключи, `ruleTag` и пользовательское `enabled` не меняют граф. Неверный тип поля или правила не превращается в «зависимостей нет»; ошибка формы препятствует решению о допустимости действия.

Активные входы индексируются по итоговому корневому `tag`, а не по UUID. Повтор одного тега среди активных входов даёт неоднозначность с обеими позициями. Ссылка на отсутствующий либо выключенный вход остаётся находкой «не готово» для черновика. Повторное включение такого правила не запрещает сохранение черновика, но эта находка должна блокировать будущую подготовку к применению. Содержимое отключённых входов для действующего каталога не требуется, однако полные идентичности и привязки проверяются до отбора.

Альтернатива — рекурсивный поиск ключей — создаёт ложные зависимости в произвольном JSON. Альтернатива — выбирать первый вход при повторе тега — делает результат зависимым от порядка данных.

### 4. Границы слоёв и проверка контракта

Инварианты ссылок и отказа принадлежат `internal/configuration`. Они не зависят от БД, HTTP, Xray или состояния процесса. Будущий прикладной слой координирует загрузку полного снимка и проверку перед сохранением; адаптеры переводят структурированные ошибки в сообщения канала. Контракт предполагаемых границ фиксируется тестами до логики: успешный результат содержит независимые находки/кандидат, структурная ошибка возвращает отсутствие успешного результата, отказ по действующей ссылке возвращает зависимые позиции без мутации, а неразрешённая ссылка в черновике остаётся находкой с признаком неготовности.

Сценарии B09 и дельты становятся поведенческими тестами с фактически подтверждёнными Red/Green. Отдельные регрессии проверяют, что существующие B06/B08 по-прежнему собирают свои прежние входы и сохраняют порядок/ошибки. В B10 нет инфраструктурного адаптера для интеграционной проверки. Макеты B09 уже показывают блокировку входа и неготовый черновик; перед будущим UI-кодом соответствующая задача повторно проверит экраны 04, 06, 07, 08 и 13 через MCP Pencil.

## Risks / Trade-offs

- [Разные пути выбора активного содержимого и B06 могут разойтись] → Переиспользовать общий шаг выбора одного элемента и закрепить регрессии B06/B08 на наследовании, полной замене, локальном JSON и исключении.
- [Неполный снимок может ошибочно разрешить действие] → Контракт требует полного набора секций и отдельной проверки его полноты прикладным слоем при появлении хранилища; B10 не объявляет снимок подтверждённым только по отсутствию ссылки.
- [Доменный анализ охватывает лишь явный `inboundTag`] → В B12 проверять полный каталог закреплённым Xray; не использовать успех B10 как подтверждение остальных секций.

## Migration Plan

B10 не меняет сохранённые данные и формат доставки, поэтому миграция не требуется. Новые чистые операции подключаются к будущему прикладному сценарию после появления хранения. Откат к прежнему коду удаляет только новый доменный анализ; существующие B06/B08 продолжают работать по прежнему контракту.
