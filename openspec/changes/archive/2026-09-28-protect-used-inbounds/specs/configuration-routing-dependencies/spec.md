# Spec Delta

## MODIFIED Requirements

### Requirement: Dependencies use effective element content and active rules

Анализ зависимостей SHALL использовать выбранное для конкретного роутера содержимое общих, локальных и полностью заменённых элементов после разрешения переменных, переопределений и исключений. Ссылки SHALL читаться из итогового JSON, а не из известных полей формы, сырого неактивного шаблона, UUID, `ruleTag` или положения правила. Отключение правила SHALL быть отдельным состоянием модели; пользовательское поле `enabled` внутри JSON SHALL NOT самостоятельно переключать это состояние. Исключённое и отключённое правило SHALL NOT создавать действующих зависимостей, сохраняя своё содержимое и место в полном порядке для возможного возврата. Полный набор UUID, источников и порядка SHALL проверяться до отбора действующих правил, включая отключённые и исключённые записи. Содержимое отключённого правила SHALL NOT собираться ради анализа действующих ссылок; незаполненная переменная такого правила SHALL NOT препятствовать анализу действующего роутинга. Его обычная проверка содержимого SHALL возобновляться при повторном включении.

#### Scenario: Inherited variable selects an inbound tag
- **WHEN** активное общее правило содержит `{"inboundTag":["${source}"]}`, а персональное значение `source` равно `"lan-in"`
- **THEN** действующая ссылка указывает на Xray-тег `lan-in`, а не на текст `${source}` или UUID правила

#### Scenario: Full replacement and local rule replace the dependency set
- **WHEN** правило шаблона ссылается на `old-in`, его активная полная замена ссылается на `new-in`, а локальное активное правило ссылается на `local-in`
- **THEN** действующие зависимости этих правил относятся к `new-in` и `local-in`; ссылка на `old-in` из невыбранного содержимого не учитывается

#### Scenario: Excluded or disabled rule retains data without an active edge
- **WHEN** общее правило исключено или правило отключено, а его JSON содержит `{"inboundTag":["lan-in"]}`
- **THEN** правило не удерживает `lan-in` от выключения или удаления; исключение и отключение не удаляют сохранённый JSON и UUID

#### Scenario: JSON field does not define rule state
- **WHEN** активное правило содержит пользовательское поле `"enabled":false` рядом с `"inboundTag":["lan-in"]`
- **THEN** ссылка на `lan-in` учитывается, пока отдельное состояние правила остаётся активным

#### Scenario: Disabled rule with missing value does not block active analysis
- **WHEN** отключённое общее правило содержит обязательную переменную без персонального значения и дефолта, а другое действующее правило ссылается на `lan-in`
- **THEN** анализ действующих ссылок успешно обнаруживает ссылку на `lan-in`, сохраняет отключённое правило в полном порядке и не требует собрать его неготовое содержимое

#### Scenario: Disabled rule does not hide invalid identity
- **WHEN** отключённое локальное правило повторяет UUID общего правила выбранного шаблона
- **THEN** проверка полного набора возвращает `duplicate_element_id` с обеими позициями до анализа ссылок, без успешного результата

### Requirement: Active inbound references guard inbound removal and deactivation

Выключение или удаление входа SHALL отклоняться, если действующее правило явно ссылается на его текущий `tag` через `inboundTag` в итоговом кандидате одного роутера. Проверка SHALL учитывать изменения правил, отключений и исключений того же кандидата: если последняя действующая ссылка исчезла, действие SHALL допускаться. Результат отказа SHALL перечислять зависимые правила и места ссылок, сохраняя исходное состояние. Правило без `inboundTag` SHALL NOT считаться явной зависимостью от каждого входа. После отключения либо исключения последнего ссылающегося правила вход SHALL допускать выключение или удаление. Повторное включение сохранённого правила SHALL допускаться в черновике; если его вход отсутствует или выключен, черновик SHALL получить ошибку ссылки и SHALL NOT считаться готовым к применению, пока вход не восстановлен либо ссылка не исправлена. Вывод о допустимости действия SHALL относиться только к переданному снимку одного роутера и SHALL NOT заменять проверку всех затронутых роутеров при публикации.

#### Scenario: Used inbound rejects deactivation and removal
- **WHEN** активное правило ссылается через `inboundTag` на включённый вход `lan-in`, а запрошено выключение либо удаление этого входа
- **THEN** действие отклоняется с указанием правила и пути `inboundTag`; вход и правило остаются прежними

#### Scenario: Disabled rule releases the inbound
- **WHEN** единственное правило с JSON `{"inboundTag":["lan-in"]}` отключено, а запрошено выключение либо удаление `lan-in`
- **THEN** действие допускается; JSON и UUID отключённого правила сохраняются

#### Scenario: Reenabled rule creates an incomplete draft
- **WHEN** после удаления `lan-in` пользователь снова включает сохранённое правило с JSON `{"inboundTag":["lan-in"]}`
- **THEN** включение и сохранение черновика допускаются, ошибка указывает место ссылки, а подготовка к применению отклоняется до восстановления `lan-in` либо изменения правила

#### Scenario: Rule without inboundTag has no explicit inbound edge
- **WHEN** активное правило не содержит `inboundTag`, а пользователь выключает один из входов
- **THEN** само это правило не блокирует действие как ссылка на тег выключаемого входа

#### Scenario: Same candidate removes the last reference
- **WHEN** действующее правило первоначально ссылается на `lan-in`, а один кандидат одновременно убирает эту ссылку из выбранного JSON правила и выключает либо удаляет вход `lan-in`
- **THEN** проверка итогового кандидата допускает действие над входом, не переписывая сохранённое правило автоматически

#### Scenario: Same candidate retains another active reference
- **WHEN** один кандидат убирает ссылку на `lan-in` из первого правила, но второе действующее правило продолжает ссылаться на `lan-in`, и запрошено выключение входа
- **THEN** действие отклоняется с местом ссылки второго правила и без частичного изменения кандидата
