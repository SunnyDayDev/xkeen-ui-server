## Context

Мотивация и issue — в [proposal](proposal.md); поведение — в [дельте](specs/configuration-content-inheritance/spec.md). Дизайн нужен для новой границы полного набора и разделения метаданных, исключений и содержимого.

Сейчас [identity_set.go](../../../../internal/configuration/identity_set.go) проверяет полный переданный набор UUID; его тесты уже включают коллизию с исключённым и новым общим элементом. [ValidateOverrideSources](../../../../internal/configuration/override_sources.go) проверяет ссылки и повторы, но не существование источника. [SelectElementContent](../../../../internal/configuration/content_override.go) выбирает B04 или буквальный JSON одного общего элемента. `InheritanceIssue` сохраняет диагностику переменных, `ElementIssue` умеет указывать обе позиции конфликта; ни один тип пока не объединяет эти возможности для полного набора.

Модель `Element` содержит определения переменных и описывает сохраняемый черновик. Использовать её как готовый локальный JSON с молчаливым игнорированием `Variables` нельзя. В B03 уже определены независимость исключения, отсутствие сборки исключённого содержимого и проверка всех UUID до исключения. Выбранный пользователем вариант B06 добавляет буквальную локальную ветвь. Остальные уточнения этого документа — проектные решения данного предложения, а не ранее реализованные возможности.

## Goals / Non-Goals

**Goals:** одна чистая доменная граница выбора набора из переданного снимка; переиспользование проверок A08/B05; явные типы локального содержимого и ссылок; независимый результат, пригодный для последующих стадий порядка и анализа зависимостей.

**Non-Goals:** загрузка или сохранение снимка, HTTP-контракты, смена модели `Element`/`elementjson`, формирование файлов. Список результатов не становится порядком маршрутизации. Настройки отключения не вводятся: все переданные элементы участвуют в проверке UUID, явное исключение фильтрует только общие. Полный перечень границ — в proposal.

## Decisions

### 1. Полный снимок и отдельные типы входных записей

Предлагаемая публичная операция ядра: `SelectRouterElements(input RouterSelectionInput) (*RouterSelection, []SelectionIssue)`. Вход содержит владельцев `Template` и `Router` и четыре списка:

| Список | Предлагаемая запись | Назначение |
| --- | --- | --- |
| `Shared` | `SharedElement { Element, Position }` | Текущие общие элементы; Position относится к шаблону |
| `Local` | `LocalContent { ID, Content, Position }` | Готовый `json.RawMessage` и позиция роутера, без Variables |
| `Overrides` | `LocatedContentOverride { Override, Position }` | Существующий `ContentOverride` и позиция персональной записи |
| `Exclusions` | `SharedExclusion { Source, Position }` | `ElementSource` и позиция отдельной записи исключения |

Владелец задаётся один раз для каждого контекста. Все позиции — валидные JSON Pointer по существующим правилам. В диагностике обязательного персонального значения без записи использовать позицию `/shared/<индекс во входном Shared>` в контексте роутера; с записью — позицию записи переопределения. Ошибки исходного JSON/определений/дефолтов сохраняют позицию шаблона. Этот индекс адресует переданный снимок, а не будущий порядок Xray.

Списки вместо входных map позволяют обнаружить дубликаты с обеими позициями. Независимый список исключений совместим с `ResetContentOverride`: отсутствие переопределения после сброса не стирает исключение. Альтернатива с флагом внутри `ContentOverride` потребовала бы менять уже принятый смысл успешного сброса `(nil, nil)`. Локальный `LocalContent` исключает неявное отбрасывание определений. Преобразование сохранённой модели в такой ввод в будущих адаптерах должно быть явным; B06 не добавляет автоматический конвертер.

### 2. Проверки набора до фильтрации и сборки

Порядок фаз:

```text
Complete snapshot
       |
       v
Owners, positions, UUIDs, collisions, modes, bindings
       |
       v
Shared exclusions --> omitted sources
       |
       v
Shared: B05 choice     Local: literal JSON
       |                     |
       +----------+----------+
                  v
        Independent set by UUID
```

`ValidateRouterLocalIDs` получает все общие и локальные записи, до исключений. `ValidateOverrideSources` проверяет список переопределений без расширения своего контракта. В B06 добавляются проверка наличия источника по индексу `Shared` и отдельная проверка исключений; общие узкие примитивы допустимо переиспользовать без универсального фреймворка валидации. Дубликат исключения получает `duplicate_exclusion`. Совместное наличие одного исключения и одного переопределения законно.

Любая ошибка метаданных завершает операцию до разбора JSON. Неизвестный режим относится к метаданным, даже под исключением. Ошибки независимых записей допускают возврат первой найденной; тесты не фиксируют произвольный порядок таких ошибок. Установленные приоритеты — метаданные до содержимого, другой шаблон до поиска источника — проверяются отдельно.

Отсутствующий источник даёт `source_not_found`: это отказ от сборки неконсистентного снимка, а не контракт операции удаления источника. Персональные записи не удаляются, не переносятся и не становятся локальными. Альтернатива молчаливого игнорирования скрыла бы потерю привязки. Операции удаления и смены профиля позднее должны подготовить согласованный снимок по собственным правилам.

### 3. Сборка только включённого содержимого

После метаданных исключённый общий элемент не передаётся `SelectElementContent`. Поэтому даже неготовый сохранённый JSON полной замены не блокирует остальные элементы. Сохранение/ввод JSON имеет собственную границу проверки; этот пропуск не разрешает обход правил сохранения. Снятие исключения снова включает обычную проверку активной ветви. B06 не создаёт отдельную мутацию состояния: добавление/удаление записи исключения в следующем входном снимке достаточно для чистой операции; будущий сервис сохранит изменение.

Включённые общие элементы используют B05 без копирования логики B01/B02. Для локальных вызывается существующий синтаксический парсер `parseJSON` с `Source: content`, затем `bytes.Clone`. Можно выделить узкий помощник проверки/копирования буквального JSON, общий с B05, если сохранены все его ошибки и поведение. `PrepareElement` и автообъявления не вызываются. Синтаксическая проверка разрешает `null`, а доменный запрет B01/B02 сохраняется в наследуемой ветви.

### 4. Результат и диагностика полного набора

`RouterSelection` содержит `Elements map[string]EffectiveElement`, где ключ — UUID. `EffectiveElement` содержит независимый `Content`, `Origin` (`shared`/`local`), `Location` исходного элемента, а для общего — собственную копию `Source` и `Mode`. Для локального `Source` отсутствует, `Mode` пуст: локальное происхождение не называется полной заменой. `Location` сохраняет исходную позицию и не задаёт итоговый порядок. Успех всегда возвращает ненулевой `RouterSelection`, включая инициализированный пустой map. Ошибка — nil-результат и непустой список проблем.

`SelectionIssue` объединяет существующий `Issue`, `Location`, необязательные `OtherLocation` и `DefinitionIndex`; преобразования из `ElementIssue`/`InheritanceIssue` сохраняют все применимые поля, включая DefinitionIndex, Path, Offset, VariableName и ExpectedType. Проверки контекста возвращают безопасную пустую location, невалидный UUID не включается в ошибку. Текст JSON и персональные значения не добавляются. Новые коды: `source_not_found` и `duplicate_exclusion`; остальные сохраняют значение существующих контрактов.

Результат формируется во временном наборе и отдаётся только целиком. Каждому буферу и указателю Source принадлежит собственная память. Нельзя возвращать указатель на персональную запись либо сохранять входной изменяемый JSON. Проверяются оба направления независимости и соседние элементы результата.

Map исключает обещание «локальные после общих»; такое обещание могло бы изменить смысл маршрутизации до B07/B08. Альтернатива с упорядоченным списком потребовала бы либо преждевременного решения порядка, либо неоднозначного контракта потребителя. Будущий сборщик порядка отдельно получает ID и соответствующие настройки.

### 5. Границы и проверка до реализации

Инварианты принадлежат `internal/configuration`. Будущие прикладные сценарии загружают полный снимок, вызывают ядро и фиксируют допустимое состояние в своей транзакции. HTTP/БД зависят от ядра; ядро не зависит от адаптера `elementjson`, I/O, Xray или сервера. Новые интерфейсы хранилища, универсальные репозитории и внешние библиотеки для B06 не нужны. Это сохраняет проверяемость без устройств и сборку Docker/Entware без cgo.

Тесты пишутся из сценариев дельты через предложенную публичную границу. Для каждого небольшого сценария: тест, запуск и поведенческий Red, минимальная логика Green, рефакторинг и повторная проверка. Заглушка может понадобиться для компиляции, но ошибка компиляции не засчитывается как Red. Если тест уже проходит через A08/B05, фиксируется первоначальный Green и проверяется чувствительность теста, без искусственного заявления о Red.

Приёмка включает все сценарии дельты и исходные B03 `Local elements remain independent additions`, `Shared exclusions survive repeated content selection`, атомарность и независимость. Проверки проходят нативно, с race/vet и компиляцией всех пакетов для Linux amd64/arm64 без cgo. Работающий сервер, БД и Xray для этого не требуются. До реализации будущих экранов 05/06/10/11/07/08 их изменения должны пройти Pencil по правилам UI; B06 UI не меняет, макет не объявляется проверенным.

## Risks / Trade-offs

- Неполный снимок может скрыть чужой UUID → контракт требует все элементы; полноту загрузки и транзакции будущий прикладной слой проверяет отдельно.
- Успешный пустой набор можно перепутать с ошибкой → ненулевой результат при успехе и nil при ошибке, отдельные тесты.
- Буквальное локальное содержимое отличается от шаблона с переменными → отдельный тип без определений и без неявного преобразования из `Element`.
- Исключение скрывает ошибки содержимого до восстановления → это ожидаемо; после снятия выполняется обычная проверка, данные не теряются.
- Ссылки на удалённый источник блокируют выбор → явная безопасная ошибка сохраняет настройки до будущего согласованного сценария удаления.
- Результат можно ошибочно считать готовой конфигурацией → тип и документация обозначают набор содержимого; порядок, отключение и зависимости остаются следующими стадиями.

## Migration Plan

Изменение добавляет доменную операцию без изменения сохранённого формата и публичного HTTP API; миграции данных и развёртывание не нужны. Существующие операции остаются доступными. При завершении реализации обновляются статусы документации, записываются фактические проверки, затем отдельно проверяются синхронизация/архивирование change и закрытие issue #23. Реализация выполнена по этому дизайну; фактические проверки — в [отчёте](verification.md). Дельта синхронизирована с основной спецификацией; change архивирован 2026-09-22.
