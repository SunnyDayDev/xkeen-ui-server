## Context

Мотивация и связь с [issue #6](https://github.com/SunnyDayDev/xkeen-ui-server/issues/6) приведены в [proposal](proposal.md). Действующий код содержит только HTTP-каркас; в `internal/server/handler_test.go` проверки обращаются к публичной границе пакета. Доменного пакета, хранилища элементов и API сборки нет. Существующие specs охватывают жизненный цикл сервера и лабораторию, а не переменные.

Этот документ проектирует будущую реализацию, но A05 остаётся задачей контракта. [Спецификация](specs/configuration-variables/spec.md) — согласованный контракт, не свидетельство реализованного поведения. Дизайн необходим для однозначного представления отсутствия, сохранения JSON-типов и границ будущего ядра.

## Goals / Non-Goals

**Goals:**

- Задать проверяемую границу сборки одного элемента без HTTP, БД и работающего роутера.
- Отличить отсутствующее значение, пустую строку, неверный тип и запрещённый `null`.
- Дать конкретные примеры для последовательных A06, B01 и B02 без объединения их реализации с A05.

**Non-Goals:**

- Сериализация ресурса для HTTP/БД, полный агрегат шаблона, генерация ID и правила уникальности блоков A07.
- Обработка собственного JSON при полной замене, сборка нескольких элементов, `exclude_ips` и валидация установленным Xray.
- Проектирование или реализация форм. Экраны 02, 09 и 10 позднее потребуют отражения правил заполненности в Pencil до тестов и кода UI; текущий change их не изменяет.

## Decisions

### 1. Статус решений

| Статус | Решение |
| --- | --- |
| Согласовано ранее | Точное имя в рамках элемента, точка как часть имени, пять JSON-типов, отсутствие дефолта означает обязательность |
| Согласовано в этой сессии | Только целые значения; никакой частичной интерполяции; запрет `null`; строка, пустая после `trim`, незаполнена |
| Принято при выполнении A05 | Запрет `null` охватывает все входы сборки одного элемента, включая сырой шаблон и вложенные значения: буквальное прочтение «никаких null». Это не вводит глобальный запрет для будущих несвязанных API |
| Принято при выполнении A05 | `trim` по Unicode White_Space только для определения заполненности, без изменения непустой строки; пустое персональное значение выбирает дефолт |
| Принято при выполнении A05 | Пустой строковый дефолт равен отсутствию дефолта; `false`, `0`, `{}` и `[]` заполнены; вложенные пустые строки сохраняются |
| Принято при выполнении A05 | Правила имён, `$$` для буквального `$`, один проход, неизменные ключи, значения переменных не являются шаблонами |
| Принято при выполнении A05 | Проверка всех определений, дефолтов и лишних персональных имён; отказ при повторяющихся ключах JSON; сохранение точности чисел; структурированные ошибки |

2026-09-08 подготовленный вариант принят к выполнению A05. При сверке проверены область null, заполненность, типы, синтаксис и диагностики; приведённые решения согласованы как единый контракт. Имена будущих Go-деклараций и выбор парсера остаются техническими предложениями для A06, а не утверждённым API.

### 2. Доменная граница и представление значений

Предлагаем будущий пакет `internal/configuration`, владеющий правилами переменных. Он не импортирует `internal/server`, HTTP, БД, файловую систему или Xray. Прикладной сценарий позднее загрузит элемент и значения, вызовет ядро и передаст результат публикации; инфраструктурные адаптеры преобразуют свои форматы на входе и выходе.

```text
HTTP / storage adapters
          |
          v
Application use case
          |
          v
Configuration core
  definitions + values + template --> result OR issues
```

Предлагаемый контракт операции `ResolveElement` (имя и форма Go-декларации не являются продуктовым API):

| Вход / выход | Содержание |
| --- | --- |
| Вход | Непрозрачный ID элемента для диагностики; один сырой JSON; список определений `{name, type, optional default}`; значения по именам |
| Успех | Новый JSON-результат без изменения входов |
| Ошибка | Непустой набор диагностик и отсутствие результата |

Определения передаются списком, чтобы дубликаты имён можно было обнаружить до построения индекса. Отсутствие дефолта или значения представляется отсутствием записи/явным признаком присутствия, не JSON `null` и не zero-value типа. `false` и `0` поэтому не теряются. HTTP-обёртку этой структуры и ID-модель не фиксируем.

JSON-представление должно сохранять точность чисел; декодирование всех чисел в `float64` не подходит. Конкретная реализация дерева и парсера выбирается при подготовке A06; контрактные примеры с большим целым и дробью проверяют результат независимо от выбора. Граница разбора отвечает также за повторяющиеся ключи и лишний текст после одного значения.

Альтернатива — текстовая замена перед разбором JSON — потребовала бы отдельного экранирования строк и не обеспечивает единообразную подстановку объектов и массивов. Поэтому работаем со структурой JSON; универсальные репозитории и интерфейс на каждый тип здесь не нужны.

### 3. Заполненность и дефолты

Различаем отсутствие и ошибку. Строка, пустая после `trim`, нормализуется в отсутствие на границе выбора значения независимо от объявленного типа. Это позволяет будущей форме очистить и числовую переменную. Если значение отсутствует, выбираем заполненный дефолт; если отсутствует и он, получаем `missing_value`. Заполненное значение неверного типа не маскируем дефолтом.

| Персональное значение | Дефолт | Результат |
| --- | --- | --- |
| Нет / `" \t "` | Нет / `" "` | `missing_value` |
| Нет / `" "` | `443` типа number | Число `443` |
| `"8443"` | `443` типа number | `type_mismatch` |
| `null` | Любой | `null_not_allowed` |
| `false` | `true` | `false` |
| `"  edge.example.com  "` | Нет | Исходная строка с пробелами |

Полностью обрезать непустые строки было бы проще для форм, но это меняет заданные данные. Проверка заполненности поэтому не является очисткой содержимого. Пустые вложенные строки object/array также не превращаются в отсутствие всей переменной. Сырые постоянные строки шаблона не являются значениями переменных и сохраняются.

`null` отклоняется рекурсивно во всех входах этой операции, даже в невыбранном дефолте. Альтернатива трактовать его как отсутствие смешала бы ошибочный тип и явный возврат к наследованию. Для возврата достаточно убрать запись значения или передать пустую строку.

### 4. Синтаксис без повторного вычисления

Выбрано `$$` как экранирование буквального `$` в исходных строковых значениях шаблона. Обратная косая черта уже принадлежит JSON-экранированию; второй слой с тем же символом затруднил бы чтение. Однопроходный разбор делает `$${host}` буквальным `${host}`, а `$$$$` — `$$`; повторного вычисления результата нет.

Неэкранированный `${...}` допустим только как вся исходная строка, без пробелов вокруг. Составную строку пользователь передаёт одной string-переменной или записывает как константу. Ключи объектов не обрабатываются: это сохраняет произвольные имена полей и исключает коллизии после подстановки.

Подставленное значение считается готовыми данными. Рекурсивно обходим исходный шаблон, но не ищем ссылки в уже вставленном object/array/string. Иначе ввод реквизита с `${...}` мог бы неожиданно стать зависимостью, потребовал бы обработки циклов и менял бы смысл пользовательских данных.

Принятая грамматика имён допускает точки, дефисы и Unicode-буквы, запрещая пробелы, управляющие символы и разделители `$`, `{`, `}`. Альтернатива поддерживать экранирование внутри имени значительно усложняет синтаксис без установленной потребности.

### 5. Ошибки и порядок проверок

Предлагаемый порядок: разобрать входы → проверить определения и запрет `null` → проверить присутствие/типы значений и дефолтов → разобрать ссылки исходного шаблона → собрать новый результат. Порядок обхода объектов и количество накопленных ошибок не являются пользовательским контрактом; тесты не должны зависеть от первой ошибки при нескольких независимых нарушениях.

Коды: `invalid_json`, `duplicate_json_key`, `invalid_definition`, `duplicate_variable`, `unexpected_value`, `unknown_variable`, `missing_value`, `type_mismatch`, `null_not_allowed`, `invalid_reference`, `unsupported_interpolation`.

Диагностика содержит `elementId`, `source`, при наличии `variableName`, JSON-путь с экранированием `~` как `~0` и `/` как `~1`, либо позицию синтаксической ошибки. Для корня используется пустой путь. Дефолт и персональное значение получают путь относительно своего JSON. В сообщении допустимы ожидаемый/полученный типы; исходное значение не включается. ID здесь только передаётся, его уникальность не проверяется этим контрактом.

### 6. Границы последующей разработки

| Задача | Какие сценарии контракта реализует |
| --- | --- |
| A06, issue #7 | Точный поиск и области имён, пять типов, корень/вложенность, точность чисел, неизвестная ссылка, корректность входного JSON (включая дубликаты ключей и лишний текст), сохранность результата и входов |
| B01 | Заполненность после trim, выбор дефолта, обязательность, типы и ошибки определений/значений |
| B02 | Полный запрет null, экранирование, частичная/невалидная ссылка, буквальные ключи и однопроходность |

Структурированная диагностика и отсутствие частичного результата проверяются в каждой задаче для её ошибок. Это разделение работ, а не три разных пользовательских контракта. До завершения всего набора нельзя подключать частичный сборщик к публикации конфигурации или заявлять полную поддержку capability. Перед A06 потребуется его собственный план реализации по согласованному A05; задачи кода не становятся задачами этого change.

Для каждого небольшого сценария A06/B01/B02: сначала контрактный тест через публичную границу ядра, запуск с подтверждённым Red по отсутствующему поведению, минимальная реализация для Green, рефакторинг и повторные проверки. Заглушка допустима для компиляции; ошибка среды или сборки не засчитывается как Red. Отчёт каждого будущего change должен содержать фактические результаты. В A05 проверяются только полнота и согласованность документов, JSON-примеры и OpenSpec.

## Risks / Trade-offs

- Широкая трактовка запрета `null` исключает некоторые допустимые JSON-конфигурации → область явно показана в спецификации и проверена при завершении контракта; неизвестные ненулевые поля продолжают сохраняться.
- Пустая персональная строка возвращает дефолт → это поведение явно показывается в примерах; пустую строку как конечное значение переменной выразить нельзя, но константа в шаблоне возможна.
- `$$` меняет существующие строковые константы шаблона → для двух буквальных долларов используется `$$$$`; в значениях переменных экранирование не выполняется.
- Разные парсеры могут терять точность или принимать дубликаты → контрактные примеры проверяют обе границы до подключения транспорта или хранилища.
- Подробный контракт может расширить A06 → реализацию дефолтов и оставшегося синтаксиса сохраняем в B01/B02, а не объявляем весь механизм завершённым после A06.

## Migration Plan

В рабочем сервисе миграции и развёртывания нет: переменные пока не реализованы. После ревью A05 нужно обновить исходную модель и прототип, указать результат в roadmap и повторить проверки документации. Затем отдельно завершить/архивировать change с синхронизацией основной spec и закрыть issue #6 только после всех её критериев. Архивированная spec описывает согласованный контракт, но документы должны явно сохранять статус «реализация A06/B01/B02 впереди».

Перед последующим изменением принятого контракта обновлять связанные требования и сценарии. Результаты завершения A05 фиксируются в verification.md; основной контракт не означает готовность кода A06/B01/B02.
