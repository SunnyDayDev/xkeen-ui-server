## Context

Одно локальное правило получает собственный UUID и буквальный JSON. Вставить его в полный порядок правилами B08 и атомарно сохранить порядок и локальный блок. Источник порядка сохраняется после перезапуска, происхождение видно в списке. Используются F13, B06, B08, C04.

## Decisions

F14 использует F12 текущий C04 черновик, принятый общий снимок и все UUID из B06/B08. Новое локальное правило получает UUIDv4 при явном сохранении. Вместе с локальным блоком атомарно фиксируются полный порядок и основание этого порядка с точной версией общего шаблона и полным списком его общих UUID. Предпочтительно хранить отдельное необязательное основание рядом с C04 снимком и брать его в одной writer-транзакции. Миграция сохраняет прежний nullable порядок. При унаследованном nil ранее сохранённое основание не требуется. При явном старом порядке неизвестная версия не угадывается, если нельзя подтвердить источник. Подготовку C06.1 переиспользуем после явной сверки. Конкретный шов и migration review входят в F14. Не выводить позицию скрытого или отключённого правила из визуального индекса; вставка B08 проверяет полный набор. После редактирования сформировать вид с происхождением local даже для ещё неготового чернового контента; ошибки сборки не выдают готовый результат. Pencil 06/08, локальная вставка и ошибки.

Ожидаемая реализация SQLite — nullable `router_settings.order_basis` рядом с C04. Поколение остаётся общим для любой записи этого черновика. F12/F13 сохраняют основание при правках содержимого. При первом создании черновика из активной записи копируется доказанное основание C06, если есть персональный порядок. F14, F15 и F17 передают в B08 и C06.1 основание именно используемого черновика. Для legacy без значения допустимо взять активное основание только при совпадении полного персонального порядка и локальных UUID с активной записью. При иных данных требуется явная сверка, без догадки о старой основе. C07 сохраняет работу с активными настройками и своим основанием.

В интерфейсе список показывает полный порядок с пометками источника, исключения и отключения. Точка вставки задаётся «в начало» или «после» конкретного UUID, сервер находит место уже в полном списке B08. До записи проверяется уникальность нового UUID среди всех общих и локальных элементов, затем буквальный JSON сохраняется как самостоятельное правило. Выбор точки вставки, новый JSON, порядок и основание фиксируются только вместе.

## Risks / Trade-offs

Сетевой отказ и неполное доказательство не подтверждают изменение. Места ошибок и безопасные диагностические результаты сверяются с актуальными входами на штатном сервере.
