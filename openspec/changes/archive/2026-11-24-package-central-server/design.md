## Context

Go-каркас уже поддерживает SIGTERM, миграции до listen, прямой TLS и явный web-origin. F02/F03 предоставляют защищённую команду `admin setup` и SQLite-сессии. F04 хранит собранное вложение в `internal/server/webdist/dist`.

## Decisions

1. **Образ.** Сборочная стадия использует официальный Go 1.27.1 с закреплённым manifest digest, GOTOOLCHAIN=local и CGO=0 для Linux AMD64/ARM64. Финальная стадия scratch содержит серверный бинарник, заранее подготовленный каталог состояния UID/GID 65532 и встроенные ресурсы внутри бинарника. Контекст допускает исходный код и конкретные embedded ресурсы. Node в сборке упаковки не нужен.
2. **Запуск и состояние.** ENTRYPOINT вызывает Go-процесс напрямую. Контейнер слушает 8080, документация связывает порт с loopback хоста. Именованный том на `/var/lib/xkeen-ui-server` получает подготовленный каталог `state` при первом запуске. SQLite использует существующий относительный путь и сохраняет вспомогательные файлы рядом. Закрытое тело контейнера допускает запись только в том. Привязанный каталог должен быть подготовлен с правами этого UID/GID.
3. **Доверие и Setup.** HTTPS задаётся через действующие флаги, сертификат и ключ монтируются только для чтения. Владелец выполняет встроенную локальную команду в интерактивном терминале либо передаёт отдельный читаемый файл 0600 владельца UID процесса. Применяется текущая проверка F02. В образ, сборочный контекст и окружение не попадают секреты.
4. **Границы.** Контейнер не получает Docker socket, реальные конфигурации Xray или право запускать валидатор. Публикация через существующий прикладной сервис требует отдельного доверенного валидатора там, где он настраивается. Docker-поставка не создаёт новый endpoint публикации и не меняет серверные контракты.

## Risks / Trade-offs

Минимальный контейнер работает без shell. Проверка доступности выполняется снаружи, а локальные административные команды вызывают тот же бинарник. Публичный тег и публикация артефакта зависят от отдельного решения владельца.
