## Context

A08 уже предоставляет `configuration.ValidateTemplateIDs` и `elementjson.Encode/Decode`. C01 открывает SQLite и применяет последовательные атомарные миграции. B12 принимает полный снимок шаблона и роутера, различает пустые и отсутствующие дополнительные группы и получает полный общий порядок правил.

## Goals / Non-Goals

- Хранить один черновик как целое для последующего чтения внутренним сервисом.
- Сохранить границу между редактированием и сборкой каталога. Не вводить чтение настроек устройств, смену профиля, обновление шаблона или контракты публикации.

## Decisions

1. **Форма снимка.** Непрозрачный ID шаблона следует действующему `configuration.Owner`. Черновик содержит упорядоченный список секций с уникальными непустыми UTF-8 именами. Каждая секция содержит упорядоченные элементы с отдельным булевым состоянием отключения. Явно пустая секция представлена самой секцией. Порядок элементов `rules` является общим порядком UUID, включая отключённые. Правило подготовки отсутствующих обязательных групп для B12 относится к C05. Дополнительные группы хранятся с явным признаком присутствия. В B12 отключение поддержано для правил и входов. Флаги прочих секций остаются частью черновика, а их применимость определяет будущий контракт сборки. В C02 кратность элементов, зависимости, переменные и форма результата для Xray не валидируются.
2. **Прикладной слой.** Внутренний сервис владеет операциями Create/Get и узким контрактом репозитория. Домен проверяет полный набор UUID до подготовки отдельных записей, используя `ValidateTemplateIDs` с позициями в JSON Pointer. Подготовка элементов использует правила A08, чтение не запускает автообъявление. Инфраструктурный адаптер кодирует и восстанавливает элементы через `elementjson`; валидировать экземпляры доменных данных без БД по-прежнему можно. Потребитель сам передаёт стабильный ID. Придумывать ограничения формата ID шаблона, кроме уже используемых Owner, для C02 не требуется.
3. **Формат SQLite.** `templates` содержит стабильный текстовый первичный ключ с точным сравнением и один снимок секций в сериализованной записи. Снимок объединяет секции и элементы одной атомарной SQL-вставкой. Сериализация существующего формата A08 сохраняет исходный JSON как текст внутри записи элемента. Поэлементный поиск текущему потребителю не нужен, поэтому отдельные таблицы секций и элементов увеличили бы объём миграции. Чтение выбирает одну строку и возвращает снимок целиком либо безопасную ошибку.
4. **Соседние операции.** C03 добавит условную замену по версии для той же строки отдельной миграцией или откроет собственное поле версии согласно своему контракту. C04 может хранить выбранный ID без внешнего ключа или автоматического исправления персональных ссылок. Сценарий проверки связей с актуальным шаблоном относится к сборке и публикации. Поля будущей карточки шаблона, в том числе отображаемое имя, вводятся соответствующей задаче интерфейса или управления.

## Risks / Trade-offs

- Полный снимок читается и пишется целиком. Это соответствует операциям C02 и сохраняет контекст полного набора, но для дополнительных запросов может потребоваться отдельное представление.
- Ошибки декодирования вложенной записи должны сохранять безопасную позицию и код. Сырой JSON, дефолты и невалидные идентификаторы не логируются.

## Migration Plan

Добавить собственную миграцию следующим свободным номером после актуального main. Миграция создаёт `templates` через механизм C01; существующий журнал и уже применённые миграции остаются в силе. Проверить обновление существующего файла C01 и создание нового файла. Откат бинарника до версии, не поддерживающей новую схему, следует действующему контракту C01.
