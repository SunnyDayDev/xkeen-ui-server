## Context

См. [proposal.md](proposal.md). В проекте пока отсутствуют сервер, агент и сборки. Подтверждены Entware bootstrap в `/opt`, загрузка Xray через `-confdir` и зависимость XKeen от хуков KeeneticOS. Доступен Docker с Linux ARM64.

## Goals / Non-Goals

**Goals:** запуск настоящих бинарников и наблюдаемая проверка трафика при смене правил, дискового состояния и процесса.

**Non-Goals:** эмуляция KeeneticOS, полноценный агент, центральный сервис, прозрачная маршрутизация всей сети и поддержка всех архитектур.

## Decisions

- Образ на минимальной Debian с Entware/opkg и BusyBox в `/opt`. Это даёт привычный пакетный слой роутера без зависимости на полную прошивку. Поддержка сборки ARM64 и AMD64; результат теста утверждается только для фактически запущенной архитектуры.
- Закрепить ревизию XKeen и релиз Xray; записать версии установленных Entware-пакетов. Entware feed изменяемый, поэтому не обещать побитовую воспроизводимость будущей сборки.
- Два явных режима запуска в одной среде: проба XKeen и Xray напрямую. Ошибка XKeen не должна маскироваться автоматической успешной подменой процесса.
- Эксперимент подтвердил запуск XKeen в режиме `Other` с SOCKS и доступным Xray API. Поэтому длительный режим по умолчанию использует XKeen, а `LAB_RUNTIME=xray` выбирает прямой запуск. Прозрачная маршрутизация и API прошивки в этом результате не подтверждены.
- Конфиги API, inbound, outbound и routing хранятся отдельными JSON-объектами с корневыми ключами Xray в `/opt/etc/xray/configs`. Каталог конфигов сохраняется в отдельном Docker volume.
- API слушает loopback контейнера. SOCKS и локальная HTTP-мишень позволяют проверить allow/block без внешнего прокси, реальных ключей и чужих сетей.
- Полная конфигурация кандидата проверяется `xray run -test -confdir ...`. Затем RoutingService заменяет правила; тест проверяет процесс и новый запрос; файл заменяется rename в том же каталоге; рестарт перечитывает его. Этот эксперимент не является реализацией транзакционного применения агента.
- XKeen запускается только внутри отдельного контейнера; дополнительные сетевые права, если потребуются, ограничены его network namespace. Host network и privileged не используются.

## Risks / Trade-offs

- XKeen требует компонентов прошивки → записать конкретные ошибки и перейти к разрешённому Xray fallback.
- Разная семантика API в релизах → закрепить релиз и проверить замену трафиком, а не только кодом ответа.
- Успешный тест Xray не доказывает совместимость firewall → явно вынести `exclude_ips` и netfilter-хуки за пределы Xray-проверки.
- Изменяемые публичные feeds → сохранить manifest пакетов и контрольные суммы полученных артефактов.

## Migration Plan

Стенд запускается отдельным Compose-проектом. Остановка удаляет его контейнеры и сеть; удаление volume выполняется отдельной явно описанной командой. Миграций пользовательских данных нет.
