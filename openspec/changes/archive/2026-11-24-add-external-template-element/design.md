## Decisions

1. `POST /api/v1/templates/item/elements?templateId=<exact>` принимает один строгий JSON-объект со строками `section`, `elementId`, `source`. ID нового элемента выбирает клиент. Допускается канонический UUIDv4 C02. Действуют допуск F20, проверка источника F19, ограничение 8 МиБ и один сильный `If-Match` F21. Ответ на изменение без ETag равен 428, на прошедший разбор устаревший ETag — 412.
2. Условное чтение и запись переиспользуют F21/F22. Для пустого шаблона применить F07, для остальных — #159. Коллизия UUID проверяется по всем секциям. Для повторного UUID или занятой однократной секции вернуть 409 с безопасным кодом. Некорректный внешний запрос даёт 400, некорректный JSON элемента — 422. Применяется подготовка A08 с сохранением точного текста и объявлением новых переменных. XKeen `exclude_ips` использует собственный ресурс.
3. SQLite writer перечитывает текущий permit F20 и выполняет C03 CAS в одной транзакции. Переподключение к роутеру, принятый снимок и желаемые ревизии в этой операции не участвуют.
4. Ответ `201` содержит полное сохранённое представление, новый ETag и `Content-Location` на точный путь F21. После потери ответа клиент сверяет выбранный UUID и текст через F21, затем решает, нужно ли повторять операцию. Текущая совпадающая запись сама по себе не подтверждает, кто её создал.

## Verification

Самостоятельный HTTPS-клиент создаёт пустой шаблон по #175, добавляет первый и второй элементы, читает точные строки и проверяет новый ETag. В отдельной проверке допуска конкурируют запись F22 и добавление, один запрос использует старый permit после отзыва, другой передаёт UUID из соседней секции. Артефакты должны показать, что после отказов версия и содержимое остались прежними.
