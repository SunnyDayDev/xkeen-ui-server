## Context

Мотивация и трекер — в [proposal.md](proposal.md); наблюдаемый контракт — в [дельте](specs/configuration-variables/spec.md) и [основной спецификации](../../../specs/configuration-variables/spec.md).

Исследованное ядро уже содержит `PrepareValues` с независимыми буферами результата и проверкой всех определений/дефолтов, `SubstituteValues` с обходом JSON-дерева, `validVariableName`, `nullPath` и диагностику `Issue`. Текущая подстановка распознаёт только префикс `${` и суффикс `}`; полноценного разбора строк нет. `internal/jsonvalue.Parse` проверяет UTF-8, один корень и декодированные дубликаты ключей, сохраняя числа через `json.Number`.

`PrepareElement`/`RestoreElement` и `elementjson` сохраняют черновики, включая семантически неверные ссылки и `null`. Обнаружение объявлений при сохранении уже принимает только корректные целые ссылки и игнорирует ключи/дефолты. Тесты A06/B01/A08 проверяют эти отдельные контракты; UI и I/O к рассматриваемым операциям не подключены.

Design нужен для выбора единой границы, места разбора строк и сохранения различия между исходным шаблоном и подставленными данными. Решения ниже — план реализации этого change.

## Goals / Non-Goals

**Goals:**

- Завершить разрешение переменных через одну чистую операцию с наблюдаемыми результатами и существующей диагностикой.
- Переиспользовать подготовку значений и обход подстановки без второго независимого языка шаблонов.
- Сохранить направление зависимостей к ядру и возможность тестировать всё без хранилища, сервера или роутера.

**Non-Goals:**

- Не связывать сборку с сохранением, автообъявлением, проверкой UUID или проекцией `_xkeenUiId`.
- Не вводить промежуточный публичный AST, сервисный объект, интерфейсы без внешней границы или отдельный фреймворк валидации.
- Не считать разрешение переменных проверкой схемы Xray или конфигурации устройства. UI и макеты не меняются.

## Decisions

### 1. Единая операция поверх существующих шагов

Планируемая граница в `internal/configuration/assemble.go`:

```go
func AssembleElement(
    elementID string,
    template json.RawMessage,
    definitions []VariableDefinition,
    personal map[string]json.RawMessage,
) (json.RawMessage, []Issue)
```

Операция вызывает `PrepareValues`, останавливается при ошибке, затем передаёт выбранный набор в дополненную `SubstituteValues`. Успех возвращает новый ненулевой JSON-буфер и отсутствие ошибок; отказ — `nil` и как минимум одну диагностику. ID является непрозрачным контекстом, как в B01/A06. Вызывающая сторона может передать `Element.ID`, `json.RawMessage(Element.Content)` и `Element.Variables`, но операция не вызывает подготовку сохранения и не добавляет определения.

Сигнатуры `PrepareValues` и `SubstituteValues` сохраняются. Полная граница проверяет все входы; низкоуровневая подстановка по-прежнему принимает подготовленные значения и не выбирает дефолты, не проверяет обязательность или определения. Новый запрет `null` в этом шаге относится к сырому шаблону; гарантия отсутствия `null` в данных переменных обеспечивается B01. Существующая строгая JSON-проверка всех переданных подготовленных значений сохраняется. Для непрошедших B01 данных нельзя обещать полную валидацию по одному успеху `SubstituteValues`.

Это завершает ранее отложенную границу A05. Расширять подстановку списком определений означало бы смешать её ответственность с уже готовой B01. Оставлять только разрозненные шаги потребовало бы от каждого будущего потребителя заново собирать обязательный набор проверок.

### 2. Доменный разбор исходных строк за один проход

Заменить проверку префикса/суффикса в `substitute.go` внутренним разбором декодированной строки; при необходимости выделить его в `reference.go`. Разбор отличает буквальную строку, целую ссылку и ошибку. Он не выполняет поиск значения до классификации всей строки.

- `$$` потребляет пару и добавляет буквальный `$`; полученный символ не сканируется повторно.
- `${` открывает ссылку до `}`. Отсутствие закрытия или нарушение `validVariableName` даёт `invalid_reference`.
- Одиночный `$`, за которым нет `{`, и прочие символы являются буквальным содержимым.
- Единственная корректная ссылка заменяется значением только если занимает всю исходную строку. Любое дополнительное содержимое, включая экранированный доллар, означает `unsupported_interpolation`.
- Для целой корректной ссылки поиск выполняется по точному имени; отсутствие имени даёт `unknown_variable`.

Сканер может остановиться на некорректной ссылке. При нескольких причинах спецификация не закрепляет общий порядок ошибок. При диагностике интерполяции имя возвращается только для одной корректной ссылки без других ошибок ссылки; для нескольких ссылок либо некорректного имени оно отсутствует.

Примеры различий: `$${host}` — буквальное `${host}`; `$$${host}` — доллар плюс настоящая ссылка и ошибка интерполяции; `$$$${host}` — буквальное `$${host}`. `$${host` допустимо как буквальная строка, поскольку открывающий доллар экранирован. JSON-экранирование декодируется общим парсером раньше этих правил.

Альтернатива с последовательными текстовыми заменами может повторно распознать результат экранирования и изменить пользовательские данные. Набор независимых регулярных выражений осложняет сочетания ссылок и экранирования. Небольшой однопроходный разбор прямо отражает контракт.

### 3. Исходное дерево и данные остаются раздельными

В `SubstituteValues` после строгого разбора шаблона проверить `nullPath(tree, "")` и вернуть `Issue` с источником `template` при найденном `null`. Затем сохранить существующие строгий разбор подготовленного набора и обход шаблона. `nullPath` переиспользуется внутри доменного пакета; общий JSON-парсер остаётся синтаксическим.

Обход посещает только значения исходных объектов/массивов. Ключи не обрабатываются. При ссылке возвращается уже разобранное значение из подготовленного набора без рекурсивного запуска сканера над заменой. После `$$` возвращается буквальная строка без повторной обработки. Заключительного сканирования результата на `${...}` нет: эти последовательности могут законно происходить из данных или экранирования.

Сборка сохраняет `json.Number` и сериализует результат один раз. Повторный синтаксический разбор выбранных значений после B01 остаётся существующей ценой композиции; оптимизация с общим AST не требуется без измеренной проблемы. Входы никогда не изменяются, успешный результат сериализуется в самостоятельный буфер.

Нельзя переносить запрет `null` в `jsonvalue.Parse`: это ужесточило бы хранение черновиков. Нельзя проверять шаблон только после подстановки: исчезло бы различие между исходной строкой и буквальными данными переменной.

### 4. Используем существующую диагностику без нового формата

`Issue` остаётся общим результатом для всех шагов. Новые случаи используют `invalid_reference`, `unsupported_interpolation` и `null_not_allowed`; `unknown_variable`, `invalid_json` и `duplicate_json_key` сохраняются. Для корректно разобранной строки путь указывает на строковое значение, а не на байт внутри него; `Offset` нужен для синтаксически неразбираемого JSON и отсчитывается от нуля.

Новые ошибки шаблона содержат ID и `Source: "template"`. `VariableName` устанавливается для неизвестной целой ссылки и единственной корректной ссылки при интерполяции; в остальных случаях остаётся `nil`. `ExpectedType` остаётся только у `type_mismatch`. Данные и фрагменты ошибочных ссылок не сохраняются в диагностике. Пустой JSON Pointer является непустым по присутствию указателем на корень; `nil` не подменяет корневой путь.

Проверка всех определений через B01 выполняется раньше подстановки. Внутри подстановки строгий разбор шаблона предшествует поиску `null` и обработке ссылок. Это способ реализации, а не контракт приоритета независимых ошибок; тесты с несколькими нарушениями проверяют допустимую конкретную причину, отсутствие результата и безопасность.

### 5. Проверяемые границы и сохранение черновиков

Тесты используют публичные функции из внешнего пакета `configuration_test`, как существующие проверки A06/B01. Каждый новый сценарий проходит собственный Red → Green → Refactor; минимальная заглушка новой операции допустима только для компиляции и наблюдения поведенческого Red. Сбой компиляции или окружения не засчитывается как Red.

| Граница | Что проверяется |
| --- | --- |
| `SubstituteValues` | Синтаксис исходных строк, экранирование, `null` шаблона, локализация; регрессии типов, чисел, строгого JSON и неизменности |
| `AssembleElement` | Выбор и проверки B01 вместе с полным синтаксисом; все источники ошибок; запрет автообъявления; атомарность результата |
| `PrepareElement` / `RestoreElement` / `elementjson` | Черновики по-прежнему сохраняются; обнаружение только целых корректных ссылок не изменилось |

Обнаружение объявлений A08 сейчас уже соответствует нужной границе. Его не требуется заменять общим сканером: режим сохранения сознательно допускает ошибки и не преобразует текст. Согласованность проверяется примерами целых, экранированных и некорректных ссылок через существующий публичный контракт.

После добавления новых сценариев выполнить целевые тесты ядра и JSON-адаптера, затем существующие проверки проекта: все Go-тесты, vet, race и сборки Linux amd64/arm64 без cgo. Документация должна отдельно обозначать завершённую сборку переменных одного элемента и будущую сборку файлов Xray. Реального роутера для этих гарантий не требуется.

## Risks / Trade-offs

- Повторная обработка результата экранирования или замены → тесты буквальных `${...}`, `$$` и некорректных ссылок внутри object/array данных.
- Незаметное ужесточение сохранения → запрет остаётся в доменной сборке; регрессии `elementjson` и сценарий «сохранено, но сборка отклонена».
- Старый вызывающий код мог считать успех низкоуровневой подстановки полной проверкой → комментарии функций и документация явно описывают единую границу и предпосылку подготовленного набора.
- Избыточные копирования и повторный разбор → принимаются для изоляции входов и небольшого текущего объёма; не вводим общий изменяемый AST без потребности.
- Произвольный JSON после разрешения переменных может быть невалиден для Xray → проекция метки, зависимости и проверка итогового каталога остаются отдельными шагами.

## Migration Plan

Изменения формата хранения и миграция БД отсутствуют. Реализация добавит доменную функцию и дополнит существующую подстановку, затем обновит описания статуса и отчёт фактических проверок. Откат кода не требует преобразования сохранённых элементов.

Перед реализацией связать change с отдельной issue B02. По завершении отдельно проверить приёмку issue, синхронизировать дельту, архивировать change и закрыть issue только при выполненных критериях. Обзорная #1 остаётся открытой. Подготовка этих артефактов не означает выполнения задач или проверок кода.
