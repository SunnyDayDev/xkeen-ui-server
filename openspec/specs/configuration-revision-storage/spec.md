# configuration-revision-storage Specification

## Purpose

Восстанавливать принятые настройки, действующие назначения и неизменяемые желаемые ревизии из постоянного хранилища и фиксировать результат одной публикации без частичного изменения.

## Requirements

### Requirement: Publication inputs are read as one consistent snapshot

Операция чтения SHALL возвращать согласованный снимок запрошенного роутера и шаблона либо ошибку. Принятый общий снимок, действующее назначение с настройками и основанием порядка, редактируемые данные и текущая желаемая ревизия SHALL различаться. Отсутствие записи SHALL отличаться от повреждённой или недоступной записи.

#### Scenario: An accepted snapshot remains available after editing
- **GIVEN** ранее принятый снимок шаблона и действующие настройки роутера
- **WHEN** шаблон и роутер получают новые независимо сохранённые черновики
- **THEN** чтение возвращает прежнее принятое состояние и различимые новые черновики из одной согласованной точки

#### Scenario: An existing draft is not an active assignment
- **WHEN** открыт обновлённый файл, содержащий только данные C03/C04
- **THEN** исходные черновики доступны
- **AND** подтверждённое назначение, принятый снимок и желаемая ревизия считаются отсутствующими

#### Scenario: Damaged state does not become an empty input
- **WHEN** одна из запрошенных записей нарушает сохранённый контракт
- **THEN** чтение возвращает безопасную ошибку, а частичный снимок отсутствует

### Requirement: Revision storage preserves exact immutable payloads

Запись желаемой ревизии SHALL сохранять именованные файлы побайтово и сведения о проверенном профиле. Успех фиксации изменившегося каталога SHALL добавлять одну новую ревизию роутера. Фиксация без отличий SHALL сохранять предыдущую желаемую ревизию, при этом другие принятые настройки могут измениться.

#### Scenario: Reopening preserves current and previously recorded bytes
- **WHEN** для одного роутера зафиксированы два разных каталога и тот же файл базы открыт снова
- **THEN** желаемой является вторая ревизия, обе сохранённые записи имеют исходные имена и байты, а первая не изменилась

#### Scenario: Committing unchanged files preserves desired identity
- **WHEN** фиксация принятого состояния не содержит новой ревизии и подтверждает ожидаемую существующую желаемую запись
- **THEN** принятые настройки фиксируются, а в хранилище не появляется новая желаемая ревизия

### Requirement: Publication storage checks expectations before committing

Фиксация SHALL проверять ожидания по всем использованным записанным состояниям и изменяемым черновикам. Проверка и запись SHALL быть атомарными. Ошибка или конфликт SHALL оставлять принятые данные и желаемую ревизию без частичной записи и возвращать безопасную диагностику.

#### Scenario: Concurrent use of the same expected state
- **WHEN** два разных результата переданы на фиксацию с одинаковыми ожиданиями активного состояния и желаемой ревизии
- **THEN** фиксируется один результат, конкурент с устаревшими ожиданиями получает конфликт, состояние победителя сохраняется

#### Scenario: Unused pending draft remains unchanged
- **WHEN** фиксация активного контекста A не использует черновик смены на B, а черновик B изменяется
- **THEN** результат для A не перезаписывает B и изменение черновика B само по себе не даёт конфликт

#### Scenario: An ordinary commit cannot change an active assignment
- **GIVEN** роутеру подтверждён шаблон A
- **WHEN** обычная фиксация содержит настройки для B либо ожидания другого роутера
- **THEN** фиксация отклоняется без смены назначения, принятых настроек или желаемой ревизии

#### Scenario: Used draft has changed
- **WHEN** между чтением и фиксацией изменён использованный черновик шаблона или роутера
- **THEN** операция возвращает конфликт и не принимает результат из более старого снимка

#### Scenario: An error occurs after an earlier write
- **WHEN** одна операция фиксации завершается ошибкой после успешной записи другого её компонента
- **THEN** обе записи отсутствуют в видимом результате фиксации, а прежнее состояние полностью доступно

### Requirement: Initial confirmation atomically accepts a first assignment

Первая фиксация назначения SHALL создавать его вместе с первой желаемой ревизией. При принятии первого общего снимка в той же операции SHALL проверяться отсутствие принятого снимка и других действующих назначений этого шаблона. Наличие действующего назначения у роутера SHALL исключать применение операции первого подтверждения.

#### Scenario: First assignment to a previously accepted snapshot
- **WHEN** зафиксирован результат первого подтверждения для уже принятого общего снимка
- **THEN** создаются действующее назначение, настройки и первая ревизия только одного роутера, а общий снимок не переписывается

#### Scenario: Competing first confirmations try to accept a template
- **WHEN** два роутера пытаются одновременно принять первый общий снимок одного шаблона
- **THEN** одна атомарная операция принимает снимок и один роутер, а другая получает конфликт без собственного назначения и ревизии

### Requirement: Shared publication inputs form one template-scoped snapshot

Групповое чтение SHALL возвращать принятый общий снимок, редактируемый шаблон и полные действующие состояния всех подтверждённых назначений выбранного шаблона из одной согласованной точки. Каждое состояние SHALL включать основание порядка и текущую желаемую ревизию. Редактируемые данные роутеров в состав не входят.

#### Scenario: A pending switch does not join the new template group
- **GIVEN** роутеру подтверждён A, а в рабочей записи указан B
- **WHEN** читаются наборы назначений A и B
- **THEN** роутер участвует только в A, с действующими настройками и текущей желаемой ревизией

### Requirement: Shared finalization accepts exactly the verified group atomically

Групповая фиксация SHALL проверять общий токен черновика, принятый снимок, точное множество действующих роутеров и ожидаемые активные и желаемые версии каждого участника. План SHALL покрывать каждого участника ровно один раз. Любое несовпадение или ошибка SHALL откатывать правку, общий снимок и все обновления роутеров.

#### Scenario: A new confirmed router changes the group without touching old members
- **WHEN** другой процесс подтверждает новое назначение к этому шаблону после исходного чтения
- **THEN** финализация отклоняется, даже если все исходные персональные токены продолжают совпадать

#### Scenario: A removed or reassigned router changes the group
- **WHEN** до записи одно из прочитанных действующих назначений исчезает либо переходит на другой шаблон
- **THEN** финализация отклоняется и сохраняет принятый результат другой операции

#### Scenario: A late write failure rolls back every earlier write
- **WHEN** правка, принятый общий снимок и запись первого роутера обработаны, а запись следующего завершается ошибкой
- **THEN** при независимом чтении и после повторного открытия видны только ранее зафиксированные данные

#### Scenario: A plan cannot omit an unchanged router or include one twice
- **WHEN** в плане отсутствует действующий участник, повторён его ID либо включён чужой ID
- **THEN** общий снимок, настройки и ревизии не изменяются
