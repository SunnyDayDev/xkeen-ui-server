# Работа с xkeen-ui-server

## Проект и контекст

`xkeen-ui-server` — публичный проект централизованного управления конфигурацией XKeen/Xray на роутерах. Центральный сервис хранит шаблоны и настройки устройств; агент роутера получает и применяет итоговую конфигурацию. Планируются развёртывание сервера в Docker и на роутере с Entware, веб-интерфейс и внешний API управления. На старте сервер и агент устанавливаются файлами/скриптами с регистрацией в `init.d`; нужны инструкция и установочный скрипт из GitHub, а не собственные `.ipk` или репозиторий пакетов.

Сейчас в репозитории находятся концепция, документация, макеты и экспериментальный Docker-стенд `lab/` с Entware/XKeen/Xray. Рабочего центрального сервера, агента и их установочных скриптов пока нет. Не выдавай проектные решения, примеры запросов или нарисованные элементы интерфейса за реализованные возможности.

## Процесс OpenSpec

- Работаем по OpenSpec. При запросе новой функциональности предлагай процесс OpenSpec и подходящий следующий этап: исследование (`openspec-explore`), предложение изменения (`openspec-propose`), реализация (`openspec-apply-change`), завершение (`openspec-archive-change`).
- Если пользователь уже выбрал этап или разрешил конкретную работу, продолжай её без повторного предложения того же процесса. Не превращай обычное исправление или уточнение документации в обязательный новый цикл планирования.
- Перед работой над изменением выполни `openspec list --json`, прочитай применимый контекст и артефакты. Следуй инструкциям соответствующего доступного навыка.
- Во время исследования обсуждаем поведение и проектные решения. Не начинай реализацию функций без перехода к реализации. Явно запрошенные пользователем правки документации и макетов выполняй в согласованной области.
- Не создавай каталоги изменений вручную: используй CLI OpenSpec. Не записывай решения как согласованные, если они пока только предложены.
- При изменении поведения обновляй связанные артефакты и документацию, чтобы они не противоречили друг другу.

## Инварианты продукта

- Центральный сервис — источник истины. Персональные настройки роутера также хранятся на сервере.
- Шаблон состоит из элементов со стабильными ID, сырым JSON и собственными переменными. Список известных интерфейсу полей Xray не ограничивает допустимую структуру JSON.
- Ссылки на переменные имеют вид `${variableName}`. Имя ищется целиком; точка является частью имени. Подстановка целого значения сохраняет его JSON-тип.
- Переопределение имеет два режима: только переменные или собственный JSON целиком. ID переопределяемого блока всегда совпадает с ID блока шаблона.
- Роутер может менять порядок общих и локальных правил. Наследование содержимого и наследование порядка рассматриваются отдельно.
- Нельзя выключить или удалить вход, используемый итоговым роутингом. Проверка должна учитывать шаблоны, локальные изменения и сырой JSON, а не только состояние формы.
- Перед подключением должны быть заполнены переменные без дефолта. Значения с дефолтом можно унаследовать.
- «Агент на связи» и «ревизия применена» — разные состояния. Недоступное устройство получает актуальную ревизию при восстановлении связи.
- Внешний API управления включается отдельно; его авторизация опциональна. Это не переключатель канала синхронизации и идентификации роутеров.

## Публичные материалы

- Используй вымышленные названия устройств, домены `example.com`, `example.net`, `*.example` и адреса из диапазонов для документации, например `192.0.2.0/24`.
- Не добавляй сведения о частных инфраструктурах, личных проектах, локальных путях пользователя, реальных узлах или учётных данных. Это относится и к слоям, текстам и метаданным макетов.
- Не помещай в репозиторий настоящие конфиги устройств, токены, клиентские реквизиты, ключи, дампы состояния или журналы с такими значениями. Примеры должны быть безопасны для публикации по построению.
- Не выбирай лицензию, не публикуй репозиторий и не подключай реальные устройства без соответствующего запроса.

## Дизайн и проверка

- Файл макетов: `design/xkeen-ui-server-design.pen`. Читай и изменяй `.pen` только через MCP Pencil.
- Используй дизайн-систему: `Tokens`, `Atoms`, `Molecules`, при необходимости `Organisms`. Повторяющиеся элементы делай компонентами и экземплярами.
- После изменения компонентов проверяй затронутые экраны: размещение, обрезку, подписи, состояния и согласованность сценариев.
- Для документации проверяй ссылки, примеры JSON и отсутствие частных данных. Когда появится код, запускай проверки, соответствующие изменению; не сообщай о пройденных проверках, которые не выполнялись.
- Общие инструкции для любых помощников находятся здесь. Файлы отдельных инструментов должны ссылаться на `AGENTS.md` и содержать только специфичные для этих инструментов дополнения.
