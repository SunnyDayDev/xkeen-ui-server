# Проверка стенда: Linux ARM64

Дата: 2026-09-05. Команды завершились с кодом 0:

```sh
docker compose -f lab/compose.yaml build router
sh lab/check.sh
LAB_RUNTIME=xray sh lab/check.sh
docker compose -f lab/compose.yaml up -d --wait --wait-timeout 40 router
```

## Наблюдаемый результат

- Настоящий XKeen запускает Xray в режиме `Other`; API доступен. При старте есть предупреждение о недоступности API прошивки на loopback-порту 79. Прозрачное проксирование не активно.
- Все пять JSON-файлов прочитаны из `/opt/etc/xray/configs`, полная конфигурация проходит проверку Xray.
- SOCKS-запрос возвращает `router-lab-ok` от локальной HTTP-мишени.
- Неверный протокол в кандидатной конфигурации отвергнут до вызова API; рабочий процесс и запросы не изменились.
- `adrules --append=false` удаляет предыдущее правило и применяет блокирующее. PID и время запуска Xray не меняются; новый SOCKS-запрос блокируется, напрямую мишень остаётся доступной.
- После записи файла блокировка сохраняется при `xkeen -restart` и при перезапуске контейнера.
- Возврат разрешающего правила через API восстанавливает запросы.
- Тот же тест проходит в режиме прямого Xray; шаг рестарта XKeen к нему не применяется.
- Рабочий экземпляр Compose остаётся `healthy`; временные тестовые контейнеры, сети и volumes удалены.

Это подтверждает конфигурационный/API-слой и управление процессом XKeen для режима `Other`. Совместимость с Keenetic firewall, TProxy, `exclude_ips`, другие архитектуры и отказоустойчивое применение будущим агентом не проверены.
